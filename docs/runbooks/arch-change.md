# 维护者自己的 A 改动和外部审阅

依据：`AGENTS.md`「自己写的改动不自己审」、`docs/collaboration.md`「Claude 自己的改动」、ADR-009 原文第 1、3、4 条和增补 1 第 2、7 条、ADR-007 增补 1 最后一段、`docs/adr/README.md`。

**输入**：维护者要写的规格、schema、ADR、CI 规则、模板、流程文档的改动；或 Luka 带回的审阅意见（「审阅 #N」）。
**输出**：一个 `arch/` PR，附审阅任务和 `docs/reviews/pr-<N>.md`；需要 Luka 确认的事已经问过并有答复。

## 1. 动手前

- 先勾选：改了意思的规格、模板、`AGENTS.md`、`GLOSSARY.md`、`docs/standards.md`、`docs/collaboration.md`、ADR 都是 **A**。只有 `docs/handoff.md`、`docs/retros/`、`README.md` 的内容，以及不改意思的错别字、排版、坏链接，才可能是 D（五条排除条件见 ADR-009 增补 1 第 1 条）。
- 需要 Luka 拍板的设计问题**一轮问完**：每个问题附推荐答案，措辞成「回答『是』就采纳推荐」。查得到的事实自己查。
- 用词对照 `GLOSSARY.md`，新概念先加术语。ADR 只在三条同时满足时写：难以撤回；不交代背景后人会奇怪；确实做了取舍。
- 新规格用 `docs/specs/TEMPLATE.md`，写明测试接缝和验收用例。

## 2. 改动

- 开 `arch/<名字>` 分支。
- 改 `tools/` 时同步改 `tools/tests/`，每条规则至少一个通过样例、一个失败样例；跑 `python -m unittest discover -s tools/tests`。
- 和规格开头「依据」列的每份文档逐节交叉核对（相关 ADR、规格、`AGENTS.md`、`docs/collaboration.md`），确认不矛盾；修订了哪份就在同一个 PR 里改哪份。
- **ADR 怎么改**（`docs/adr/README.md`）：错别字和澄清直接改；改变内容加「增补 N」节，原文保留，要外部审阅和 Luka 确认；改变方向写新 ADR 取代旧的。
- 提交末尾 `Reviewed-By: <维护者>（自检）`、`Refs: #<N>`。开 PR，正文写「给 Luka 的一句话」「改了什么」「怎么验收」，注明「等审阅」。

## 3. 选审阅者

- 审阅者要**没参与制作**，先从规格和验收标准独立判断，再看实现。
- 数据迁移、恢复、权限、事件和发布这类长期契约**必须跨模型**：审阅者和维护者来自不同的模型来源。注意这条是相对维护者说的：维护者是 Claude 时，Codex、GLM、Kimi 算跨模型；**维护者换成别家模型以后，同家的子 agent 就不再算跨模型**。
- 其他 A 可以用一个新开的、没参与过的同模型会话审，记录里写「同模型独立审阅」，不能写成跨模型。

## 4. 写审阅任务

- 写 `prompts/review.<名字>.md`（参照 `prompts/review.practices.md`、`prompts/review.tiers.md`）：背景；审阅者角色（请挑刺）；重点问题清单；用 `{{embed: …}}` 原样贴入改动的文件和依据文件；固定输出格式（结论；问题：严重程度 阻断/重要/建议、位置、问题、建议）。
- 稳定的参考资料取自 `main`，待审的改动取自 PR 的候选提交。提交到同一个分支后：
  ```bash
  python tools/make_task.py review.<名字> --draft --commit <分支头提交号> --out <临时目录>
  ```
  待审的规则不能为了生成审阅任务先合入。
- 外部审阅：任务文件交给 Luka，说明交给哪个模型、回来时发「审阅 #<PR 号>」；issue 或 PR 里记下基于哪个提交、字节数和 SHA-256（同一个提交生成的文件可以复算核对）。
- 同模型独立审阅：把同一份任务文件交给一个新开的子 agent 或会话。

## 5. 收到审阅意见

- 逐条判断：采纳 / 部分采纳 / 不采纳（写理由）。不为了少改而不采纳。
- 审阅原文和逐条答复存进 `docs/reviews/pr-<N>.md`，PR 评论贴摘要。
- 在分支上改完，跑测试。改动大或者有新设计，再请一轮。
- 涉及 ADR 增补或方向性决定的，用「回答『是』」的格式向 Luka 确认，等他答复。
- `main` 有新提交时先合进分支；CI「检查」绿勾后 squash 合入。

## 6. 合入后

- 更新路线图 issue #13 和受影响的下游 issue（例如合入后追加的验收项）。
- 影响了已派发未交付的任务的，判断要不要重新生成任务文件（`dispatch-task.md`「规格改了怎么办」）。
- 改到了 `docs/handoff.md` 第 7 节涉及的事项，顺手更新快照。

## 不能做

- 不直接推 `main`；不合入 CI 没过的 PR；不改写 `main` 的历史。
- DeepSeek 等服务的密钥绝不进对话、文件或仓库，只让 Luka 填进中转服务的设置。
