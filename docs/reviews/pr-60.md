问题
1. 未作答直接看答案，可以使五题挑战按1/1点亮
严重程度：阻断
位置： 切片规格§4末尾、§6“提示／看答案／完成”。

规格没有要求提交过作答才能看答案。按文字允许的流程：
1. 一道题首答正确；
2. 其他四道只看提示，再看答案，不产生item.answered；
3. 每道题都有“结果”，外壳写completed。
内核会合法地算出`1/1`并点亮。这说明“每道题答对或看过答案”不足以保证分母完整。页面若显示“一共5道”，还会与事件重放的成绩不一致。

建议： 本切片要求每题至少有一条持久化成功的真实作答，才允许通过“看答案”结束该题；completed前核对活动中的所有item_id都已有首答记录。不要伪造错误作答补分母。

若必须允许直接跳过，则需要明确的跳过或揭示事实，并同步定义事件和分母规则。
2. 写库失败后，内存已有事件，重试却可能被去重
严重程度：阻断
位置： 切片规格§3 API、§6“写事件／刷新”。

目前的流程是：

log.ingest → accepted → 写IndexedDB

accepted已经修改内存日志、占用事件ID和设备序号。后续事务失败，仅显示“没存上”不会撤销这些修改。重试同一原文会得到duplicate，而规格只要求accepted时写库。

因此，同一会话中的日志与刷新后恢复的日志可能不同。即使暂时不更新星星，后续重试、try和设备序号仍未定义。

建议： 明确以IndexedDB整个事务提交完成作为成功边界。通过临时日志校验，在原文、收据和序号一起提交后，再更新正式日志及界面进度；或者失败后从已提交存储重建日志，并明确重试规则。

至少验证作答写入失败、completed写入失败、事务末尾abort三种情况，确保重试及刷新后只有一份事实。
3. 发布ID没有绑定浏览器实际读取的JSON
严重程度：重要
位置： 内容规格§6.2～6.3、切片§2、构建器。

“由YAML确定性生成”不能保证部署端收到的JSON就是正确产物。陈旧缓存、漏传、人工改动或转换器变化，都可能导致同一个release_id对应不同的题目或答案。

外壳不解析YAML，无法通过YAML哈希验证JSON；事件中的content_release也就不能唯一说明孩子看过的运行内容。

建议：值得现在调整清单。

在版本化清单中登记运行时JSON的path、sha256、bytes，并将其纳入content_hash；保留YAML原始哈希供审核追溯。构建时从同一字节快照生成、检查JSON，外壳验证摘要后再使用。

若暂缓改格式，至少部署前逐份重新生成比对、固定转换器版本并一次性发布，但这仍只是过渡保证。
4. 构建和写出重新读取源文件，可能生成内部不一致的发布包
严重程度：重要
位置： tools/build_release.py 的build、write_release。

build生成清单后，write_release重新读取源文件，没有核对写出字节是否仍匹配清单。

隔离实验中，build后修改节点title，再write_release：
- 写出的YAML哈希与清单不一致；
- JSON包含修改后的title；
- 构建器没有拒绝。
此外，先写release.json再逐文件写出，失败时可能留下部分产物。未提供PR diff，无法断言原有读取流程是本PR新增，但JSON方案直接依赖其一致性。

建议： 审核、哈希、转换和写出使用固定字节快照；或写出时逐文件复核哈希。先生成完整临时目录，验证成功后再发布。
5. 小数精度向量被整数schema掩盖
严重程度：重要
位置： ingest-invalid.json第10项、事件规格§2。

1e-7被放在必须为整数的duration_ms中。即使实现完全漏掉“小数不超过6位”的规则，最终仍返回invalid。

本次实际跳过了非整数的小数精度和幅度检查，该文件26个期望值仍全部通过。当前五个动词的有效数值字段都要求整数，无法仅靠摄入结果独立验证小数规则。

建议： 为通用数值校验函数增加独立向量，不必提前实现sim.*。包括：
- 0.000001接受，`1e-7`、`1.5e-7`拒绝；
- 普通写法的6／7位小数；
- 非整数接近`1e9`；
- 正负安全整数边界、非有限值和`-0`。
JavaScript可先检查有限性，整数值用`Number.isSafeInteger`；非整数将`String(x)`拆成尾数与指数。若尾数小数位数为d、指数为e，实际小数位数为`max(0,d-e)`。所以`1.5e-7`是8位。

不要按原始JSON文本数位数，也不要用乘以一百万后是否整数替代。`1`、`1.0`、`1e0`均应视为整数1。
6. best及其他投影规则缺少能区分错误算法的反例
严重程度：重要
位置： 掌握度向量、切片§7。

现有主要候选`3/4→4/5→8/10`的正确率与正确题数同时增加。本次将best改成“correct最多优先，再取answered最多”，9份向量仍全部通过。

7. 多标签页会争用序号，也可能互相放弃挑战
严重程度：重要
位置： 切片§6。

两个标签页共享dev_id。如果各自在内存递增序号，会争用同一(device_id, device_seq)。

第二页启动时若把本设备所有未结束尝试写成abandoned，还会结束第一页仍在进行的挑战；第一页继续写事件后，尝试违反规则4。

建议： 首切片明确同一设备仅允许一个活动写入者，并用浏览器锁或等价机制保证。若允许并发，则需要共享事务分配序号，以及会话归属和存活判断。
8. quiz.js的界面职责与纯函数约束冲突
严重程度：建议
位置： 切片§1。

quiz.js要“画挑战、处理作答和提示”，同时所有引擎模块又被要求不碰DOM。实现者可能交付纯状态机，也可能直接操作DOM，测试接缝不同。

建议： 明确quiz.js为纯状态机，输入动作，输出界面状态和事件意图；DOM留在app。洗牌所需的题序或随机源由外壳传入。
9. 跨语言字符串边界尚未完全明确
严重程度：建议
位置： payload长度规则、判分规整和分数解析。

JSON Schema的字符长度按Unicode码点计算，JavaScript的string.length按UTF-16单元计算。“空白／空格”也未规定统一集合；Python strip和JavaScript trim对部分字符处理不同。

建议： 明确码点计数与允许的空白集合，并补充：
- 32／33个补充平面字符的长度边界；
- 全角小数点`２．５`；
- 分数6位正边界、分母7位；
- 正确答案与common_wrong同时命中时，正确优先。

不建议在投影中硬编码“至少五道题”：单题活动的合法`1/1`与五题活动漏记四题是不同问题。

## 问题

### 1. 清单接受 `version: 1.0`，Python 和 JavaScript 却会算出不同发布哈希

- 严重程度：**阻断**
- 位置：`docs/specs/content.md` §6.2；`schemas/release.schema.json` 的 `version`、`engine_min`；`tools/build_release.py` 的 `load_document`、`build_package`、规范 JSON 生成。
- 问题：规格把“JSON Schema 意义上的整数值”当成了“Python 一定以整数形式序列化”。YAML 的 `version: 1.0` 会解析成 Python float；它是整数值，能通过附件 release schema 的 `type: integer`。构建器把该值直接放入清单，Python 写成 `"version":1.0`，JavaScript 解析并规范化后写成 `"version":1`。两边都照规格实现，哈希仍不一致，浏览器会拒绝该发布。`engine_min` 及 version 字段还没有 schema 上界，和 §6.2 声称的“不超过 2^53−1”不一致。

  已复现：用附件的文件条目生成函数和 release schema 构造 `version=1.0` 清单，schema 校验通过；按附件公式算出的 Python 摘要为 `c79b780f5d35ee621963124432d61947bf83ceca0e6980eb07643480a7680c7f`，JavaScript 递归排序后摘要为 `d5597af379a7f37012eca37b9b4844a20d546d382aae2d6a808cb02ff4e0f6d1`。本实验隔离验证规范化和 schema，不声称已通过缺失的发布门禁。
- 建议：对**清单中的** version、engine_min 等数值先验证有限、安全、整数值，再统一转换为 Python int；或明确拒绝这些字段的浮点表示，并用构建测试落实。给相关 schema 字段补一致的安全整数上界。增加 Python 生成、JavaScript 验证的共享清单夹具，包含 `version: 1.0`、边界整数、嵌套 json 条目和非 ASCII 内容文件。

  不必重新序列化运行内容的 JSON 来核对哈希：sidecar 应始终按收到的 UTF-8 字节验证。清单键都是 ASCII 时，码点排序与 RFC 8785 的 UTF-16 排序不会产生差异；这里真正的问题是数值输出形式。[参考：RFC 8785 §3.2.2.3、§3.2.3](https://www.rfc-editor.org/rfc/rfc8785.html)

### 2. “拿到锁就一直写到关闭”缺少失锁与页面恢复规则

- 严重程度：**阻断**
- 位置：`docs/specs/slice-1.md` §6.3“一个窗口写事件”“启动”；§6.2 `commitEvent` 的调用前提。
- 问题：Web Locks 的持有期由回调返回的 Promise 决定，不是由保存下来的 `lock` 对象或页面存活时间决定。规格未要求处理锁请求 Promise 的结束/异常，也未定义后台或历史缓存恢复后的写权限。WebKit 的已核验源码在 `PageWillBeSuspended` 或 `BackForwardCache` 挂起时清理锁，并拒绝相关 Promise；不能假定页面的旧 JavaScript 状态恢复时仍持有原锁。[Web Locks 规范](https://www.w3.org/TR/web-locks/)；[WebKit 固定修订源码：`WebLockManager::suspend` 与 `clientIsGoingAway`](https://chromium.googlesource.com/external/github.com/WebKit/webkit/+/bb09dadea639bc4cf5ef573e761c882ca2cfcb7e/Source/WebCore/Modules/web-locks/WebLockManager.cpp)

  风险顺序是：A 页暂停并失锁 → B 页取得锁、重放并把 A 的未完成尝试写成 abandoned → A 页恢复后沿用旧日志和序号继续写。这样会重新出现序号争用、结束事件之后追加作答。上述源码说明该场景需要设计处理；不代表已在用户的特定 iPad/Safari 版本复现。
- 建议：为外壳明确“只读／持有写锁／正在恢复”状态。持锁回调用未结束的 Promise 覆盖写入期；锁丢失或生命周期恢复存在不确定性时，先禁止写入。重新取得锁后，重新读库、重建日志和序号、处理遗留尝试，再允许开始新的挑战，不能继续旧挑战状态机。对挂起前尚未确定结果的事务，先从数据库确认结果，不把它直接当成失败。

  首切片可采用简单策略：失锁或 BFCache 恢复后提示重新打开/重新初始化，避免自动接续旧挑战。首次建立 learner/device 信息也必须在同一写入所有权下原子完成，防止两个空库窗口各生成一套身份。只读页提供“重新尝试”或刷新指引即可，暂不做自动接管，也不要用 `steal` 或超时心跳强抢锁。验收增加“A 后台或离开页面 → B 取得写权限 → A 恢复”的测试。

### 3. 提交方案正确，但三种失败测试尚未覆盖提交边界两侧

- 严重程度：**重要**
- 位置：切片 §6.2、§6.3；计划中的 `app/test/commit.test.js`、`app/store.js`。
- 问题：目前三种场景都关注“事务没有提交成功”。它们不能证明“已经提交、但还没 ingest/回传 saved”的恢复，也不能证明整个 `check → store → ingest` 阶段只有一个调用者。单窗口只排除其他窗口，不能自动排除同一窗口双击重试、启动清理与交互写入并发。`duplicate` 分支把内存存在当成已持久化成立，需要先明确“日志只能来自重放或已提交事务”的不变量。

  此外 `store` 仅声明三个方法，`loadAll` 的结果未写出设备信息和 nextSeq；`commitEvent` 内的 `nextSeq` 从哪里来、是否校验旧值也未定。所有原文共用收件表时，必须能保存冲突副本和无法解析的输入，不能简单把 `event_id` 或 `(device_id, device_seq)` 当成收件表的全局唯一键。
- 建议：保持现有方案，补足以下边界即可，不必推翻重做：

  1. 所有本地提交和启动清理通过同一串行入口；在途重试只启动一次存储操作。除该入口与启动重放外，外壳不直接修改日志。
  2. `store.commit` 只在事务 `complete` 后 resolve；abort/error reject，不能在单条 put 的 success 时 resolve。原文、收据、序号在同一事务内原子更新。[IndexedDB 事务生命周期](https://w3c.github.io/IndexedDB/#transaction-lifecycle)
  3. nextSeq 按持久化元数据校验并推进；重试同一 raw 不额外推进。收件表使用持久化到达序号排序；接收事件的唯一约束与隔离原文保存分开设计。
  4. 写明 `loadAll` 如何返回一致的原文、身份与序号快照。`quarantined` 不是状态机的 saved；只有 accepted，或确认对应事实已持久化的 duplicate，才推进挑战。
  5. 如果提交已完成但内存同步异常，冻结写入并从存储重建，不能声称“内存和存储都没变”。这不是事务中止，错误处理应分开。

  至少增加：事务完成后、ingest 前模拟页面终止；ingest 后、saved 前模拟终止；双击 retry；启动清理未结束时尝试开始挑战；隔离原文重放；事务失败后检查原文、收据、nextSeq 三者均未改变。真假存储的关键差异还应有一个实际 IndexedDB 冒烟测试，家长的正常试玩不能替代事务回滚测试。

### 4. 启动补写 abandoned 必须沿用旧尝试的 content，不能套当前发布

- 严重程度：**重要**
- 位置：切片 §6.3“启动”“写事件”；事件规格 §6.3 规则 3。
- 问题：启动要求给旧尝试补 abandoned；通用写事件规则又说 `content_release` 是当前发布包、`activity_version` 是当前活动版本。若孩子在 R1 的活动 v1 中途关闭，部署更新到 R2/v2 后重新打开，照通用组装规则补写会使同一尝试混入两份 content，触发规则 3。旧活动被移出新包时，甚至没有当前活动可查。
- 建议：补写事件从旧尝试事实复制完整 `content`、`attempt_id`、`learner_id` 和原设备身份；仅生成新 event_id、当前 occurred_at、下一个 device_seq、system actor 和 reason。冻结每次新挑战的内容上下文，同一尝试内不切换发布。明确只补写尚无结束事件、可合法闭合的尝试；已有 completed/abandoned 的不再补。

### 5. 两类新增边界用例仍未区分“真正校验”与“碰巧判错”

- 位置：`kernel/vectors/numbers.json`；`engine/vectors/grading.json` 第 66、67 条及旧第 51 条；`tools/tests/test_vectors.py`。
- 问题：独立变异实验发现两处覆盖缺口：

| --- | --- | --- |

### 6. 先 check 再 ingest 的结果相同，还不足以证明 check 无副作用

- 严重程度：**重要**
- 位置：切片 §3、§7 的执行器规则。
- 问题：如果错误实现的 `check(invalidRaw)` 已向隔离区追加原文，随后 `ingest(invalidRaw)` 再追加一次，两次返回仍都是 invalid；已接收 raw 和最终 mastery 也都正确，现有通用断言抓不到。`check` 改 detail、隔离记录或其他可观察状态也不一定改变返回值。附件 Python 对照实现没有 check API，所以它目前没有验证这一契约。
- 建议：执行器对 check 前后的 `events()`、`raw()`、`quarantined()` 做深快照比较，连续调用两次 check 后仍不变；再 ingest 一次，确认接收或隔离只发生规定的一次。重复和冲突的首次原文也保留检查。`mastery_after` 的全量投影定义清楚，可以保留；若以后引入独立增量投影器，再增加“同批次增量结果等于全量结果”的测试，当前不用提前实现。

### 7. 数字判分避开非二进制精确小数，会漏掉真实的容差边界误判

- 严重程度：**重要**
- 位置：切片 §5 数字题；`engine/vectors/grading.json` 的 about；`tools/tests/test_vectors.py::ref_grade`。
- 问题：文件明确说明数字都选择二进制可精确表示的值。这样本轮 71 条虽然全对，仍不能支持规格对一般十进制答案的承诺。独立复现：正确值 `0.3`、容差 `0.1`，输入 `0.4`，数学上差恰好为 `0.1`，应判对；附件 Python 对照实现和直接照做的 JS 都算出 `0.10000000000000003`，从而判错。它还会影响 common_wrong 的边界归属。
- 建议：在派发三种判分实现前，明确十进制比较策略。小规模内容可限定值、容差及输入的小数位数/幅度，按十进制整数缩放精确比较；或使用明确的十进制解析算法。不要随意加一个统一 epsilon，那会悄悄扩大容差。至少补 `0.3±0.1` 两侧边界、略超边界、正确区间与误区区间重叠的用例。

  这不是要求修改本轮已经正确的 11 条期望；是对原有泛化规则的新发现。虽然 1a 页面只有选择题，但本稿把数字判分代码也放进 1a，仍应把这一合同说清楚，避免 1b 直接启用错误实现。

### 8. 纯状态机还缺完成意图、保存确认和启动门槛的明确接口

- 严重程度：**重要**
- 位置：切片 §1、§6.1、§6.3；`startQuiz/step` 与 `commitEvent` 接缝。
- 问题：`quiz.js` 被要求不读时间；`startQuiz(activity, order)` 没有时间参数，四种 action 也没有 elapsed 值，却要产出带合法 payload 的 completed，而事件要求 `duration_ms`。可以由外壳补，但当前“意图”与“完整事件 payload”的责任边界没有明确写出。`saved` 没有关联到具体 pending，完成后的重复确认、旧提交回调是否还能推进新 pending 也未定义。startQuiz 前必须先存好 started 的顺序应成为契约，而不是依赖实现者理解。
