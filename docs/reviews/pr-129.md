## 总评

**改完以后可以接受。** 大方向是对的，也是成熟的做法：HKDF 给每个文件派生新密钥，分块 AES-GCM，随机数里放块序号和末块标记（STREAM），文件头整行作 AAD，`key_check` 把「密钥不对」和「文件坏了」分开，内容版本和文件格式版本分开，恢复计划写成纯函数，恢复走和本机摄入同一套 `log.check`。我在 Python 和 Node（Web Crypto）里各写了一遍，`compression: none` 时**两边独立算出的文件逐字节相同**（SHA-256 一致），截断、删一个字节、换块顺序、改一个字节、改文件头、尾部多出字节、密钥错，全部按规格被发现。

但是这份规格定的是改不回来的东西，现在还有几处会让「两个人照着写出唯一的实现」做不到，或者会在真实使用中丢数据、卡死：

- **阻塞**（3 条）：`chunk_size` 写死和测试里要改小互相矛盾（R1）；JSON 的写法（键的顺序、要不要转义非 ASCII、数字怎么写）没定，逐字节的黄金向量没法独立算出（R2）；恢复密钥什么时候存、谁能生成、恢复时遇到另一把密钥怎么办没写清，可能出现「纸上的密钥打不开这台设备做的备份」（R3）。
- **应改**（14 条）：主要是 gzip 的读写约定、UTF-8 和 BOM、文件头的严格程度、恢复密钥的输入宽容规则、恢复后本机序号可能撞车而卡死写入、分批写的事务边界和 `restoring` 标记、写锁和数据库升级、存储接口没定、旧收据去重是平方复杂度、内容发布包「能从网站重新拿到」不成立、私人文字进备份时和 ADR-010 数据密钥方向的关系、测试缺口。
- **建议**（8 条）。

另外，#8 的 6 条验收标准里有 2 条（删除先应用、双向完整性检查）整条推迟到 `backup-manifest/2`，推迟本身站得住（v1 没有私人文字），但这偏离了 #8「被阻塞于 #25」的原定顺序，**要 Luka 拍板**，并且要把「竖切片 2 不能先于 `backup-manifest/2` 上线」写成硬门槛（R12、第 5 部分）。

## 逐条发现

### R1 · 阻塞 · 3.1、3.2、测试接缝 — `chunk_size` 既「固定」又「测试里可以改小」

**问题**：3.1 写「v1 固定 1048576」，同时「值不对按文件坏了处理」；测试表又要求「明文正好 2 个整块（`chunk_size` 在测试里可以改小，例如 64）」。照 3.1 写的严格读程序会把 64 的文件判成「文件坏了」。实验：我的 Python 读程序加上 `chunk_size == 1048576` 的检查以后，64 的样例文件得到 `corrupt-header(chunk)`。而 3.4 要求样例文件**永久**留在 `tests/fixtures/backup/`，以后的读程序都要能读：到底能不能读 `chunk_size: 64` 的文件，现在就得定。

如果不改小，要证明「末块是满块」就得造 2 MiB 的样例，不现实。

**建议**：读程序接受 `chunk_size` 为 64～16777216（16 MiB）之间的整数（或者限定为 2 的幂）；写程序 v1 固定写 1048576。黄金向量和永久样例用 64。顺带写明：读程序按文件头的 `chunk_size` 切块，不假设 1 MiB。

### R2 · 阻塞 · 3.1、4、9、测试接缝 — JSON 的确切写法没定，逐字节的期望值没法独立算

**问题**：规格要求「整个文件逐字节等于期望值」「可读导出逐字节等于期望值」，期望值又要用 Python 独立算出。可是：

1. **文件头的键顺序**：只说「紧凑写法」，没说键的顺序。文件头是 AAD，顺序不同就是另一个文件。示例里的顺序看上去是约定，但没写成规则。
2. **Python 和 JS 默认写法不同**（实验 E5）：同一个对象 `{"n":"说明 \t\x7f/","x":1.0}`，
   - JS `JSON.stringify` → `{"n":"说明 \t/","x":1}`
   - Python `json.dumps` 默认 → `{"n": "说明 \t\u007f/", "x": 1.0}`（有空格、非 ASCII 被转义、`1.0` 保留）
   - Python 加 `separators=(",",":"), ensure_ascii=False` 以后字符串部分一致，但 `1.0`、`100.0`、`-0.0` 还是和 JS 不同。
   可读导出第一行的 `note` 是中文，清单行、收据行、导入记录行的键顺序也都没定。
3. **清单里收据的键顺序**：收据从 IndexedDB 读出来是什么顺序就是什么顺序，规格没说要不要按固定顺序重写。

**建议**：加一小节「本规格里 JSON 行的写法」：
- 键按规格里示例 / 表格的顺序写（逐个列出：文件头 9 个、清单 6 个、`counts` 4 个、`end` 3 个、导出首行 5 个、导入记录 11 个、收据按 `event_id, recorded_at, source, batch_id, clock_skew_ms`）；
- 不加空格；非 ASCII 原样写 UTF-8，不转义；只转义 `"`、`\`、U+0000～U+001F（用 `\b \f \n \r \t`，其余 `\u00xx` 小写），这正是 `JSON.stringify` 的行为，Python 要写成 `json.dumps(v, separators=(",",":"), ensure_ascii=False)`；
- 这些行里的数只有非负整数，写成不带小数点、不带指数的十进制。
- 读的时候**不要求**写法规范（校验和已经覆盖原始字节），只要求字段对；写的程序必须按上面写。这样黄金向量能逐字节对，读又不会因为别的程序多一个空格就拒收。

（`inbox` 行里的 `raw` 是字符串，按上面的规则写，不受影响。）

### R3 · 阻塞 · 2、6.3、7 — 恢复密钥的生成、保存时机和「一家两把钥匙」

**问题**：
1. **什么时候存**：规格只说第一次做备份时「先给一把恢复密钥」，家长抄好、完整输入一遍「才算完成」。没说密钥什么时候写进 `meta.recoveryKey`。如果确认通过后才存，家长抄到一半刷新页面（或 Safari 把页面挂起），下次会生成**另一把**，纸上那把作废，家长不知道。
2. **谁能生成**：生成是一次写入。规格没说只读窗口能不能「做一份备份」。两个窗口同时第一次点，会各生成一把。
3. **一家两把**：6.3 说本机已有密钥且和输入的不同时「不覆盖，提示，备份照样恢复」。典型路径：新电脑先打开 Curio（建了身份），家长好奇点了「做一份备份」→ 生成了 K2（收件表是空的也没禁止）；然后「从备份恢复」输入 K1 → 本机留着 K2。之后这台电脑做的备份都要 K2 才能打开，而家长纸上抄的是 K1。这和第 2 节「以后的备份都用这一把」、ADR-010 第 7 条「主密钥就是家庭恢复密钥」直接冲突，是一条真实的丢数据路径。
4. **恢复成功后存密钥**不在 6.3 的事务列表里，是不是放在最后一个事务里没写。

**建议**：
- 密钥在**显示之前**就在一个事务里写进 `meta.recoveryKey`（已有就中止，像 `store.init`），另存 `meta.recoveryKeyConfirmed`（或 `{bytes, confirmed_at}`）。没确认的不能用来做备份；再进来时显示同一把，不重新生成。
- 生成、确认、写 `lastBackup` 都只在拿着写锁的窗口里做；只读窗口的「做一份备份」可以做（只读事务），但如果本机还没有已确认的密钥就提示「请在正在用的那个窗口里做」。
- 收件表为空（6.1 第一种情况）时不允许生成密钥，按钮改成「从备份恢复」为主。
- 恢复时：本机密钥**没确认过、或者从没用来做过备份**，就用输入的那把覆盖；**已经用过**而且不同，就不是「提示一下」，而是明确告诉家长两把都要保留，并在家长页一直显示「这台设备用的是另一把恢复密钥」。更好是写 ADR 之前直接拒绝产生第二把（v1 不能换密钥，就也不该悄悄出现第二把）。
- 写明：恢复成功后的 `meta.recoveryKey` 在最后一个事务里和导入记录一起写。

### R4 · 应改 · 3.1、3.2 — gzip 的读写约定不够，两边会对同一个文件给出不同结论

**实验**（E3、E4）：
- Python `gzip.compress(p)` 默认把**当前时间**写进 gzip 头的 MTIME，两次压缩结果不同；`compresslevel` 默认 9（XFL=02），OS 字节 0xFF。
- Node 22 `CompressionStream("gzip")`：MTIME=0、XFL=00、OS=03，确定（同一输入跑两次、按不同大小分块喂入都得到同样的字节），但和 Python `compresslevel=6, mtime=0` 的输出**只差第 9 字节（OS）**。浏览器之间的 deflate 实现也未必相同。所以 `gzip` 模式不可能要求逐字节相同，规格目前也没要求，但要明说。
- **多段 gzip**（两个 member 首尾相接）：Python 和 Node 都能解成拼起来的内容。
- **gzip 后面有零字节填充**：Python 照样解开；Node `DecompressionStream` 报「Trailing junk」。
- **gzip 后面有别的字节**：两边都报错。
- 带 FNAME 标志的 gzip：两边都能解。

也就是说，一个写程序（例如以后的 Python 工具）多写几个零字节，浏览器判「坏了」，Python 判「好的」。

**建议**：3.2 写明：
- 写：恰好一个 gzip member；FLG=0（不带文件名、注释、额外字段）；MTIME=0；XFL、OS、压缩级别不限定（所以 `gzip` 模式不要求逐字节相同，逐字节的黄金向量只用 `none`）。
- 读：必须恰好一个 member，member 结束后不能再有任何字节（包括零字节）；CRC32 和 ISIZE 必须对。Python 读程序要用 `zlib.decompressobj(16+zlib.MAX_WBITS)` 并检查 `unused_data == b""`，不能直接 `gzip.decompress`。
- 加两个黄金向量：「两个 member」「末尾补零」都判「文件坏了或不完整」。

### R5 · 应改 · 3.5、4、9 — UTF-8 解码和 BOM 没定死，JS 和 Python 结论不同

**实验**（E6）：
- `new TextDecoder("utf-8", {fatal: true})` 默认会**悄悄去掉开头的 BOM**；Python `bytes.decode("utf-8")` 保留 U+FEFF，`json.loads` 随后报「Unexpected UTF-8 BOM」。
- `new TextDecoder()`（不加 `fatal`）遇到坏字节换成 U+FFFD，不报错。

明文开头要是有 BOM，JS 读程序当它不存在，Python 读程序判坏。规格说 `sha256` 是「这些行的 UTF-8 字节」的哈希，如果 JS 按解码后再编码的文字算，又会和按原始字节算的不同。

**建议**：第 4 节写明：明文文档不能以 BOM 开头（有就是「文件坏了」）；必须严格 UTF-8（JS 用 `TextDecoder("utf-8", {fatal: true, ignoreBOM: true})` 再检查第一个字符不是 U+FEFF）；`end.sha256` 按**解压后的原始字节**算，不先解码。可读导出同样不带 BOM。加一个「明文以 BOM 开头」的黄金向量。

### R6 · 应改 · 3.1、3.5 — 文件头的严格程度和几个边界没写

**问题和实验**（E2）：
1. **重复的键**：`{"…","compression":"none",…,"compression":"gzip"}`，JS `JSON.parse` 和 Python `json.loads` 都取后一个，但「不允许有表里以外的字段」没覆盖这种情况，第三方解析器可能取第一个。AAD 能保证文件头没被改，挡不住写程序自己写出重复键。
2. **Base64**：Python `b64decode(..., validate=True)` 和 `atob` 都接受末尾多余位不为零的非规范写法（`…AAB==` 解成全零）。要说清楚是只看解出来的长度，还是要求规范写法。
3. **第一行和 `format` 不一致**：第一行 `CURIO-BACKUP/1`、`format` 是 `curio-backup/2`，按表该提示「更新 Curio」还是「坏了」？第一行**不在** AAD 里。
4. **「整行不超过 4096 字节」**含不含结尾的 `\n`；读程序读了 4097 字节还没见到 `\n` 时怎么判。
5. **第一行**：`CURIO-BACKUP/1\r\n`、`CURIO-BACKUP/01` 算什么。
6. **边读边解时怎么认出末块**：只有读到文件结尾才知道哪块是末块，流式读程序要多读一个字节判断。规格说「最后剩下的不足一整块（或正好一整块）的就是末块」，意思对，但写成步骤更不容易错。

**建议**：
- 读程序按固定顺序把解析出的文件头重新写一遍（R2 的写法），**必须和原始那一行逐字节相同**，不同就是「文件坏了」。这一条同时解决重复键、多余空格、非规范 Base64、转义写法这些问题，Python 和 JS 都好做。
- 第一行必须正好是 `CURIO-BACKUP/` 加一个不带前导零的十进制数加 `\n`；数字不是 1 → 「请先更新」；是 1 而 `format` 不是 `curio-backup/1` → 「文件坏了」。也可以把第一行一起放进 AAD（AAD = 前两行的原始字节，不含第二个 `\n`），这样改第一行也会被发现；这要现在定，以后改不了。
- 写明「4096 字节不含 `\n`；读到第 4097 个字节仍没有 `\n` 就是『文件坏了』」。
- 把末块的判断写成步骤：「读到一整块（`chunk_size + 16` 字节）以后，再看后面还有没有字节：没有，它就是末块」。

### R7 · 应改 · 2 — 恢复密钥的输入规则：全角字符、报错顺序、示例密钥校验位不对、校验强度说过头

**实验**（E1）：
- 规格里的示例 `7KQ2M-XW9PD-4HN6T-RB3CJ-8FVA2` 按规格自己的规则算，**校验位不对**。示例会被抄进代码注释、测试和打印页，最好用一把合法的，或注明「示意，不是合法密钥」。
- 校验位只有 5 位，**单个字符抄错有约 1/32 的机会漏过**（实测 744 种单字符替换里 20 种漏过，2.7%），「几乎一定当场发现」说过头了。相邻两个字符对调 22 种全部发现（因为整体哈希）。漏过的也不会出事，只是落到「恢复密钥不对」那一句。
- **iPad 的中文输入法**常常打出全角字母、全角数字、全角连字符「－」和全角空格。按现在的规则，全角输入全部报「有一个字不对」。`grade.js` 在 slice-1 第 5 节对全角处理得很仔细，这里也该一样。
- **报错顺序**：输入 `ABCU`，先报「有一个字不对」还是「位数不对」？我的两种实现给出不同结果。测试表要求「四种提示」，顺序必须定。

**建议**：
- 规整步骤写成有序列表：① 全角 `０-９Ａ-Ｚａ-ｚ` 换半角，全角空格、全角连字符「－」、长破折号「—」也去掉（或者直接 NFKC，再去掉 `-`、`‐`、`－`、空格类字符）；② 去空格和连字符；③ 转大写；④ `O→0`、`I/L→1`；⑤ 有不在字母表里的字符 → 「有一个字不对」；⑥ 长度不是 25 → 「位数不对」；⑦ 校验位。
- 换成合法的示例密钥（例如用 15 个字节 `01..0F` 算出的 `04106-1050R-3GG28-A1C60-T3GF6`）。
- 「几乎一定」改成「大约 97% 能当场发现；漏过的会在下一步报『恢复密钥不对』」。如果要更强，可以把校验位换成 GF(32) 上带权的线性校验（24 个不同的非零权重），能发现**全部**单字符错误和相邻对调，长度不变；这要现在定。

### R8 · 应改 · 6.1、6.3 — 恢复以后本机序号可能和备份里本机自己的事件撞车，写入从此卡死

**问题**：6.1 说恢复以后 `nextSeq` 不变。正常情况下备份里不会有本机 `device_id` 的、序号不小于 `nextSeq` 的事件。但有现实路径会出现：设备的网页存储被回滚到较早的状态（例如 iPad 从 iCloud/电脑上的整机备份恢复，Safari 的网站数据跟着回到过去），家长再用这台设备**自己**以前做的、更新的 `.curio` 文件恢复。

**模拟**（E7，用仓库里的 `RefLog`）：本机有 `dev_B` 的 1、2，`nextSeq = 3`；备份里有 `dev_B` 的 1～4。合并后 3、4 被接收。下一条本机事件用 `device_seq = 3` → `quarantined:conflict`。按 slice-1 6.2 第 3 步，`committer` 把它存进收件表然后抛错，`nextSeq` 不前进，**之后每一次都一样**，这台设备再也记不了东西，收件表里还越积越多隔离的副本。

**建议**：6.2 的结果里加 `nextSeq`：`max(existing nextSeq, 合并后日志里本机 device_id 的最大 device_seq + 1)`，6.3 的最后一个事务写回 `meta.nextSeq`。加一个黄金向量。顺带：备份里本机 `device_id` 的事件出现时，`report` 里提一句「备份里有这台设备以前的记录」，方便排查。

### R9 · 应改 · 6.3 — 分批写的事务边界、`restoring` 标记的语义、没有退路

**问题**：
1. 「每个事务最多 500 条」，500 条什么？如果收件表的原始文字和它的收据不在同一个事务里，写到一半失败后，再恢复一次时这些事件都是「重复」，不会再生成收据，**收据永远缺了**（6.4 只会列出来，修不回来）。
2. `restoring = {batch_id, started_at}` 不记是哪个文件。标记还在时，家长换一个文件、甚至换一个孩子的文件恢复，规则没说。如果第一个事务（标记 + 换身份）写完就断了，收件表还是空的，按 6.1 第一种情况可以恢复**任何**孩子的备份，身份又换一次，没有问题，但是标记里的 `batch_id` 会被覆盖还是怎么样，没写。
3. **没有退路**：标记还在时外壳一直不进「可以写」，只说「请再从同一个备份恢复一次」。如果文件找不到了（网盘里删了、密钥忘了），这台设备就永远不能用，只能清浏览器数据，而规格自己说写进去的都是合法、按顺序的事件。
4. 标记还在时 `openSession` 要不要照常补写 `attempt.abandoned`、要不要建身份，没写。
5. 空间检查：「原始文字总字节数」是 UTF-8 还是 UTF-16 字节，没写（IndexedDB 里字符串大约按 UTF-16 占空间）。

**建议**：
- 写明：每个事务里，一条原始文字和它的收据（如果是 `accepted`）一起写；`appendArchive` 可以单独成批（重做时会被去重）。
- 标记里加 `file_created_at`、`file_device_id`、`file_learner_id`；标记还在时只允许恢复 `learner_id` 相同的备份（身份已经换了时）。
- 给一个「不恢复了，就用现在这些」按钮：只删掉标记，`report` 写进一条 `partial: true` 的导入记录。写进去的都是合法事件，删标记是安全的。
- 写明标记还在时 `openSession` 照常做第 1～3 步（建身份、重放、补写本机的放弃），只是不进「可以写」。
- 空间按「原始文字的 UTF-16 码元数 × 2 字节 × 2」估，或者干脆写「UTF-8 字节数 × 3」，定一个。

### R10 · 应改 · 6.3、5 — 写锁、`committer` 冻结、数据库升级时的旧窗口

**问题**：
1. 「开始前把 `committer` 冻结」：冻结不能撤销（slice-1 6.2）。6.1 判断不能恢复、空间不够、密钥不对时，`committer` 已经冻结了，这个窗口还能不能接着用？规格没说要重新加载。
2. **恢复进行中失去写锁**（Safari 挂起页面会收回锁，slice-1 6.3）：恢复的事务直接走存储，不经过 `committer`，规格没说失锁以后要停。另一个窗口拿到锁以后看到 `restoring` 会不进「可以写」，这挡住了它写事件，但原窗口的恢复事务还在继续写，两个窗口都会在之后读到一半的状态。
3. **数据库从 1 升到 2**：`app/store.js` 里旧连接的 `onversionchange` 只是 `db.close()`。如果旧版本的页面（Service Worker 缓存、或另一个没刷新的标签页）正拿着写锁，新版本在只读窗口里打开数据库触发升级，旧窗口的连接被关掉，它的下一次 `submit` 才失败，提示「出错了」，而且它还一直拿着锁，新窗口只能是只读。另外，演示页回退到旧提交时，旧代码用版本 1 打开版本 2 的数据库会得到 `VersionError`，停在错误页（不丢数据，但要写进去）。

**建议**：
- 冻结放在「6.1 判断通过、空间够、家长点了确认」以后；不管恢复成功还是失败，结束后都重新加载页面。
- 恢复的每个事务之前检查一次是否已失锁（照 `session.js` 的 `guardDeps` 做法），失锁就停，留着标记。
- 第 5 节加：`onversionchange` 按「失去写锁」处理（冻结、提示「请刷新页面」），并且升级只在拿着写锁的窗口里做（只读窗口用 `indexedDB.open(name)` 不带版本号先看版本，低于 2 就提示刷新正在用的那个窗口）。写明回退到旧代码时会停在错误页。
- `onupgradeneeded` 按 `oldVersion` 分支：0 → 建全部 5 个仓库；1 → 只建两个新的（原则 7 的迁移脚本）。

### R12 · 应改 · 1、3.4、6.4、「不做什么」 — 私人文字进备份的方向要现在说清楚，不然 `backup-manifest/2` 会和 ADR-010、事件规格 4.2 打架

**问题**：
1. ADR-010 第 7 条第 3 点：每个对象（私人文字、附件）用**自己的数据密钥**加密，数据密钥「单独放在密钥库里，**不进备份包**，不然销毁就是空话」。ADR-006 第 8 条对附件也这样说。本规格第 3.4 节说加私人文字时「只升内容版本，文件格式可以不变」，暗示文字明文放进 `backup-manifest/2`、只受恢复密钥保护。这样一来，删掉的文字在每一份旧 `.curio` 里都能被拿着恢复密钥的人读出来；事件规格 4.2 接受「旧备份改不了」，但 ADR-010 选的是「靠数据密钥让旧备份里的那份读不出来」。两种做法要选一个，选了就改不回来（一旦有带明文文字的备份文件散出去）。
2. 如果选 ADR-010 的做法，「完整备份包能单独恢复」（ADR-006 表格）就要求密钥库也在某个地方：要么备份包里带一份被恢复密钥包住的密钥库快照（那么销毁要等旧备份过期），要么备份包不能单独恢复文字。这是 CURIO-008 / 竖切片 2 要定的，但本规格应该写明「`backup-manifest/2` 加文字之前必须先有这个决定」。
3. 事件规格 4.2：「用旧备份恢复时，恢复工具必须先拿到最新的删除事件（从后端或较新的备份）再完成恢复，否则要明确提示」。v1 的格式能做到「先应用备份里和本机已有的 `text.erased`」（`inbox` 在前、文字部分加在后面，顺序是对的），但拿不到「更新的」删除事件，提示要在 v2 时加。
4. **门槛**：v1 合入、演练通过以后，规格说「设备上的记录开始算数」。如果竖切片 2 先于 `backup-manifest/2` 上线，设备上就会有备份里没有的文字。

**建议**：在「不做什么」和 3.4 里加三句：
- 「私人文字、附件进备份的方式（明文进清单，还是按 ADR-010 每段单独加密、数据密钥另存）在竖切片 2 之前写 ADR；不先定这件事，不加 `backup-manifest/2`。」
- 「`backup-manifest/2` 里文字类部分一律放在 `inbox` 之后；恢复时先摄入全部事件，再处理文字，已有 `text.erased` 的文字直接丢弃（事件规格 4.2 第 2 条）；拿不到更新的删除事件时显示『可能恢复出已删除的文字』。」
- 「竖切片 2 和 `backup-manifest/2` 同时上线，不能先上竖切片 2。」并加进文末「要 Luka 拍板的」。

### R13 · 应改 · 1 — 「内容发布包按哈希能从网站重新拿到」不成立

**问题**：`.github/workflows/pages.yml` 每次只把当前的 `content/` 构建成 `_site/release/release.json` 发布，网站上**只有最新的一份**，旧的 `rel_…` 拿不到。能拿到的「确切来源」其实是仓库历史（`build_release.py` 是确定的，某个提交的 `content/` 能重建出同一个哈希），但没有「哈希 → 提交」的索引，十年后要从几千个提交里一个个试。ADR-006 表格要求「被事件引用过的内容发布清单（或能拿到它们的确切来源）」。

### R14 · 应改 · 6.2 第 4 步 — 旧收据「和每一条比」是平方复杂度，十年后在 iPad 上跑不动

**问题**：「和 `existing.archive`、已经放进 `appendArchive` 的**每一条**按语义相同比」。十年的记录按每天几十条事件算，收据可能有 5～10 万条；恢复链（A → B → C）每次都把收据带进 archive，第二次恢复时是 10 万 × 10 万 = 10^10 次深比较。

**建议**：规定一个规范化的比较键（例如按 R2 的写法、键按字母排序、数字写成最短十进制后的字符串，或直接用 `(event_id, recorded_at, source, batch_id ?? "", clock_skew_ms ?? "")` 这个元组，收据的字段是固定的、没有浮点数），用集合去重。和「语义相同」的结果一样，但是线性的。第 3 步「逐字节相同的一份已经在 `existing.inbox` 里」也写明用集合。

### R15 · 应改 · 4 — 清单行的字段检查不完整

**问题**：第 4 节的检查清单只写了 `schema` 认识，没写：
- 清单不许有多余字段（文件头写了，清单没写）；
- `created_at` 必须和文件头的相同（第 4 节说「一样」，但没说不一样算坏）；
- `learner_id`、`device_id` 的格式。这条有后果：`learner_id` 是乱写的字符串时，6.1 第一种情况会把本机身份换成它，之后每一条本机事件的信封都不合格（`learner_id` 不匹配 `lrn_<ULID>`），`committer` 每次都抛错，设备卡死；

- `app_commit`「读的时候不检查」和「不符合第 4 节就是坏了」矛盾，要说清楚是「格式要查、值不用」还是完全不查。

**建议**：把清单、记录行、`end` 行的字段写成和文件头一样的表（必填、类型、格式、不许多余字段），并把这些情况加进黄金向量。

### R16 · 应改 · 9 — 可读导出唯一的「重写」规则不确定

**问题**：「原始文字里有 `\r` 或 `\n` 的，改成把它解析后紧凑写出的一行」。被接收的事件允许 `1.0`、`1e2` 这种写法（事件规格第 2 节），解析后重写：JS 写成 `1`、`100`，Python 写成 `1.0`、`100.0`（实验 E5）；JS 对像整数的键（`"2"`）会提到前面（E6）。所以这一行两边算出来不同，导出的逐字节黄金向量做不出来。

**建议**：合法 JSON 的字符串里不可能有原样的 CR、LF（必须转义），所以 CR、LF 只会出现在记号之间的空白里。规则改成「把原始文字里每个 `\r`、`\n` 换成一个空格」，不解析、不重写，两种语言结果一样，也保留了原始字节的其余部分。加一个黄金向量（带换行和 `1.0` 的原始文字）。

### R17 · 应改 · 测试接缝 — 黄金向量和测试的缺口

已列的场景基本够，但缺下面这些（多数来自上面的发现），而且有一条现在写不出来（R1）：

- 文件格式：`chunk_size` 不是 1 MiB 的合法文件（R1）；文件头重复键、多余空格、非规范 Base64（R6）；第一行和 `format` 不一致（R6）；文件头超过 4096 字节；末块不足 17 字节；尾部多出整整一块；gzip 两个 member、gzip 末尾补零（R4）；明文以 BOM 开头、明文里有坏的 UTF-8（R5）；清单 `created_at` 和文件头不同、`learner_id` 格式不对（R15）。
- 「错的密钥 → 不去解密文」：要能观察到，就造一个**密钥错、同时密文也坏了**的文件，期望结果必须是「恢复密钥不对」而不是「文件坏了」。
- 恢复密钥：全角输入、`ABCU` 这种同时有坏字符又位数不对的输入（R7）。
- 恢复计划：备份里有本机 `device_id`、序号超过 `nextSeq`（R8）；本机已有密钥（没确认 / 已确认）时恢复（R3）；`restoring` 标记还在时恢复别的孩子的备份（R9）；用自己做的备份恢复自己（R18）；收件表为空但 `receipts_archive`/`imports` 不空（6.1 的「干净」该怎么判，R19）。
- **数据库升级**：用版本 1 的数据库（带收件表、收据、身份、`nextSeq`）升到 2，原数据一字不变（ADR-006 第 4 条「每个历史格式版本都有样例、都验证能迁移」，原则 7）。规格的测试接缝里完全没有这一条。没有依赖可用的话，整合时在真实浏览器里跑一次也要写进去。
- 记录指纹：0 条事件时是什么（`e3b0 c442`，SHA-256 空串），界面怎么显示。

**期望值能否独立算出**：能。我用 Python 独立算出的 `compression: none` 文件和 Node Web Crypto 的逐字节一致（E2）；`planRestore` 可以基于仓库已有的 `RefLog` 写对照实现（E7 就是这样做的）。前提是 R1、R2、R16 先改。`gzip` 的样例只能「Python 写、浏览器读」和「浏览器写、Python 读」，不能逐字节比，要在测试表里写明。

### R18 · 建议 · 6.2 第 4、5 步 — 导入历史在恢复链里丢掉；用自己的备份恢复自己会多存一份收据

1. 备份里的 `import` 部分「不进本机」，只计数。A → B 恢复以后，B 再做的备份里就没有 A 的导入记录了，A → B → C 时这段审计历史丢了。收据却通过 `receipts_archive` 一路带着走，两者不对称。建议也给导入记录一个 `imports_archive`（或在 `imports` 里加 `origin: "backup"`），和收据同样处理。
2. 第 4 步只和 `existing.archive` 比，不和本机 `receipts` 比。用这台设备自己做的备份恢复自己时，备份的 `receipt` 部分全是本机的收据，第一次会全部复制进 archive。建议也和本机 `receipts` 比。

### R19 · 建议 · 6.1 — 「干净的设备」只看收件表

收件表为空但 `receipts_archive`、`imports` 不空（以前恢复过一个空备份），或者 `restoring` 标记还在（R9），按现在的规则也算「干净」，可以换成别的孩子，旧孩子的 archive 留在新孩子名下。建议「干净」= 收件表、收据、旧收据、导入记录都为空，且没有 `restoring`。另外，换身份对干净设备是安全的（没有任何事件带着旧的 `learner_id`，`device_id` 和 `nextSeq` 不变，我检查了 `session.js`：`openSession` 读到已有身份就不再 `init`，补写放弃只看本机 `device_id`，不受影响），这一点可以在规格里写一句理由。

### R20 · 建议 · 2 — 「本机明文存密钥不增加风险」说得不准，换密钥要在 CURIO-008 之前定

能摸到这台设备的人确实能看到这台设备上的记录；但恢复密钥按 ADR-010 是**全家的主密钥**，以后还要打开云上副本、所有旧备份、别的设备写的私人文字，而且 v1 不能换密钥。所以一台丢了的 iPad 泄露的是「从今以后所有加密副本」，不只是「这台设备上的记录」。这在 v1（只有本机备份）阶段可以接受，但要写准，并写明：「换恢复密钥的 ADR 和本机口令包装必须在 CURIO-008 用这把密钥加密云上副本之前完成」。

格式本身不挡路：HKDF 的 `info` 已经带着 `curio-backup/1`，CURIO-008 用同一把主密钥派生别的用途时只要换 `info`，不会冲突；本机加一层口令包装不影响文件格式。可以考虑在文件头加一个不加盐的**密钥编号**（例如 HKDF(主密钥, 空 salt, "curio key id") 的前 4 字节），以后有两把密钥时界面能说「这个备份用的是尾号 xxxx 的那把」；代价是拿到多个文件的人能看出它们出自同一家。要加只能现在加（文件头不许多余字段）。

### R21 · 建议 · 1、6.2 — 用旧版 Curio 恢复新版做的备份

新动词（竖切片 2～4）加进来时清单版本不变（只有新的部分才升版本）。旧版 Curio 恢复新版的备份，新动词的事件会被判「不合格」进隔离区，`report` 显示「新进隔离区 N 条」，家长会以为出错了；更新以后重放收件表，它们会自动变成接收（收件表保留原文，这是好的）。建议 `report` 区分「这一版还不认识的 N 条（更新 Curio 后会自动算上）」和真正的冲突。

### R22 · 建议 · 6.2、slice-1 6.3 — 恢复后 `mode` 的含义

外壳判断 `first`/`retry` 只看「这台设备上」有没有完成过（`app.js` 第 400 行按 `device_id` 过滤）。恢复到新设备以后，舰长在原设备上做过的挑战再做一次，记下的是 `mode: first`。这是存下来的事实，以后分析「第一次就答对」会被它误导。建议恢复后改成看「这个孩子」所有已接收的事件（改 slice-1 的定义），在本规格里点一句。

### R23 · 建议 · 3.3、6.2 — 「边读边解边写」和全量校验矛盾；附件可能要新的文件格式

规格要求先检查完整个明文（`counts`、`end.sha256`、每一行），`planRestore` 也是拿整份备份的纯函数，所以实际上必须先在内存里解完全部明文，「边读边解边写」做不到。几十 MB 的事件没问题；以后加附件（照片）就会到几百 MB，而且 JSON Lines 里放 Base64 会大三分之一。建议：3.3 的理由改成「分块是为了不受单次加密的大小限制，并能边读边解压」，并明说附件很可能要 `curio-backup/2`（每个附件单独一段密文、可以跳着读），不要让人以为只升清单版本就够。另外给解压后的大小设一个上限（例如不超过 `navigator.storage.estimate()` 的剩余空间），防止坏文件把页面撑爆。

### R24 · 建议 · 5、导入批次 — 恢复的批次不能被 `import.voided` 作废，要说清楚

恢复产生的 `imp_…` 只在收据和导入记录里，事件信封里没有 `import_batch`，所以 `import.voided {batch_id}`（事件规格 3.5、6.1）对它不起作用。以后家长端列出导入批次、给一个「作废」按钮时会是空操作。建议在第 5 节写一句「`source: backup` 的批次不能用 `import.voided` 作废；恢复错了孩子的情况由 6.1 拒绝，不靠作废」。

### R25 · 建议 · 10、#8 验收第 5 条 — 「不会悄悄重置」

`app.js` 已经调用 `navigator.storage.persist()`，好。但浏览器自己清掉存储以后，数据库能正常打开、只是空的，外壳会建新身份、显示空星图，这正是 #8 说的「悄悄重置」，而 `lastBackup` 也跟着没了，所以没法从本机判断。建议家长页显示 `navigator.storage.persisted()` 的结果（「这台设备可能会自动清理记录」），并在空设备的首页提示「以前在这台设备上用过？从备份恢复」。
