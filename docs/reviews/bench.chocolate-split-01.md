# 多模型对比 · 掰巧克力（act.simulation.chocolate-split-01）

同一份任务文件（`prompts/act.simulation.chocolate-split-01.md` v1，由 `tools/make_task.py` 生成）交给几个模型分别做，Claude 按下面的评分表给每份交付打分。评分表在派发前定稿、随提示词一起合入；打分时不改权重，发现评分表本身有问题，写在结果后面，下一次对比再改。

issue：#55（父任务 #54）

## 规则

- **每个模型开一个新对话**，原样上传任务文件，不补充别的话。交付包整份带回，在对话里发「交付 #55 · <模型名>」。
- **只评第一轮。**第一轮交付就是成绩，不打回重做。分数最高、而且没有阻断问题的那一份，再按正常流程打回修改、审查、整合进 `kp/math.operation.distributive-law`，等孩子试玩。
- **同一套走查**：每份交付放进同一个沙箱宿主（`preview/build.py` 那样的 `sandbox="allow-scripts"` iframe，按 activity/1.1 回 `init`），用同一个走查脚本在三种环境里从头玩到尾：平板 820×1180 浅色、手机 390×844 深色、电脑 1280×900 浅色加 `prefers-reduced-motion`。脚本只用任务文件第 8 节写定的测试接缝（元素 id、键盘操作、`state` 和 `event` 消息），对每个模型都一样。脚本走不通的地方，Claude 再手动点，扣分记在「交互手感」或「测试接缝」里，不重复扣。
- **审美盲评**：先把每份交付的截图拼成缩略图总览，去掉模型名，按 A、B、C… 随机编号，审美一项按编号打分，打完再揭晓是谁。
- **利益冲突**：评分者是 Claude。如果参赛的有 Claude 系列模型，审美一项另请一个不参赛的模型对同一组匿名截图打分，两份分数都写出来，取平均计入总分。

### 对比总结

1. **前两名差距很小。**审美复评后，Opus 95.5、GPT 94，名次不变。Opus 赢在画风和教学细节（错账当场纠正、试过的缝打勾），GPT 赢在契约和手机布局。
2. **最常见的契约错误是「先发 state 再发 ready」**：Opus、Kimi 都把 `enter1()` 写在了 `Host.ready()` 前面。骨架里 `Host.ready()` 本来就写在最后，下次要在 lessons 里写明「`ready` 必须先于任何 `state`」。
3. **触摸是区分度最大的一项。**GPT、Opus、Kimi 都按教训 20 只在抓住控件时拦截滚动；GLM 漏了一次重画，DeepSeek 完全没有拦截。只靠键盘走查发现不了这类问题，所以手动点必须做。
4. **改骨架就容易出事。**Kimi 只改坏了骨架里的一个下标，审美分就从中游掉到最后。
5. **格式稳定性**：只有 Opus 一次就交出了合格的交付包。GPT、Kimi 的正文是复制后补回标记才通过的；GLM、DeepSeek 都栽在格式上。v2 已经把交付格式简化成 2 个固定命名的 MD 文件。
