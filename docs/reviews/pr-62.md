# 审阅意见 · ADR-010 和中转服务规格 · 审阅者：GLM-5.3（智谱）

> 审阅对象：提交 `dbf5a02` 内嵌的 ADR-010、`docs/specs/relay.md` 全文，及其引用的 ADR-004、ADR-006、ADR-008、事件规格第 1/4/5 节、`architecture.md`、`AGENTS.md`、`GLOSSARY.md`。审阅日期：2026-11-09。视角：云架构与安全工程师，兼顾儿童产品隐私。

## 结论

**改完再合入。** 方向和骨架站得住：无服务器函数 + 对象存储、每家一份、密钥只在服务端、花费三道闸，这些取舍的理由都成立；花费的整数算法和十条验收用例**全部复算一致**。但规格有三处「照字面实现就跑不通」的缺口（COS 桶配置与函数授权/超时、CORS 预检响应头、模型档位未钉死），ADR 有两处必须现在定方向、后补代价很高的点（加密数据的删除控制通道、密钥层级与轮换），还有一句关于恢复密钥的表述会误导家长——按任务里「阻断」的定义已经接近「照此执行会丢孩子数据」。上述都是文字层面的修改，不动骨架，改完即可派发实现。

| # | 情况 | 复算 | 结论 |
| --- | --- | --- | --- |
| 1 | 单价 `200,20,800`；未命中 1000、命中 500、输出 300 | 1000×200 + 500×20 + 300×800 = 200,000 + 10,000 + 240,000 = **450,000 微分**；⌈450,000 ÷ 1,000,000⌉ = **1 分** | 一致 |
| 2 | 上限 2000 分，累计 1,999,999,999 | 上限换算 2000 × 1,000,000 = 2,000,000,000 微分。规则 5 是事前判断：1,999,999,999 < 上限 → 放行；任一次成功调用花费 ≥ 1 微分（token 计数与单价均为正整数），故调用后累计必然越过上限，下一次 429 `monthly_cap` | 一致（隐含前提「单次花费 ≥ 1 微分」在实践中恒成立；只有把某档单价配成 0 且该次对应 token 全为 0 才失效，属理论边界） |
| 3 | 每天 30 次已满 | 429 `daily_cap`；UTC+8 次日 00:00 = 前一日 UTC 16:00（中国无夏令时，全年成立），新本地日期在 `calls_by_day` 里是新键，自然恢复 | 一致 |
| 4 | UTC 2026-11-30T15:59:59.999Z 与 2026-11-30T16:00:00.000Z | +8h 后分别是本地 2026-11-30 23:59:59.999 和 2026-12-01 00:00:00.000 → 分别记入 `usage/2026-11.json`、`usage/2026-12.json` | 一致（实现注意见注 1） |
| 5 | 口令连错 10 次，第 10 次在 t | 第 10 次本身回 401（当时仅 9 条失败记录，规则 2 在规则 3 之前）；从第 11 次起 429 `locked`，直到「最早一条失败 + 3600 秒」；口令对也一样（锁定判断先于口令判断）；锁定期间的请求不新增失败记录（规则 2 直接返回），窗口严格自愈 | 一致，但复算发现滑窗行为，见注 2 和问题 4 |
| 6 | 连错 9 次后第 10 次口令对 | 9 < 10 未锁；口令对 → 清空失败记录 → 200 | 一致 |
| 7 | DeepSeek 回 500、无用量 | 规则 6：502，次数不加；无用量则花费不记 | 一致 |
| 8 | `question` 是 201 个汉字 | 201 个 Unicode 码点 > 200 → 规则 1 → 400，不计失败、不计次数 | 一致 |
| 9 | `Origin` 不在允许名单 | 照常处理，但响应里没有 `Access-Control-Allow-Origin` | 一致（CORS 只管浏览器能不能读响应，不管服务端执不执行请求——规格的处理是对的，但建议文中点明这一句，避免读者把 CORS 当访问控制） |
| 10 | 任何请求之后 | 存储里只有 `usage/<月>.json`（次数与 `cost_ufen`）和 `auth/failures.json`（毫秒时间戳数组），字段不含问答内容；配合「日志不打印问答」 | 一致 |

**注 1（UTC+8 的实现方式）**：从毫秒时间戳算 UTC+8 日期，必须写成「取 UTC 字段 + 8 小时再进位」的纯函数，不要用运行环境的本地时区方法——云函数运行时恰好是 UTC 时才碰巧正确，换平台就错。这正是「日期和月份按 UTC+8 切换」这条测试要覆盖的点，建议在测试清单里把这个陷阱写明。

**注 2（锁定窗口的滑窗）**：失败记录「只保留最近 10 个」。解锁后（最早一条满 3600 秒），攻击者只要再发一次错误口令，失败列表就滑成新的 10 条、立即重新锁定。**每小时 1 个错误请求即可把一家长期锁在门外**，详见问题 4。

## 问题

### 1. 配置表没有 COS 桶参数，部署清单缺「授权」和「超时」两步
- 严重程度：重要
- 位置：`docs/specs/relay.md` §2（配置）、§7（部署手册）、§1（`adapters/tencent.js`）
- 问题：环境变量表里没有任何 COS 桶的名称与地域，`deps.storage` 无从知道读写哪个桶——按现在的表，函数部署起来也跑不通。部署手册的步骤清单还缺两步：①给函数绑定可读写该桶的**运行角色**（CAM），否则对 COS 的每次读写都是 403；②函数自身的执行超时必须大于上游 15 秒加余量（云函数默认超时通常只有几秒，不改会全部 502）。适配层不引依赖、直连 COS 的 XML API 是可行的（用运行角色注入的临时密钥 + Node 内建 crypto 签名），但这恰恰依赖「角色已绑定」这一步。
- 建议：配置表加 `CURIO_BUCKET` 与 `CURIO_REGION`；手册补「绑定运行角色」「设置超时（建议 20 秒）」两步，每步写明点哪里、应该看到什么；「常见问题」加一条「用量一直是 0 / 报存储错误 → 检查角色授权」。

### 2. CORS 只写了 ACAO，预检必然失败
- 严重程度：重要
- 位置：`docs/specs/relay.md` §3（接口）
- 问题：页面（`github.io`）跨域调用函数 URL，POST 带 `Authorization` 和 `Content-Type: application/json` 必然触发预检；预检通过需要 `Access-Control-Allow-Methods` 和 `Access-Control-Allow-Headers: authorization, content-type`。规格只写了回显 `Access-Control-Allow-Origin` 和 OPTIONS 回 204。实现者照字面写，页面第一次调用就会死在预检上，而且这属于「部署后才发现」的问题，会白白消耗 Luka 的排查时间。
- 建议：把预检响应头写全（允许的方法和头），并加一条验收用例：从允许名单里的 `Origin` 发预检必须通过、从名单外的 `Origin` 发预检必须拿不到 ACAO。顺手加 `Vary: Origin`，防中间层把不同 Origin 的响应串缓存。

### 3. 模型档位没有钉住，思考型模型 + 15 秒超时 + max_tokens 400 会大面积失败
- 严重程度：重要
- 位置：`docs/specs/relay.md` §2（`DEEPSEEK_MODEL`）、§4 规则 6（15 秒、`max_tokens` 400）
- 问题：DeepSeek 的对话接口分「思考 / 非思考」两档。若手册里当时写的是思考型型号：400 token 的上限大概率被推理过程吃光，孩子拿到空回答；思考 token 同样计费，单次花费结构完全不同；15 秒超时也更容易触发 502。规格把模型名完全交给手册「写当时的名字」，没有约束档位——十年里 DeepSeek 改一次产品线，手册抄错一次，就整段坏掉。
- 建议：规格写死约束「使用非思考档（如 deepseek-chat 一类），请求里显式关闭思考输出」；验收标准加「试问一个问题应在数秒内收到完整回答，若为空或被截断，先检查型号档位」。

### 4. 锁定可被用来把一家长期锁在门外，且没有写恢复手段
- 严重程度：重要
- 位置：ADR-010 第 4 条；`docs/specs/relay.md` §4 规则 2
- 问题：函数 URL 是公开的，会出现在孩子设备的设置里、浏览器历史里。攻击者前 10 次错误口令各记一条失败；锁定期间不新增记录，但每次窗口一过（最早一条满 3600 秒），再补一次错误口令就重新集满 10 条——**每小时 1 个请求即可让这家长期 429 `locked`，口令对也没用**。对孩子来说就是「AI 永远坏了」，家长翻遍手册也找不到原因。另外要提醒：家长自己在指挥中心里反复试错口令，同样会把自己锁一小时，手册应写明。
- 建议：①手册「常见问题」第一条写应急解锁：在 COS 控制台找到并删除 `auth/failures.json` 即恢复（这是家长点得动的操作）；②ADR 里明确「接受锁定被滥用为可用性攻击，不泄密不产生费用」这一取舍；③可选：把失败记录的判断改成「只统计距现在 30 分钟内的失败」，攻击者维持锁的成本不变，但家长手滑后的自愈时间从 1 小时缩到 30 分钟。

### 5. 公开网页放在 github.io，和 ADR 自己放弃 Cloudflare 的理由打架
- 严重程度：重要
- 位置：ADR-010 第 3 条；`docs/specs/relay.md` §2（默认 CORS）
- 问题：ADR 因为「workers.dev 在中国大陆被阻断」而推迟 Cloudflare，但孩子和别家家长每天要打开的页面在 `deepnorth2077.github.io`——github.io 在大陆同样长期时好时坏（`architecture.md` 附录自己就记过「jsdelivr / GitHub 外链国内不稳定」）。中转服务再稳，页面打不开就全盘不可用。PWA 离线缓存能救已缓存的设备，救不了首次访问和更新；对「别的家庭照着用」影响最大，他们连仓库都未必访问得顺畅。
- 建议：①在 ADR 和手册里承认这个风险，把「页面打不开怎么办」写进常见问题；②每个家庭的部署既然已经有 COS，手册可以提供可选路径「把页面也放到自己的静态托管上」（CORS 名单已支持加自己的地址）；③保持 Service Worker 缓存「有缓存就先用」的策略，并把「检查更新」做成手动动作。

### 6. 「恢复密钥丢了，家里那份备份包也还在」是一句会害人的话
- 严重程度：重要（按任务里「阻断」的定义已接近：可能间接丢失孩子的数据）
- 位置：ADR-010「后果」第 3 条；第 7 条第 3、4 点
- 问题：月度备份包是加密的（ADR-006、ADR-010 第 7 条），解密用的就是这把家庭恢复密钥。密钥丢了，云上副本和家里的备份包**都**读不出来，能救命的只剩各设备上的本地数据。现在的表述会让家长以为「备份还在就还行」。而且整条链路——云副本、每月备份包、以后所有端到端加密数据——共用一把钥匙，是单点故障；方案只要求「打印一份放家里」，十年里一张纸丢了、字迹褪了，都是全灭。
- 建议：①把这句改成实话：「密钥丢失时，云上副本和所有加密备份包全部失效，只剩设备上的数据」；②恢复手册要求至少两份纸质副本放两处（家里 + 祖辈家 / 保险柜），部署清单里作为必选项；③在 CURIO-008 里认真评估「密钥由一段可记住的话经 KDF 派生」作为兜底（十年后凭记忆还能救回来），权衡被 guessing 的风险后写明取舍。

### 7. 端到端加密下，「删除私人文字」如何让服务端删对象，字面上是矛盾的
- 严重程度：重要（属于必须现在定方向、不能全留给 CURIO-008 的点）
- 位置：ADR-010 第 7 条第 2、3 点；`docs/specs/events.md` §4.2；ADR-004 第 8 条
- 问题：第 7.2 承诺「删除一段文字时，把云上这个对象连同全部历史版本一起删」；第 7.3 说服务端不解析内容。但 `text.erased` 是加密事件，服务端看不见——它凭什么知道要删哪个对象？必然需要一条**设备发起、服务端可读的明文删除命令**（「删除对象 txt_…」）。这条通道的鉴权、能删什么、误删和滥用怎么防，直接决定中转服务的接口形态和安全模型。留给 CURIO-008 细化可以，但「存在这条明文控制通道」必须现在写进 ADR，否则 7.2 和 7.3 在字面上矛盾，后面的规格会各写各的。同时，ADR-004 第 8 条的「销毁附件密钥使所有备份里的附件不可读」和 7.2 的「删除对象 + 历史版本」是两种擦除机制（前者管旧备份包里的密文，后者管云上），两者的分工也需要一句话说清。
- 建议：在 ADR-010 第 7 条加一条：「删除类指令走独立的明文控制接口，按对象名寻址，鉴权同家庭口令，只允许删除、不允许改写；与『销毁对象密钥』的分工是：删对象管云上，销毁密钥管旧备份包」。细则留 CURIO-008。

### 8. 密钥层级和轮换没有方向，而「设备丢失」十年里几乎必然发生
- 严重程度：重要（属于必须现在定方向、后补代价很高的点）
- 位置：ADR-010 第 7 条第 3 点
- 问题：现在只有「一把家庭恢复密钥」。ADR-004 第 8 条又说附件「按对象单独加密」——那每个对象的密钥从哪来、存在哪、被谁包着？平板丢了要不要换钥匙？不支持轮换的话，捡到设备的人是否有了一把永久有效的钥匙（设备上的钥匙和「打印在纸上」的恢复密钥是同一个东西吗）？这些都标着「细节留给 CURIO-008」，但「要不要支持轮换、用什么层级」是方向问题：先按单密钥实现、上线后再补轮换，要重加密全部云端数据，属于「以后很难纠正」。
- 建议：现在就定方向：主密钥（进恢复手册）包裹每对象的数据密钥；轮换 = 换主密钥并重新包裹对象密钥，不用重加密全部密文；设备上保存的主密钥副本再被设备本地口令包一层，丢设备就作废这台设备的访问。细节留 CURIO-008。

### 9. 孩子可能在问题里塞个人信息，领航员说明和手册都没接住
- 严重程度：重要（儿童产品，修复成本极低、收益高）
- 位置：`docs/specs/relay.md` §5（领航员说明）、§7（部署手册）
- 问题：现在的保护是「不带名字、不问个人信息、中转不存原文」，但三年级的孩子完全可能自己写「我叫某某，我在某某小学三年级」。提示词里的「不问」拦不住「主动说」；回答一旦复述这些内容，就进了设备上的私人文字和 DeepSeek 一侧的日志。另外，孩子的原始问题整个发给 DeepSeek，DeepSeek 按什么条款留存这些数据，家长应当知情。
- 建议：①领航员说明加一条：舰长的问题里出现姓名、住址、学校、电话等内容时，回答里不复述、不展开，并温和提醒「这些事不用告诉电脑哦」；②手册加一行透明说明「孩子的问题会发送给 DeepSeek，按对方当时的条款处理」；③部署前核对一次 DeepSeek 当时的数据处理条款，把结论写进手册的对应版本。

### 10. 口令哈希是家长最容易卡死的一步，现在的设计容错为零
- 严重程度：建议
- 位置：`docs/specs/relay.md` §2（配置）、§7（部署手册）
- 问题：流程是「下载本地小网页 → 输盐和口令 → 复制 64 位十六进制 → 粘进平台环境变量」。多一位、少一位、大小写错、带空格，结果都是「永远 401」，家长不知道错在哪。盐要求家长自己想「随机字符串」，大概率写出「123」。
- 建议：①本地页一键生成随机盐，并直接输出 `CURIO_SALT=…`、`CURIO_PASSPHRASE_HASH=…` 两整行供整体复制；②服务启动时校验哈希格式（64 位小写十六进制）与盐非空，不对就在日志里打一句人话（「口令哈希格式不对，请回到手册第 X 步」）；③手册「常见问题」加「永远提示口令不对」条目；④手册建议口令用四个随机词，别用生日。

### 11. 三道闸只管 DeepSeek 的钱，平台侧的调用费没有闸
- 严重程度：建议
- 位置：ADR-010 第 5 条；`docs/specs/relay.md` §3（`GET /v1/ping` 不要口令）
- 问题：`/v1/ping` 无口令、无锁定、函数 URL 公开。真被刷，刷的是云函数调用费和 COS 请求费（不是 DeepSeek）。量级小、平台并发上限也兜着，但「不会有意外账单」的用户故事没有完全闭环——三道闸管的都是 DeepSeek 那一个钱包。
- 建议：手册里设置函数并发上限（例如 10）和账户预算告警；「常见问题」写「怀疑被刷怎么办」。`ping` 保持无口令是对的（连通测试要能区分『连不上』和『口令不对』，且不受锁定影响），把这个取舍在规格里点明一句即可。

### 12. 若干协议细节
- 严重程度：建议
- 位置：`docs/specs/relay.md` §3、§4、§7
- 问题与建议：
  1. `GET /v1/usage` 带 `Authorization`，响应应加 `Cache-Control: no-store`；
  2. 429 响应加 `Retry-After`，页面可以给孩子显示倒计时；
  3. 请求体设一个很小的上限（如 4 KiB）再解析，防超大包烧 CPU；
  4. 未定义路径 / 不允许方法的 404/405 行为写一句，回什么状态码、什么错误体；
  5. 上游「余额不足」类错误建议与普通 502 区分（映射成独立错误码，页面提示「请家长给 DeepSeek 充值」）——预充值耗尽是十年里最可能发生的日常故障，现在一律 502 会让家长排查无门；手册「常见问题」也要有「AI 突然全部报错 → 先看 DeepSeek 余额」；
  6. `CURIO_PRICE_FEN_PER_M` 的「怎么改单价」写进手册的「怎么改上限」一节，并注明单价与 DeepSeek 实际计价有偏差时以预充值为硬上限。

## 其他

1. **方案取舍总评（任务问题 1）**：站得住。放弃「共用中转、各自带密钥」的三条理由（替人保管密钥、上限可被绕过、运营者变成处理别家儿童数据的公共服务方）尤其到位，这是本 ADR 里最有价值的一段。十年里最可能出问题的排序，我的判断是：①部署手册随云厂商控制台改版失效（测试接缝表里已承认发现不了；建议每次平台侧大版本发布后用子 agent 只读手册走查一遍）；②github.io 可达性（问题 5）；③DeepSeek 余额静默耗尽（问题 12 第 5 点）；④价格与产品线变化。设计中「薄适配层 + 连通测试 + 换平台不迁数据」正是对这些风险的正确对策。首批选腾讯云云函数合适：免域名、免备案、实名无障碍。第二个适配层大概率是阿里云函数计算（同样 HTTP 触发器直连、免域名），届时可一并调研腾讯云开发 / CloudBase（函数 + 存储 + 静态托管一体，控制台操作对家长更简单，但平台绑定更深）。没有发现明显更优的国内替代方案；「用平台自带数据库 / KV」的拒绝理由（换平台要迁数据）成立。
2. **每家一份（任务问题 2）**：检查过规格与手册要点，除默认 CORS 指向共享页（有意为之）外，没有发现写死 Luka 家信息的地方。但共享网页的信任关系应在手册开头写一句：**页面由项目维护者托管，它能读到家长填的口令和孩子的问答**（口令必须交给页面才能带上请求头）；维护者账号被盗或页面被恶意更新，会影响所有用这个页面的家庭。这和「不共用中转」的谨慎程度要匹配——建议手册把「自托管页面」作为正式选项（而不是一句 CORS 备注），并把页面发布与仓库提交绑定（页面版本可追溯到 commit）。
3. **任务拆分（任务问题 9）**：合适。第一段不依赖 #25、不落任何数据，验证的恰是最有风险的部分（部署链路 + 三道闸 + 花费算法）；「试问一个问题」烧一次真实调用，用真金白银验证端到端，值得。第二段的事件记法（`actor` 加 `sys:relay`）先修事件规格再写规格，顺序也对。

5. **做得好的地方，值得保持**：花费全程用整数（微分）并在比较、显示两个环节分别定义换算，避免了浮点误差这一整类 bug；UTC+8 与事件规格第 1 节完全对齐；`ping` 不需要口令，让连通测试不受锁定影响，是很聪明的诊断分层；「问题字数 + 回答 token 数」的长度上限同时就是单次费用上限（估算过：按示例单价，一次调用最多约 0.5 分），三道闸之外事实上多了一道；测试接缝表诚实地区分了「能发现 / 发现不了」。
