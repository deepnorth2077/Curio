## 结论
改完再合入：「认识了就不会再失去」这条核心承诺，在作废导入和发布包回滚下会落空，需要先补；发布格式的改动也没写全（哈希、外壳核对、schema）。其余是可以在合入前一并改掉的缺口。15 个验收用例的算术我都手算过，没有算错的。

## 问题

### 1. 「`best` 只增不减」不成立，已认识的领航员在三种情况下会消失
- 严重程度：阻断
- 位置：`docs/specs/navigators.md`「实现上的决定 · 2. 认识了谁」；「和已有规格的关系 · ADR-006」；测试接缝表第一行
- 问题：`best` 在事件集合只增、每次尝试都合法的前提下才只增。核对仓库后有三条路会让它变回 `null` 或变低：
  1. **作废导入。** `docs/specs/events.md` 6.1 第 2 条：投影输入要「去掉带有被 `import.voided` 作废的 `import_batch` 的事件」。`kernel/js/mastery.js` 的 `projectMastery(events)` 假定传进来的已经是过滤后的事件。一批导入含有那次 ≥0.8 的尝试，被作废（`duplicate`、`bad_data`、`wrong_learner` 都可能）后，该知识点的 `best` 回到 `null`，对应领航员从「已认识」里消失。
  2. **尝试变成不一致。** `mastery.js` 的 `attemptRule` 对同一 `attempt_id` 的全部事件重新判定。之后到达的同 `attempt_id` 事件（多一条 `started`、`content` 不同、`try` 跳号、多一条结束事件）会让原本合法的尝试变成「不一致」，被排除出 `best`。隔离区本身不会删掉已接收的事件（events.md 5.2 第 3 条「不覆盖已有的事件」），所以隔离只是不会让它变回去，不是这条路的原因。
  3. **发布包回滚。** `knownNavigators` 的第二个参数是「发布包里的领航员定义」。ADR-003 第 5 条允许回滚，回滚到没有 `nav.x` 的旧发布后，`nav.x` 不在定义里，认识的列表里就没有它。
  - 规格自己也承认了一处：用例 11「记录被清过」、「和已有规格的关系」里「`试玩记录被清掉，认识了谁也跟着从头算`」。这和用户故事 6、拍板结果第 1 条「认识了就不会再失去」直接矛盾。测试接缝表说 `knownNavigators` 能发现「认识了又失去」，但一个对单个 `mastery` 快照的纯函数发现不了这件事。
- 建议：
  - 把规则改成「已认识 = 由掌握度算出的 ∪ `navigators_seen` 里、且发布包里仍有定义的非 `start` 领航员」。卡片出现过（孩子点过「让它陪我」或「先不换」）就等于认识过，档案里留着这个记号，作废导入和不一致尝试都动不了它。`knownNavigators` 多一个 `seen` 参数，仍是纯函数，用例要补。
  - 回滚造成的缺位，要么规定外壳显示「已认识」时并上本机见过的最高发布的领航员定义，要么在规格里明说「回滚期间少显示，不改档案」并写进用例。
  - 如果希望跨设备、跨恢复也稳，才需要新事件（如 `navigator.met`），那要改事件规格第 3 节，与「不新增事件动词」冲突，请 Luka 取舍。我的倾向是：这一版用档案里的 `seen` 兜底，并在规格里把不变量说准——「只要档案还在，就不会失去」。
  - 把「`best` 只会变好」改成「在事件集合只增、每次尝试保持合法的前提下」，并引用 events.md 6.1 的作废规则。

### 2. 第一次挑选时没有规定 `navigators_seen` 怎么初始化，卡片会对初始领航员触发
- 严重程度：重要
- 位置：规格「3. 选了谁」「4. 舰长看到的 · 认识新的一位」；验收用例 13～15
- 问题：用例 13～15 都假设 `navigators_seen` 已经是 `[lamp, ring]`，但规格没有说第一次挑选时谁把它们写进去。如果不写，孩子第一次做完挑战回星图，「已认识」里的 `nav.lamp`、`nav.ring` 不在 `navigators_seen` 里，会弹出「你点亮了『…』」的卡片，而 `start: true` 的领航员没有 `from`，文案无从生成。同样的问题出现在：在已有进度的设备上升级后第一次打开（此时第三位可能已经满足条件）、恢复数据到新设备。
- 建议：规定「第一次挑完，把当时全部已认识的 id 都写进 `navigators_seen`，但第三位这种已满足条件的除外，让它出卡片」，或者更简单：卡片只对有 `unlock.lit` 的领航员出，`start: true` 的永远不出卡片。补两个用例：首次挑选后 `seen` 的值；老档案升级。

### 3. 发布格式的改动没有写全，按字面实现会让 `navigators` 不受哈希保护，并且外壳核对不了
- 严重程度：重要
- 位置：规格「1. 领航员是内容」末段；「和已有规格的关系 · 内容规格、发布格式」；`schemas/release.schema.json`；`docs/specs/content.md` 6.1、6.2、3.8；`tools/build_release.py`；`app/app.js` 的 `verifyManifest`
- 问题：规格只说「发布清单多一个键 `navigators`，写法和 `activities` 相同，`engine_min` 至少是 2」。对照仓库，实际需要改的远不止这些：
  - `build_release.py` 里的 `hash_input` 只有 `engine_min, contracts, nodes, activities, assets` 五个键，`app/app.js` 第 72 行的 `canonicalJson({ engine_min, contracts, nodes, activities, assets })` 同样写死。只往清单里加 `navigators` 而不改这两处，`release_id` 就绑不住领航员文件，违背 ADR-003 第 2、3 条（哈希覆盖清单全部内容）。两边都改，又会让旧的外壳在 `engine_min` 检查之后、哈希核对之前就退出，这一点规格说对了（`app.js` 第 69 行的引擎检查在第 72 行的哈希之前），但要写明。
  - `release.schema.json` 是 `additionalProperties: false`，并有 `required` 列表。新键要么设成可选，要么出 `release/2`。如果设成必填，所有已经生成过的 `release/1` 清单都不再合法。如果加进 `hash_input` 的方式是「有领航员才有这个键」，旧发布的哈希不变；如果无条件加，旧发布重算会得到不同的哈希。这三种选择规格都没做。
  - `engine_min` 现在由活动的 `engine` 字段取最大值得出（`build_release.py`），没有「因收录领航员而至少是 2」的代码路径；`content.md` 3.8 说引擎等级「每增加一种 kind、答案 type 或配图 type 加一，并在表里登记」，领航员不是这三种，等级表和 `ENGINE_REQUIREMENTS` 需要新增一行并说明语义（外壳能力）。`app.js` 的 `ENGINE_LEVEL` 常量要升到 2。因为「至少有一位 `start: true`」是发布门禁，之后每个发布都 ≥2，意味着所有还停在等级 1 的设备都不能切换到任何新发布。这是代价，应当写明，而不是只写「旧外壳会显示需要更新」。
  - 「写法和 `activities` 相同」不对：一位领航员有 7 个文件（1 个 yaml 加 6 个 svg），yaml 要带 `json` 边车（`fileEntry` 的规则），`manifest_digests`、`write_release` 也要认识新键，否则「文件不多不少」的核对会报错。
  - 更省事的放法：SVG 可以直接放进现有的 `assets`，不需要新键；只有 `navigator.yaml` 需要被外壳读到。可以考虑 `navigators: [{id, version, files:[…]}]` 里只放 yaml 和 svg 的条目，或者干脆把 `navigator.yaml` 当作一种 `nodes`/`activities` 以外的条目，但无论哪种，都必须进 `hash_input`。「随外壳走」不如放进发布：加一位领航员就要改外壳代码，违背用户故事 8。所以放进发布包是对的，只是要把上面这些补全。
- 建议：规格里列出一张「这些文件要一起改」的清单（`release.schema.json`、`content.md` 1/3.8/6.1/6.2、`build_release.py` 的 `hash_input` 和 `manifest_digests`、`app.js` 的 `verifyManifest` 和 `ENGINE_LEVEL`、`ci_checks.py` 的 `ENGINE_REQUIREMENTS`）；决定 `navigators` 在 `release/1` 里是可选键（推荐，旧发布哈希不变，只有收录领航员时才进哈希），并给出一个有和没有领航员的黄金向量；把「每个发布都 ≥2」的后果写进规格。

### 4. 「已发布的领航员 `id` 和 `unlock` 永远不能改」不够，也拦不住
- 严重程度：重要
- 位置：规格「1. 领航员是内容 · 规则」；测试接缝表第二行；`tools/ci_checks.py` 的「3. ID 检查」
- 问题：
  - **「已发布」没有定义。** `navigator.yaml` 没有 `status` 字段，只有 `review`。反例里说「已合入 `main` 的 `nav.x`」，但合入 `main` 的 `pending` 领航员不在任何发布里，改它无妨；而 `approved` 之后才进发布包。应当定义成「`main` 上 `review: approved` 的那一版」。
  - **`from` 是 `unlock` 的子字段。** 规则把 `unlock` 整体冻结，意味着「生命的说明书」改名也要出一位新领航员。`from` 是纯显示字，应当移出 `unlock` 或明确允许改。
  - **CI 今天做不到。** `ci_checks.py` 的 ID 检查只覆盖 `content/nodes/` 和 `content/activities/` 下的文件（`is_node`、`is_act`），检查删除、改名、`id` 字段变化。它不比较其他字段，也不认识 `content/navigators/`。要新写：对 `base` 上 `approved` 的领航员，逐个检查 `unlock` 的 `lit` 集合没变、文件没被删、没被改名；改名（`git diff -M`）要当作删除处理。规格目前的描述只有「改了已发布的 `unlock`」一条。
  - **知识点以后被拆分或下架会让规则自相矛盾。** `knode.schema.json` 的 `status` 只有 `draft/reviewed/published`，CI 也不拦「已发布的知识点退回草稿」。如果 `lit` 里的某个知识点退回草稿，「`lit` 必须全是 `status: published`」这条门禁会让整个发布构建失败；而 `unlock` 又不许改，没有出路。反过来，知识点被拆分后，旧 id 仍在 `mastery.nodes` 里（事件里的 `content.node_id`），领航员的条件不会丢，这一点倒是安全的。
  - 目录名和 `id` 没有强制一致，`nav.<短名>` 只是写法。
- 建议：（a）把 `from` 挪出 `unlock`；（b）定义「已发布 = base 上 `approved`」；（c）加一条跨检查：被任何 `approved` 领航员的 `lit` 引用的知识点，不许离开 `published`、不许删除（改名本来就不许）；（d）加 CI：目录名等于 `id`、`id` 在 `content/navigators/` 内唯一、`approved` 的领航员不许删或改名、`lit` 集合不许变；（e）`unlock` 如果将来确实要放宽，规定一个唯一的出路：新增一个并列的 `alt` 条件（只放宽，不收紧）——这一版可以不做，但在规格里写明「现在没有，需要时走 ADR 修订」。

### 5. N1 把只有 `arch/` 能改的和只有实现者能改的文件混在一个任务里，没有任何分支能合法地提交 `content/navigators/`
- 严重程度：重要
- 位置：规格「怎么分步」N1 一行的「改到哪里」；`tools/ci_checks.py` 的 `PROTECTED` 和地盘检查
- 问题：N1 要改 `schemas/navigator.schema.json`、`tools/build_release.py`、`tools/ci_checks.py` 和测试（都在 `PROTECTED` 里，只有 `arch/` 分支能改），又要改 `app/`（实现者的地盘）和 `content/navigators/`。地盘检查里：`kp/` 分支只能改 `content/nodes`、`content/activities`、`content/assets/<节点 id>/`，`feat/`、`fix/`、`chore/` 分支不能碰 `content/`，`arch/` 分支不受地盘检查约束。`content/navigators/` 是新的目录，现有规则下实现者无处合法地提交它，设计者（Claude 本人）在 `arch/` 里提交又违反「实现者和审核者分开」的约定。
- 建议：把 N1 拆成两个 PR：`arch/` 里放 schema、`build_release`、`ci_checks` 与测试、领航员的内容检查，以及 `content/navigators/` 里两位初始领航员（它们是设计稿，审查已有 #105）；`feat/` 里放 `app/`。在 `ci_checks.py` 里为 `content/navigators/` 定一个明确的分支前缀（例如 `nav/<id>`），并规定 `kp/` 不能碰它。写进规格，不要留给实现者去猜。

### 6. N1 的演示步骤 3 在 N1 里做不出来
- 严重程度：重要
- 位置：规格「演示步骤 · N1 · 3」；「怎么分步」N1、N2 两行
- 问题：步骤 3 要看到「一个灰色的影子，下面写着要点亮哪三颗星」。但第三位领航员（`lit` 的那一位）的内容在 N2 才进（N2 一行写着「`content/navigators/` 第三位」），N1 的发布包里只有两位 `start: true`，领航员舱里不会有影子。同时 N1 的「改到哪里」里没有 `engine/js/navigators.js`，而「已认识」「选哪位」的逻辑（`knownNavigators`、`shownNavigator`）要在 N1 就用到（至少要过滤 `start`）。
- 建议：要么把影子和要点亮的星这部分挪到 N2 的演示里，N1 只验收挑选、换、刷新后保持；要么 N1 就带上第三位的占位定义（`review: claude-reviewed` 不进发布包，进不了），那就只能挪演示。同时把 `knownNavigators`、`shownNavigator` 都放进 N1，N2 只加卡片。

### 7. SVG 规则有几处在现有 CI 里拦不住，类的样式定义放在哪里没说
- 严重程度：重要
- 位置：规格「1. 领航员是内容 · 规则」第 2～4 条；`tools/ci_checks.py` 的 `check_svg`；`docs/specs/content.md` 3.6；`arch/kit` 分支的 `docs/specs/kit.md`
- 问题：
  - `check_svg` 只对 `content/assets/**/*.svg` 运行（`asset_root = repo / "content/assets"`）。放在 `content/navigators/` 的 SVG 完全不过白名单。要把检查接上，并加领航员专用的更严规则。
  - 3.6 的白名单允许 `fill`、`stroke`、`opacity`、`stop-color`、`transform`、`id`，也允许 `defs`、`use`、渐变、`clipPath`。规格说「颜色不写死，用 `class`」，但没有禁掉 `fill="#f00"`；`fill="none"` 又是线稿常用的，需要放行。`<use>` 可以把一组图形复制多次，绕过「14 个元素」；`id` 和 `url(#id)` 在六张脸内联到同一个页面（领航员舱同时显示多张）时会撞 id。
  - 「能画出东西的元素」不超过 14 个：`g` 上的 `class` 会被子元素继承，`f-accent` 放在 `g` 上等于对所有子元素生效，CI 要按「元素及其祖先」算。
  - 九个类的样式（`.f-ink{fill:var(--ink)}` 之类）在哪里定义，规格只说「由平台的样式决定」。`kit.md` 里 `kit.css` 只有三种线（`k`、`k1`、`kf`）和颜色变量，外壳的基础颜色放在 `curio-tokens` 段。这九个类要同时在外壳和零件库里有，而且要出自同一处（ADR-011 的主张），否则又会抄成两份。另外 `kit.md` 有 `kf` 这种线，领航员只有 `k`、`k1`，应当说明是有意不用。
  - 深色模式靠类名换色在原理上可行：`kit.md` 的 `palette` 键里有 `ink`、`pane`、`sky`、`sage`、`apricot`、`paper`、`accent`，和九个类里的七个填色一一对应，宿主发 `scheme`，模块设 CSS 变量即可。但前提是 SVG 必须内联到 DOM 里（用 `<img src>` 的话页面样式进不去）。规格第 5 节「去掉最外层 `<svg>` 以后的内容」交给模块，宿主还要规定怎么重新包上外层（`viewBox`、`aria-label`、`role`），否则六个模块各包一次。
  - 「影子」靠对 `curious` 的类全部覆盖成灰色实现，需要一条能压过九个类的 CSS 规则，也没说。
- 建议：（a）`check_svg` 对 `content/navigators/` 用单独的严格模式：禁 `id`、`use`、`defs`、渐变、`clipPath`、`style`；`fill`/`stroke` 只许 `none`；`class` 只许那九个；元素计数含 `g` 的继承；（b）规格里写清九个类的 CSS 放在 `curio-tokens` 段里，由 ADR-011 的同步机制带到外壳和零件库；（c）规定宿主统一做「包回 `<svg>`」，给 N3 一个函数；（d）补一个明暗两种方案下的截图验收，放在 Luka 的演示步骤里。

### 8. N3 的 `init.navigator` 没有落到契约版本上

### 9. 选择和「见过」记在设备本地档案里，这一版可以接受，但要明说限制
- 严重程度：建议
- 位置：规格「3. 选了谁」；`app/store.js`；ADR-006
- 问题：`store.js` 的 `meta` 对象仓库现在只有 `identity` 和 `nextSeq`，把 `profile` 加在这里不用升级数据库版本，这一点可行。但：
  - 档案不是事件，不进导出，也不随恢复演练走。从备份恢复后，孩子有一百天的记录，却又回到「第一次打开」的挑选页，已满足条件的领航员会逐个弹卡片。
  - 以后有多设备同步时，两台设备各选各的、各自维护 `navigators_seen`，规则上没有冲突，因为没有同步；但一旦同步，就没有合并规则。
  - 用例 11 说「记录被清过」而档案还在，但外壳清演示数据是整库删除（`meta` 一起没了），这种情况在现有存储下只会由作废导入或恢复旧备份引起。
- 建议：规格里写明「这一版的选择是每台设备各自的，不同步，不进导出」；把「以后同步时，选择改成带时间的偏好事件、取最后一条」记成未来工作，不在这一版做；恢复演练时在 Luka 的步骤里提一句「恢复后会再挑一次」。用例 11 的说明改成真实可达的原因。

### 10. 对孩子：绑定点亮和认识新伙伴的分寸基本对，但还有三处可以收紧
- 严重程度：建议
- 位置：规格「问题」「4. 领航员舱」「不做什么」
- 问题：
  - 「每颗已做到的星打一个勾」是一个小的收集进度条。影子加三颗星的清单，对一个三年级孩子是明确的目标，其实问题不大，但这个目标在掌握度上要求 ≥0.8 的首答正确率，而 `best` 取所有尝试里最好的一次，挑战可以重做。孩子可以靠重做同一份挑战把星刷亮（题只有五道），领航员的诱因会推着他做这件事。这和「做错一道题不用怕」的方向不一致。
  - 影子永久地摆在领航员舱里，对一直没点亮的孩子是一直看着没得到的东西。
  - 十年里领航员越来越多，每位都绑一个星座，节奏没有限制。
- 建议：（a）规格里写：领航员的条件只能挂在孩子本来就会走的路线上（同一个星座的几颗相邻的星），不挂在需要刷的星上；（b）家长端加一个「不显示还没认识的领航员」的开关，默认不关，但有；（c）规定一个节奏上限，比如同一个年级内最多三位新的，写在维护规则里，而不是代码里；（d）「不抽、不限时、不花点数、不催」够用，再补一条「不因为没点亮而提示或提醒」。

### 11. 第三位领航员来自孩子的画和话，要在公开仓库里怎么存，规格没说
- 严重程度：建议
- 位置：规格「6. 每一位都是原创的」第 3 条；「拍板结果」第 3 条；用户故事 9
- 问题：用户故事 9 提到「公开的仓库」。设计说明里写孩子的画和「我喜欢它什么」的原话，等于把一个未成年孩子的作品和个人偏好放进了公开的 git 历史，而且 git 里删不掉。规格要求设计说明里「只写这些」，方向正好相反。
- 建议：设计说明里只写提炼后的性格和本事（勇敢、安静），不放孩子的画原件，也不放原话；原件留在 Luka 手里。写进规格，并让 CI 检查 `content/navigators/` 下不出现位图。

### 12. N3 做完之前的过渡期：刚认识的新领航员，在动手探索里不是它
- 严重程度：建议
- 位置：规格「怎么分步」下一行；「5. 动手探索里也是它」最后一条

### 13. 验收用例：算术都对，但前提和覆盖有缺口

  - 漏了：`best` 是 `{correct:0, answered:0}`（`0×5≥0×4` 为真，`mastery.js` 不会产生，但 `knownNavigators` 应当自己拒绝 `answered === 0`）；`lit` 里的知识点没有出现在 `mastery.nodes`（用例 2 里「C 没有」覆盖了，但没有「A、B、C 都没有」）；发布包里完全没有 `start: true`（`knownNavigators` 返回空，`shownNavigator` 怎么办）；多位领航员共用同一颗星；`navigators` 参数乱序时结果按 id 排序；`navigators_seen` 里有一个发布包里已经没有的 id；首次挑选后 `seen` 的值（见问题 2）；回滚后缺位（见问题 1）。
