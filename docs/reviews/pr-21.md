### 问题

#### 1. 自由文字必须从一开始支持擦除，不能等以后再加

- 严重程度：阻断
- 位置：`docs/specs/events.md` 第 2 节、第 3.1～3.5 节；ADR-004 第 1 节
- 问题：`reflection.written`、`question.asked`、`question.answered` 等把原文直接写进不可变事件。即使以后增加 `text.deleted` 事件，原文仍存在于原事件、同步数据、导出和备份里，无法真正删除。需要覆盖的不只是反思和提问，还包括 `poe.predicted.text`、`poe.explained.text`、孩子填写的自定义任务标题，以及其他可能包含孩子自由文字的字段。
- 建议：现在增加独立的 `PrivateText`（或 `EncryptedText`）对象。事件保存 `text_id`，不保存原文；文字对象单独加密并带所有者。增加 `text.erased` 事件，记录 `text_id`、操作者和原因。擦除后，投影和界面只显示“这段文字已删除”，不显示原文；缺失文字但没有擦除事件应视为数据损坏。删除必须覆盖在线存储、设备缓存、搜索索引、诊断/AI 日志和之后生成的导出。同步擦除标记，其他设备收到后删除本地原文。明确旧备份不能被远程追改：只能承诺当前副本和后续备份删除，旧备份按保留期限到期，或采用能使命中密钥失效且经过恢复验证的加密擦除方案。不要承诺已导出的旧文件也能被删除。

**对应验收用例：**写入反思→同步→擦除→重放全部事件→两台设备和后续导出都不得出现原文；擦除不能删除“孩子曾完成一次反思”这一非文字事实。

#### 2. 多个事件竞争同一个奖励唯一键时，规格没有确定选哪一个

- 严重程度：阻断
- 位置：`docs/specs/events.md` 第 3.4 节、第 6.2～6.3 节
- 问题：反例：同一个 `reward.redeem_requested` 对应两条 `reward.spent`，一条 `amount: 5`，另一条 `amount: 10`。它们产生相同的 `cause_key = redeem:<request_event_id>`，唯一键只允许一笔，但规格没有规定选哪条。如果实现按到达顺序处理，余额会不同；全量重算也可能和增量结果不同。多个 `repair.resolved`、多个 `reward.revoked` 指向同一目标时，`cause_event_id` 也有同类歧义。
- 建议：为每类竞争明确规则，例如“按统一排序键最小的合法触发事件生效，其余标为冲突”，并加入黄金向量。`reward.spent.amount` 必须为正整数，并校验它与申请、当时目标金额的关系。明确余额不足时拒绝、排队还是允许负余额；不能留给实现自行决定。

#### 3. 首答正确率和不一致尝试仍有歧义，可能算错掌握度与奖励

- 严重程度：阻断
- 位置：`docs/specs/events.md` 第 5.3 节、第 5.4 节“掌握度”
- 问题：同一 `attempt_id`、同一 `item_id` 出现两条 `try: 1` 的 `item.answered`，一条正确、一条错误时，目前没有规定哪条是首答。若按事件数计正确、按不同题目数计分母，甚至可能得到大于 1 的比例。尝试合法性也没有明确要求同一 Attempt 的所有事件属于同一个 `learner_id`，并与正确的活动参与者一致。
- 建议：规定 `(attempt_id, item_id, try)` 唯一；冲突时整个 Attempt 判为不一致，或按 `device_seq` 明确选第一条并把其余记为冲突。首答必须按“每题一条确定的 `try=1` 事件”计算。Attempt 校验增加相同学习者、相同设备、合法 actor、合法内容引用和事件归属检查。补充重复首答、乱序首答、跨学习者 Attempt 的黄金向量。

#### 4. 发布包没有要求引用闭包，会生成含悬空引用的 release

- 严重程度：阻断
- 位置：`docs/specs/content.md` 第 5 节、第 6.1 节
- 问题：反例一：知识点 A 为 `published`，其前置知识点 B 仍为 `draft`；当前构建只收 A，不收 B，A 的前置引用在发布包中断开。反例二：一个已批准活动同时 targets A 和 B，A 已发布、B 是草稿；活动因 A 被收录，但 B 不在包内。
- 建议：明确发布引用闭包。最简单的是：已发布知识点的 `prerequisites`、发布所收活动的全部 `targets` 都必须已发布；否则构建失败。`related` 也要明确是必须已发布，还是允许保留为指向仓库中未发布内容的外部引用。增加上述两个反例的构建测试。

#### 5. `source: photo` 的错题无法满足当前 `content` 范围

- 严重程度：阻断
- 位置：`docs/specs/events.md` 第 2 节 `content`、第 3.2 节 `repair.opened/practiced/resolved`
- 问题：拍照录入一道陌生错题时，通常还不知道它属于哪个活动，更没有 `activity_id、activity_kind、activity_version、content_release`。但当前 `repair.opened` 无论来源都被归为“内容”，要求五个字段全部存在。实现者只能编造一次不存在的内容引用，或者无法表达真实拍照流程。
- 建议：把内容引用拆成可选的节点关联与完整活动来源。拍照初录允许无 `content` 或只有 `node_id`；从具体活动产生的错题才携带完整活动来源。`repair.practiced/resolved` 从 ticket 关联继承，不应被迫伪造活动 Attempt 信息。分别提供“活动内产生”和“拍照后待诊断”的合格样例。

#### 6. “规范 JSON 完全相同”会被不同序列化器误判为冲突

- 严重程度：阻断
- 位置：`docs/specs/content.md` 第 6.2 节；`docs/specs/events.md` 第 2 节、第 4.2 节
- 问题：内容发布清单只有字符串和整数时，当前规范基本可复现；但事件的 `sim.adjusted.value` 等字段允许数字，不同序列化器可能把同一个值写成 `1`、`1.0`、`1e0`，Python 与 JavaScript 对很小或很大的浮点数也可能采用不同格式。同一事件会因此被误判为“冲突”并进入隔离区。非有限数、大整数精度也未规定。
- 建议：不要把某一对 `json.dumps` 参数当作跨语言完整规范。可以选择：采用 JSON Canonicalization Scheme（RFC 8785）并测试 Python/JS 黄金向量；或者摄入时比较解析后的、经过严格 schema 约束的语义对象，同时限制数值范围和精度。明确拒绝 NaN、Infinity 和超出双方精度的整数。`1` 与 `1.0` 是否语义相同必须写清楚。

#### 7. 设备时钟错误会改变按天奖励和规则版本选择，目前只有提示，没有处理规则

- 严重程度：重要
- 位置：`docs/specs/events.md` 第 1 节、第 4.3 节、第 6.3 节
- 问题：`activity-done` 的本地日期和 `effective_from` 规则选择都直接使用设备 `occurred_at`。设备日期错误时，同一活动可能被记到另一天并再奖励一次，或者选中已经过期的规则。收据虽然记录偏差，但投影明确不读收据。
- 建议：明确第一版不是防作弊系统，时钟错误最终由家长调整或撤销；同时给出确定处理规则。例如偏差超过阈值的事件只保留学习证据，不参与按天奖励，直到追加一条家长确认事件。规则选择也要明确同一 `effective_from` 有多个版本时的唯一性或排序规则。

#### 8. 内容类型可扩展，但旧外壳是否理解新内容缺少版本门禁

- 严重程度：重要
- 位置：`docs/specs/content.md` 第 3 节、第 6 节；ADR-002
- 问题：当前选择、数字、分数三种答案适合作为第一版，以后可以新增多空、表达式、单位和作图类型。但如果新发布只改变 `answer.type`，旧设备上的共享引擎可能无法识别，离线缓存和旧版本兼容会出问题。另一个文档矛盾是：ADR-002 仍把 `hint-ladder` 列为活动类型，而内容规格只有 `explain、quiz、reflection`，实际提示阶梯已经是 item 的能力。
- 建议：现在只实现三种答案，不为高中题型提前设计复杂 DSL；但在活动或 release 中增加 `engine_requirements`/`min_engine_version`，或在发布门禁中拒绝当前外壳不认识的内容类型。同步修订 ADR-002，把 `hint-ladder` 从活动 kind 列表移到题目能力说明。

#### 9. 提示泄露检查如果直接作为硬失败，会频繁误报

- 严重程度：重要
- 位置：`docs/specs/content.md` 第 3.4 节、第 5 节
- 问题：选择题正确选项如果是“是”“一样大”等短文本，最后提示中正常出现“这是因为……”也可能命中“是”。另一方面，同义表达、数字中文写法和算式变形又很容易绕过检查。它既不能完整防泄露，也可能阻碍正常写作。
- 建议：将其分成两层：数字/分数的明确答案写法可以硬失败；选择题短选项和常见词只做警告，由审核者确认。测试同时包含“确实泄露答案”和“包含相同字但没有泄露”的样例。

#### 10. SVG 黑名单与路径规则还不足以支撑长期稳定构建

- 严重程度：重要
- 位置：`docs/specs/content.md` 第 1 节、第 3.6 节、第 6.2 节
- 问题：仅禁止 script、foreignObject、on 属性和外部 href，仍可能漏掉 CSS `url()`、`@import`、`xlink:href` 等外部资源或主动内容。哈希方面，原始字节＋排序的设计在同一仓库字节下基本可复现，但没有规定 POSIX 路径规范化、大小写冲突和 Unicode 规范化；资产路径经过不同文件系统时可能产生难排查的差异。
- 建议：SVG 使用元素和属性白名单，并覆盖 CSS URL、xlink 和嵌套资源；不要只做黑名单。仓库路径统一为 POSIX 形式，拒绝反斜杠、`.`/`..`、大小写冲突和 NFC 冲突；正文可选择统一 NFC，但不能在哈希前悄悄修改已审核文字。

#### 11. 领域模型与事件规格仍有没有列入第 9 节的 ID 冲突

- 严重程度：重要
- 位置：`docs/specs/events.md` 第 1 节、第 9 节；`docs/domain.md` 对象一览
- 问题：事件规格使用 `qst_` 和 `rpr_`，领域模型仍使用 `q_` 和 `rep_`。第 9 节列出了奖励和航线等出入，却没有列这两项。实现者无法判断应以哪份为准。
- 建议：统一前缀，并在第 9 节明确列出所有同步修改；最好由一份词汇表生成或检查 ID 前缀，避免规格之间继续漂移。

#### 12. `make_task.py` 方向正确，但需要补几个防误用测试

- 严重程度：建议
- 位置：`tools/make_task.py`；`prompts/curio-002a.md`、`prompts/curio-003a.md`
- 问题：从指定提交读取文件、正式任务必须已合入 main、按最长反引号串选择围栏，这些处理是正确的。需要补测的是：源提示词代码块里出现字面量 `{{…}}`、嵌入内容含超长反引号串、章节后紧接代码块中的二级标题、CRLF、缺 YAML 头、未合入 main 等情况。CURIO-003a 同时要求所有动词的正反样例和 15 类补充反例，文件较多，建议按动词组拆成两批，或明确要求附件交付，降低漏文件概率。
- 建议：保留工具设计，补齐上述测试；如果源提示词需要展示字面量模板语法，提供转义方式或只扫描代码围栏外的指令。

### 其他

以下设计我明确支持，不建议推翻：

- `ContentRelease` 使用完整内容哈希，`source_commit` 不参与内容身份；
- 部署记录与不可变发布分离；
- `recorded_at` 放在摄入收据而不是事件里；
- 奖励流水作为可重建投影，`cause_key` 用于业务级防重；
- 不追求跨设备全局时间顺序；
- 用黄金向量同时约束 Python 和浏览器实现；
- 第一版只实现少量答案类型，通过版本和能力门禁逐步扩展，而不是现在设计一套覆盖所有高中题型的庞大 DSL。

## 第 1 轮 · Claude 的回应


**12 条：10 条采纳，2 条部分采纳。**下面的章节号都是修改后的编号。

1. **自由文字必须能删除**（阻断）：采纳。新增私人文字 PrivateText（`txt_<ULID>`），事件里只存 `text_id`，不存原文；新增 `text.erased` 事件。删除覆盖所有在线副本和以后生成的导出、备份；删除之后，别的设备再上传这段文字会被丢弃；「写过一段反思」这个事实保留。旧备份和已经导出的文件改不了，这一点在规格里写明，并要求恢复工具先拿到最新的删除事件。诊断日志不能记文字内容。所有人写的自由文字都改成引用：反思、提问、回答、预测理由、自定义任务标题、兑换目标标题、家长备注；各个 `reason` 改为枚举值。见 events 第 4 节，ADR-004 第 1 节已同步修订。*没有采纳的部分*：没有给每段文字单独加密。在线副本直接删除就够了；能让旧备份里的文字也失效的加密擦除，要和备份格式一起设计，留到 CURIO-008。
2. **多个事件争同一个奖励唯一键**（阻断）：采纳。events 6.2 加了一条总规则：多个候选争同一个位置时，排序键最小的生效，其余列进 `conflicts`。7.3 的规则表新增「选哪条触发事件」一列。`reward.spent` 去掉了 `amount`，扣多少由申请指向的目标的 `target` 决定。余额允许为负，为负时在家长端提示。
3. **首答和尝试合法性**（阻断）：采纳。events 6.3 改成五条：同一设备、同一孩子；actor 是孩子本人；`content` 相同；首尾事件；同一道题的 `try` 恰好是 1、2、3……。不满足就判为不一致。首答正确率的分母和分子都按「每题恰好一条 `try = 1`」来算。
4. **发布包的引用闭包**（阻断）：采纳。content 6.1 规定：已发布知识点的前置知识点都必须已发布；收录活动的全部 `targets` 都必须已发布，否则构建失败。`related` 是软引用，外壳只显示发布包里有的。CURIO-002b 要加这两个反例的测试。
5. **拍照错题不满足 `content` 范围**（阻断）：采纳。`repair.opened` 按来源分两种：`item` 必须带 `content` 和 `item_id`；`photo` 不能带 `content`，必须带附件，`node_id` 可选。新增 `repair.linked`，用于诊断之后补上知识点。错题属于哪个知识点由投影算出；还没有知识点的错题进维修舱的「待诊断」。
6. **规范 JSON 跨语言不可靠**（阻断）：采纳，用的是你提的第二种方案。判断是否重复时，按解析后的语义比较：对象不看键序，数字按数值比较，`1` 和 `1.0` 相同。数值范围限定为整数不超过 2^53−1；非整数最多 6 位小数、绝对值小于 10^9，这个范围里 Python 和 JavaScript 解析出的值一一对应。大小限制：写入时不超过 15 KiB，摄入时不超过 16 KiB，留出余量。内容哈希仍用原来的写法，但写明了为什么可复现：清单里只有 ASCII 的键、id、路径和非负整数，在这些限制下结果和 RFC 8785 一致。黄金向量里加了「`1` 和 `1.0`」这个场景。
7. **设备时钟**（重要）：部分采纳。规格明确写了第一版不防作弊，时钟错误由家长撤销奖励来纠正（新增撤销原因 `clock`）；同一条规则的各个版本，`effective_from` 互不相同。*没有采纳的部分*：「时钟偏差大的事件暂不参与按天奖励」。原因有两个：这要求投影读取收据，投影就不再只取决于事件集合，收据也得同步到设备上；而且第一阶段只有一台设备、没有服务器，根本没有可以对照的时间。
8. **引擎版本门禁**（重要）：采纳。结构化活动加 `engine` 字段，发布清单加 `engine_min`。设备的引擎版本不够时不切换到新发布，并提示「需要更新」。content 3.8 有一张引擎等级表。ADR-002 已改：提示阶梯不再是活动类型。
9. **提示泄露检查误报**（重要）：采纳。数字题、分数题出现答案写法就报错；选择题只给警告，由审核者判断。两种都要有「确实泄露」和「没有泄露」的测试样例。
10. **SVG 和路径**（重要）：采纳。SVG 改成元素、属性白名单，不允许 `<style>`、`style` 属性、DOCTYPE 和实体，`href` 和 `url()` 只能指向文件内部。路径只允许 ASCII，大小写冲突报错。正文不做 Unicode 规范化，哈希按原始字节算。
11. **ID 前缀不一致**（重要）：采纳。事件规格改用领域模型的 `q_`、`rep_`，并写明以领域模型为准；附件统一为 `blob_<SHA-256>`。*暂不做*：从词汇表自动生成或检查前缀。现在只有两份文档用到这些前缀，等前缀出现在代码里（CURIO-003b）时，再由参考内核的测试对照领域模型检查。

### 新问题

#### 1. ADR-004 与事件规格在唯一约束、信封字段上仍有未同步的矛盾

- 严重程度：重要
- 位置：`docs/adr/0004` 第 2、3 节；`docs/specs/events.md` 第 2、5.1 节
- 问题：三处不一致。(a) ADR-004 第 3 节仍把「航线 `(learner_id, plan_date)` 唯一」列为**存储层**唯一约束（「设备本地和家用后端都建这些约束」），而事件规格 5.1 只建三条约束，6.4 明确多条 `plan.created` 共存、靠投影分出生效/被取代。照 ADR 实现，第二台离线设备的当日航线会在摄入时进隔离区，它上面的 `task_done` 全部变成「指向不存在的航线」进 `conflicts`——孩子完成的任务不算数、不奖励。ADR-004 第 7 节自己写着「被取代由投影得出，不另写事件」，与第 3 节自相矛盾。(b) ADR-004 第 3 节的约束清单缺私人文字的 `text_id` 唯一（事件规格 5.1 有）。(c) ADR-004 第 2 节的信封表还是旧样子：内容字段平铺（`node_id`、`activity_id`…），没有 `actor`、`activity_kind`、`import_batch`，也没有嵌套的 `content` 对象。事件规格第 10 节只声明修订了 ADR-004 的第 1、3、5、7 节，第 2 节漏掉了。
- 建议：本 PR 内改 ADR-004：第 3 节删掉航线一条（或改写为「投影层唯一性，见第 7 节」）并补 `text_id` 约束；第 2 节信封表同步成 `event/2` 的实际字段。另建议在 collaboration 流程里加一步：规格改动合入前，逐节 diff 所有「依据」文档。

#### 2. 隔离区里的私人文字不受删除覆盖

- 严重程度：重要
- 位置：`docs/specs/events.md` 4.2、5.2
- 问题：4.2 说删除时「收到它的存储，立刻删掉这段文字」，枚举的是设备本地副本和服务器副本；5.2 说同 `text_id` 不同内容的私人文字是冲突、进隔离区，而隔离区「保留原样，可以导出」。于是存在一条路径：一段已删除的文字，它的同 ID 变体（例如家长在备份里改过一个字再导入，或某台设备 bug 重写）永久留在隔离区里，随时可能随「导出排查」带出去。删除承诺明确说覆盖「所有在线副本」，隔离区就是一个在线副本的位置，这句承诺现在不成立。
- 建议：4.2 明确「删除按 `text_id` 生效，包括隔离区里同 `text_id` 的冲突副本」；黄金向量补一条「文字进隔离区后被删除，隔离区副本也消失」。

#### 3. 语义相等未定义布尔的比较；数值范围的检查程序未定义

- 严重程度：重要
- 位置：`docs/specs/events.md` 5.2、第 2 节「数值」
- 问题：(a) 5.2 定义了对象、数组、字符串、数字的比较，唯独没有布尔。Python 里 `True == 1` 为真，JavaScript 严格相等为假。`sim.adjusted` / `sim.observed` 的 `value` 是「数字、字符串或布尔」的联合类型，一条 `value: 1` 和一条 `value: true` 都能通过 schema；此时 Python 参考内核会判「重复」直接丢弃，浏览器内核会判「冲突」进隔离区——两个内核对同一事件集合算出不同的存储和投影，恰恰违反黄金向量要保证的性质，而现有向量清单里没有这个场景，两边都测不出来。(b) 「非整数最多 6 位小数」无法在解析后的值上直接判定：`1.5e-7` 解析后两个语言都以指数形式表示（Python `'1.5e-07'`、JS `'1e-7'` 风格），按什么程序认定它有 8 位小数？不写程序，两个内核会各自发明。同理，超出 2^53−1 的整数、指数写法的整数是否合法，也没有可执行的判据。
- 建议：5.2 补一句「类型必须严格相同：布尔只与布尔相等，数字只与数字相等（整数与同值小数除外）」；「数值」一节写明检查程序——要么在原始 JSON 文本上做词法检查（数字 token 的正则，拒绝指数形式与超长小数），要么给出语义判据（如 `round(x, 6) == x`）并说明其边界；黄金向量补「`true` 对 `1`」「超出 2^53−1 的整数」「第 7 位小数」三个拒绝场景。

#### 4. 发布门禁「所有活动 approved」会让一个草稿卡死全部发布

- 严重程度：重要
- 位置：`docs/specs/content.md` 第 5 节发布门禁、6.1 收录范围
- 问题：门禁要求 published 知识点的「所有活动 approved」。知识点与活动是双向引用（CI 引用规则要求一致），所以只要有人给一个已发布知识点加一道草稿活动（比如给「分数的初步认识」加个新挑战），门禁即告失败，此后**任何**发布都构建不出来，直到这道题审完。而 6.1 收录范围写的是「它们引用的活动（必须 approved）」——按 approved 过滤收录——门禁却升级成全员必须 approved，两处意图不一致。十年期的仓库里，草稿与已发布内容共存是常态，这条规则会让 CI 长期红着。
- 建议：二选一并写明：门禁改为「被收录的活动必须 approved，未 approved 的活动不收录、不阻断构建」（此时「每个误区都已覆盖」要相应改为只按被收录的活动计算）；或保留严格版，但明确规定草稿内容只能活在分支上、main 上不允许 published 知识点挂草稿活动。当前写法两头意图都有，实现者不知道按哪个做。

#### 5. 自定义实验的契约版本没有门禁

- 严重程度：重要
- 位置：`docs/specs/content.md` 3.8、6.1；`docs/activity-contract.md`
- 问题：3.8 说自定义实验「不需要 engine，只依赖契约版本（contract）」，但发布清单只有 `engine_min`，没有任何契约版本字段。现在只有 activity/1.1，问题不会出现；将来契约升到 1.2、某个实验用了新消息时，`engine_min` 不含实验的贡献，旧外壳会正常切换到新发布，然后拿到一个它跑不了的实验——这恰是引擎等级机制声称要防的事，防漏了一半。
- 建议：发布清单加 `contract_min`（收录实验中最高的契约版本），设备切换发布时一并检查；或将实验的契约版本纳入发布门禁。现在只有 1.1，加字段是一行成本；等有了多个版本再加，就要动已定型的清单格式。

#### 6. 私人文字的孤儿与永久缺失路径没有收口

- 严重程度：建议
- 位置：`docs/specs/events.md` 4.1、4.2、5.4
- 问题：三个小洞。(a) 「设备先写文字，再写引用它的事件」之间崩溃，会产生一段没有任何事件引用的孤儿文字：界面永远不显示它，家长也就永远无法对它发出 `text.erased`，它却会跟着导出走。完整性检查只查「事件在、文字缺」这个方向，不查反方向。(b) 批内上传不是原子的：上传中断且设备随后丢失，会留下「事件在、文字永久缺失」，导出时被判「数据损坏」——这不是损坏，是设备丢了；两种情况应有区分，或至少给家长一个补救动作（例如允许对缺失文字补发一条 `text.erased`，让它从「还没同步过来」变成「已删除」）。(c) 规格没规定同一批里文字和事件的入库先后，建议写明「文字先于引用它的事件入库」，让崩溃时最多出现「有文字没事件」这个无害方向。
- 建议：按上面三点各补一句；另外 4.2 最好点名「从文字派生的本地结构（搜索索引、缓存）随之删除」——第 1 轮意见提过这些，正文只写了「本地副本」，容易被实现成只删主存储。

#### 7. 悬空引用静默吞掉、不进 conflicts；对象重复打开未定义

- 严重程度：建议
- 位置：`docs/specs/events.md` 7.3、6.4
- 问题：(a) `reward.spent` 指向不存在的申请、`reward.revoked` 指向不存在的流水时，「不产生流水」之后就没有下文——不进 `conflicts`，家长端看不见。航线和错题投影对同样情况（指向不存在的航线 / ticket）都列 `conflicts`，同一份规格里两种作风，家长排查时的盲区不一致。(b) 同一 `ticket_id` 出现两条 `repair.opened`、同一 `question_id` 出现两条 `question.asked` 时归属怎么算没有规定（错题写了「多条 `resolved` 取排序键最小」，`opened` / `asked` 没有对应规则）。
- 建议：统一「引用悬空 → 进 `conflicts`」；6.4 补一句同一 ticket / question 多条 opened / asked 时按哪个排序键生效。

#### 8. 内容 id 未强制 ASCII，内容哈希的论证前提没有被 schema 保证

- 严重程度：建议
- 位置：`docs/specs/content.md` 6.2；CURIO-002a 的 schema
- 问题：6.2 论证哈希可复现的依据是「所有键名、id、路径都是 ASCII」，但全篇只有**路径**强制了 ASCII；知识点 id、活动 id 的字符集从未被 schema 约束。领域模型说内容 id 是「人能读懂的点分路径」，哪天有人写出 `act.quiz.分数-01` 甚至带 emoji 的 id：Python 构建器按码点排序，任何按 RFC 8785（按 UTF-16 码元排序）验证的实现对非 BMP 字符会排出不同顺序，同一份内容算出两个 `content_hash`——发布身份就乱了。BMP 以内的汉字不会触发，但前提本身没有被保证。
- 建议：knode / activity 的 id 在 schema 里限定为 ASCII（字母、数字、点、连字符），002a 顺手就能做，并把「id 全 ASCII」写进 6.2 的论证前提。

#### 9. 15/16 KiB 的余量扛不住重新序列化

- 严重程度：建议
- 位置：`docs/specs/events.md` 第 2 节「大小」
- 问题：1 KiB 余量假设序列化差别很小，但同一条事件若被某个中转组件「解析再序列化」，`ensure_ascii` 风格会把中文从 3 字节变成 6 字节，接近翻倍；一条 15 KiB 的合法事件经过这样一次中转就可能超过 16 KiB 被判不合格、进隔离区。导入工具改写 `event/1` 就是现成的重新序列化场景。
- 建议：写明「存储与转发一律保留原始字节，任何组件不得重新序列化事件；需要改写的场合（如导入转换）必须重新满足写入侧 15 KiB 限制」；或把摄入上限放大到能覆盖最坏转义（两倍以上）。

#### 10. 三个文档级小不一致

- 严重程度：建议
- 位置：`docs/domain.md`、`docs/activity-contract.md`、`docs/specs/events.md` 3.2
- 问题：(a) 领域模型中 Question 的生命周期是「提出 → 已回答 → **已归档**」，事件规格只有 `question.asked` / `question.answered` 两个动词，没有归档动词。(b) 契约中 `complete` 的 payload 是 `{score, total}`，而事件规格规定 `attempt.completed` 不带分数、分数一律由投影从 `item.answered` 算出——宿主必须忽略模块报的分数，但契约文档没说，也没把这个字段降级。(c) 领域模型说航线是「2 个主线和 1 个自由探索」，事件规格允许 1～5 项、三种 kind——前者其实是外壳约束，不注明会被当成内核规则。(d) `question.asked` 的范围是「来源或无」（带 `content`、不带 `attempt_id`），活动中途经 `note_question` 提的问题只能记到活动、记不到具体哪次尝试——损失小（活动已知），但与「来源」的语义有点别扭，值得想一下是否允许带 `attempt_id`。
- 建议：删「已归档」或补动词；契约注明 `score`/`total` 仅诊断用途、宿主不记录；领域模型注明任务构成是外壳规则；`question.asked` 的范围二选一写死。

### 其他

- **对 6.2 / 7.3 确定性的系统排查结论**：我把三条依赖链各自推了反例——事件 → 航线投影 → `task-done`；事件 → 流水集合 → `revoke`；申请与目标 → `redeem`。依赖关系是无环的（`revoke` 只指向 `earn`/`adjust`，不会成环）；排序键 `(occurred_at, device_id, device_seq, event_id)` 因 `(device_id, device_seq)` 唯一而是全序，无并列；各规则的「最大 / 最小」在 7.3 表里逐一写死；「撤销打卡→`earn` 自然消失→`revoke` 无目标也不产生流水」这类跨规则互动也能收敛到唯一结果。**未找到破坏「投影只取决于事件集合」的反例**，除新问题 7 列的悬空引用盲区外。这套设计可以放心交给实现。
- **私人文字与投影的边界**：第一版的五个投影（航线、掌握度、错题、问题、奖励）确实都不读文字，说法成立。但这个不变量将来很容易被无心地破坏（比如「给反思自动写摘要」一类功能天然想读文字），建议 4.3 加一句反向警告：「任何需要读文字内容的功能必须先修订本节」。
- **两份任务提示词**：002a / 003a 拿到展开后的任务文件确实可以不提问做对——资料嵌入完整（含现有 schema 和交付规范）、正反样例有精确清单、动词对账要求写进测试、「疑问」通道明确。两个小建议：003a 体量大，收货时先抽查 schema 的动词分派和 `repair.opened` 的条件分支，这两处最容易写歪；002a 的验收标准里有「挑战覆盖了知识点的全部误区」，但测试要求没让写这个断言，实现者可能只让数据碰巧满足——建议在测试要求里补一句。002a 还有一处可留意：合格样例的知识点 `status: published`，将来 CI 若对 fixtures 目录也跑发布门禁会误伤，最好在 002b 里写明 fixtures 只做 schema 校验。
- **值得保留的设计**（第 2 轮新增或强化的，后几轮不要改掉）：`cause_key` 化的流水唯一键与由唯一键算出的 `entry_id`；「被取代航线不写事件、由投影得出」；`repair.linked` 把归属判断留给投影；发布哈希只由 Python 构建器计算、其他语言按 RFC 8785 验证；不合格样例「合格样例 + 单点补丁」的写法。
- 第 1 轮第 7 条的处置我总体接受（理由见复核表），只提醒一句：等后端真正上线、有了对照时钟之后，「偏差大的事件照样计奖励」就从理论风险变成实际风险，届时记得兑现 7.4 里「再写 ADR 加防护」的承诺。

1. **ADR-004 和规格没同步干净**：采纳。ADR-004 第 2 节的信封表改成 event/2 的实际字段，并注明以规格为准。第 3 节把存储层唯一约束改成 `event_id`、`(device_id, device_seq)`、`text_id` 三条；奖励流水的唯一键和「一天只有一条生效航线」移到投影层，写明两台设备各建的航线都会被接收。领域模型的航线一行同步修改。流程上也照你的建议加了一步：合入规格改动之前，逐节对照规格「依据」里列出的文档（见 `docs/collaboration.md`「Claude 自己的改动」第 5 条）。
2. **隔离区里的文字不受删除影响**：采纳。events 4.2 改为删除这个 `text_id` 的所有副本，包括隔离区里的冲突副本，以及从文字派生出来的搜索索引、缓存和草稿。黄金向量加了对应场景。
3. **布尔值和数值检查**：采纳。语义相等改为「先比类型」，特别写明 `true` 和 `1` 不相同。数值检查写成具体步骤：先解析成双精度浮点数；整数值不能超过 2^53−1；非整数要小于 10^9，并且按最短十进制表示（Python 的 `repr`、JavaScript 的 `String`）数，小数位不超过 6 位。指数写法照样允许，按换算后的小数位数判断。黄金向量加了「`true` 和 `1`」「超大整数」「7 位小数」三个场景。
4. **一个草稿卡住整个发布**：采纳你的第一种方案。发布门禁和覆盖检查都只看会被收录的活动（`approved` 的）；没批准的活动不收录，也不阻断发布。
5. **契约版本没有门禁**：采纳。发布清单加 `contracts`：收录的实验用到的全部契约版本。设备不支持其中任何一个，就不切换到这个发布。没有用「最低版本」这种写法，因为契约的版本之间不一定向后兼容，列出全部版本更稳妥。
6. **孤儿文字和永久缺失的文字**：采纳。规定「先文字、后事件」，写入和接收都按这个顺序。完整性检查两个方向都查：有事件没文字时，家长可以补发 `text.erased`（原因 `lost`）；有文字没事件时，家长可以直接删除（原因 `orphan`）。`text.erased` 可以指向任何 `text_id`。4.3 也加上了你说的反向提醒：任何要读文字内容的功能，都必须先修订这一节。
7. **悬空引用和重复打开**：采纳。6.2 加了统一规则：引用悬空的事件不生效，全部列进 `conflicts`。同一张错题有多条 `repair.opened`、同一个问题有多条 `question.asked` 时，都取排序键最小的。
8. **id 没有强制 ASCII**：其实 schema 已经保证了：现有 knode 和 activity schema 的 id 正则只允许小写字母、数字、点和连字符。我在 content 6.2 的论证里写明了这一前提；002a 要求发布清单和结构化活动用同样的正则，并加了「id 含汉字或大写字母」的不合格样例。
9. **重新序列化会超出大小限制**：采纳。写明所有组件存储和转发时一律保留原始字节，不重新序列化。导入工具改写数据时产生的是新事件，要重新满足 15 KiB 的写入限制。
10. **文档里的小不一致**：全部采纳。(a) 领域模型去掉问题的「已归档」状态；(b) 契约注明 `complete` 里的分数只用于诊断，宿主不把它记进事件；(c) 领域模型注明「2 个主线加 1 个自由探索」是外壳的默认安排，内核只要求 1～5 项；(d) `question.asked` 允许带 `attempt_id`，在活动进行中提的问题能记到具体哪一次尝试。
