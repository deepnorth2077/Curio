# 审阅意见 · issue #109 · 审阅者：Claude Opus 5.5（claude-opus-5-5）（Claude 会话里的子 agent）

审阅对象：`arch/slice-5a` 上的 `docs/specs/slice-5a.md`（`4ad2711`，加上 `51d46bc` 的「拍板结果」）。我对照了仓库里的真实代码：三个已发布模拟模块的 `index.html`、`schemas/event.schema.json`、`kernel/js/validate.js`、`kernel/js/mastery.js`、`app/commit.js`、`app/session.js`、`app/app.js`、`tools/build_release.py`、事件规格和竖切片 1 规格。

## 结论
需要大改：第 3 节的换算表和真实模块发的消息对不上，第 2 节的频率配额会在正常玩的时候丢掉 `observed`、`complete`。照现在的写法，用例 9（三个已发布模块零警告走到星卡）一个都过不了。宿主的状态机、沙箱和分步的大方向没有问题。

## 问题

### 1. 换算表写的不是已发布模块真正发的消息
- 严重程度：阻断
- 位置：`docs/specs/slice-5a.md`「实现上的决定」第 3 节的表和「形状的细则」；「问题」一节和用户故事 7 里的「已发布的四个模块」；用例 9
- 问题：规格说「已发布的四个模拟模块发的 `result` 是下面的形状」，还说「表里没有的字段一律算形状不符」。拿真实代码核对，这句话对三个已发布模块都不成立：
  - `act.simulation.cell-zoom-01`：`predicted` 多一个 `item`（第 280 行：`emit("predicted", { station: S.station, item, choice: i, correct, misconception }, ...)`）。`observed` 每一条都带别的字段：`{station: 1, item: "cheek", magnification}`（608 行）、`{station: 2, item: "neuron", length_m}`（690 行）、`{station: 3, divisions, cells}`（914 行）、`{station: 4, item, nucleus}`（1075 行）。照表，这个模块的每一条 `event` 都会被丢掉并记警告。
  - `act.simulation.dna-book-01`：`predicted` 对得上。`observed` 一条都对不上：`{station: 1, item: "open-nucleus"}`、`{station: 1, item: "read-all", years}`、`{station: 2, visited: [...]}`、`{station: 3, found: [...]}`（`visited`、`found` 是数组，`sim.observed` 的 `value` 根本装不下）、`{station: 4, item: "wound", divisions}`，还有星卡前的 `{station: 5, item: "star-card"}`（1019 行）。
  - `act.simulation.chromosome-pack-01`：第 3 站配对完成时发 `Host.event("answered", { station: 3, item: "pairing", correct: true, tries: S.tries })`（618 行），没有 `choice`、`misconception`，多了 `item`、`tries`。
  - 完全符合这张表的只有 `act.simulation.chocolate-split-01`，可它是 `review: claude-reviewed`，所属知识点是 `status: draft`，构建器不会收录。「已发布的四个」也不对：已发布的只有三个。
  - 后果：用例 9 要求的「契约警告 0 条」三个模块都做不到。cell-zoom 的预测和观察、dna-book 的观察会全部丢失，模块不能改（ADR-003），这些学习证据也就再也拿不回来。
- 建议：以三个模块的真实消息为准重写第 3 节。先从源码里把每个模块发的每一种 `result` 逐条列成清单，再给每个字段定去处：
  - `item` 这类标识：并进 `observable` 或 `step` 里，比如 `observable: "s2.neuron"`；
  - `magnification`、`divisions`、`years` 这类模型常量：明确写「不记，也不警告」；
  - `visited`、`found` 这类数组：改成计数或者明确丢掉；
  - `tries`：决定它算不算 `item.answered`。
  
  把「多出来的字段一律算形状不符」改成「每个 `activity_id@version` 有一张字段白名单，名单里写明的多余字段静默忽略」。用例 9 改成在 Node 里重放从真实模块录下来的消息序列（录一次，存进测试夹具），不要只靠在浏览器里用键盘走一遍。

### 2. 频率配额把 `state` 也算进去，正常玩就会丢掉学习事件和 `complete`
- 严重程度：阻断
- 位置：第 2 节「数值」表的「消息频率」一行；用例 6、用例 9
- 问题：三个模块都在 `requestAnimationFrame` 的 `tick` 里，每一帧画面变化都发一次 `state`。比如 chromosome 的 `readout1()` 每帧调用 `Host.state(...)`，cell-zoom 的 `readoutZoom()`、`readout3()`，dna-book 的 `readout1/2/4()` 也一样。按住、拖动、缓动收尾的整个过程中，60 Hz 屏幕上每秒大约 60 条，120 Hz 屏幕上可能更多，另外还有 `resize`。更要紧的是，完成一个动作的那一帧会在同一个 tick 里先发 `state`、再发 `event`：chromosome 是 `readout1(); ... done1()`，`done1()` 里发 `observed`。按「每秒不超过 60 条，超出的丢掉」，这一秒里的第 61 条正好是 `observed`。`complete` 一样可能被丢，这次尝试就永远完不成，星星也不会变。在 120 Hz 的 iPad 上，每秒还会多一条警告，很快超过 20 条。
- 建议：`state` 和 `resize` 不计入频率配额。`state` 只留最后一条（本来就只在内存里留最后一条），覆盖不警告；`resize` 取每个时间窗的最后一次应用。`event`、`note_question`、`complete` 单独计数，上限可以低一些（比如每秒 20 条），并且写明 `complete` 永远不因为频率被丢。用例 6 改成：「100 条 `state` 中间夹 1 条 `observed`，`observed` 照常写出，0 条警告」。

### 3. 宿主和 committer 怎么衔接没写，照现有 API 直接接上会丢事件
- 严重程度：重要
- 位置：第 2 节「`app/` 里的薄适配层……把输出交给竖切片 1 的 `committer`」；竖切片 1 规格 6.2
- 问题：
  - 竖切片 1 的挑战同一时间最多一条 `pending`，有 `saved`、`failed`、「再试」的循环。模块的消息不一样：它们是一连串发过来的，宿主没法让模块等。`committer.nextSeq` 要等上一条被接收以后才加 1，`store.commit` 在事务里核对序号，对不上就中止。如果适配层收到消息就立刻组装原始文字，连着来的两条会拿到同一个 `device_seq`，第二条的事务中止，`submit` 抛错。真实的例子：dna-book 第 1019 行在同一个 tick 里先发 `observed` 再发 `complete`。
  - 规格也没说一条事件存失败以后怎么办。如果 `attempt.started` 没存上、后面的事件存上了，或者 `try=1` 没存上、`try=2` 存上了，整次尝试都会被判成规则 4 或规则 5 不一致，「探索过」也就丢了。
  - 下面几件事也都没写：舰长点「回星图」时，还没存完的事件和 `abandoned` 谁先；什么时候画星图；失去写锁、`committer` 冻结的时候运行怎么办。
- 建议：在第 2 节写明：
  - 适配层维护一个先进先出的队列，**轮到某一条时**才取 `committer.nextSeq` 组装原始文字，一次只交一条；
  - 任何一条 `submit` 失败，就把这次运行转到「中止」，丢掉队列里剩下的事件，显示「没存上，请刷新」。不要跳过失败的那条接着写，残缺的尝试留给启动时补一条 `abandoned`；
  - 离开时先等队列排空，再写 `abandoned`，然后再画星图；
  - `committer.frozen` 为真时立即中止，并且不再写任何事件。
  
  补一个用例：同一个 tick 里收到 `observed` 和 `complete`，两条序号连续、都被接收；中间一条存失败，后面的不再写，尝试的状态由启动恢复处理。

### 4. 内核这一版不认 `poe.predicted`、`sim.observed`，规格没有明说要加，事件规格本身也不在改动清单里
- 严重程度：重要
- 位置：「怎么分步」5a-2 的「改到哪里」；第 3 节「事件格式的一处改动」；「和已有规格的关系」
- 问题：`kernel/js/validate.js` 的 `SLICE_VERBS` 只有竖切片 1 的 5 个动词，`checkVerb` 对别的动词返回「这一版不认这个动词」，`log.check` 会判为隔离，`commit.js` 第 54 行收到隔离结果就抛 `QuarantinedError`。规格只在「改到哪里」里提了一句 `validate.js`，没有像竖切片 1 第 3 节那样写出两个新动词在摄入时的逐字段规则：`step` 最多 32 个码点、`misconception` 的格式、`sim.observed` 的 `value` 按 `simValue` 校验。另外，事件规格 3.1（`poe.predicted` 的 payload）和 3.7（`note_question` → `question.asked`）都要改，`docs/specs/events.md` 却不在任何一步的改动清单里。结果会是 schema 和事件规格的文字互相矛盾。
- 建议：在规格里加一张和竖切片 1 第 3 节同样格式的表，写清楚 `poe.predicted`、`sim.observed` 摄入时的规则和对应的黄金向量。`docs/specs/events.md` 3.1、3.7 的修改放进本规格同一个 PR，作为架构改动一起审，不要留给实现者。3.7 里注明「activity/1.1 模拟模块的 payload 换算见竖切片 5a 第 3 节；`note_question` 在竖切片 2 之前不记录」。

### 5. CSP 的插入点可以被绕过；沙箱还有几条出网的路，用例 8 没测
- 严重程度：重要
- 位置：第 2 节「装载」；用例 8；ADR-005 第 2 条和「能保证」
- 问题：
  - 「在 `<head>` 的最前面插入」按字面是找 `<head>` 字样。模块如果在 `<head>` 之前写 `<script>`、`<img>` 或 `<link rel=preload>`，HTML 解析器会照样执行、加载它们，而这时 CSP 的 `<meta>` 还没被解析，不起作用。注释或字符串里出现的 `<head>` 也可能被误当成插入点。三个已发布模块的开头都是规整的 `<!DOCTYPE html><html><head><meta charset>`，所以现在没事，但这是给以后不可信模块定的规则。
  - `default-src 'none'` 管不住下面几种情况：
    - iframe 自己跳转：`location = "https://…?数据"`、`<meta http-equiv="refresh">`、点一个 `<a>`。不给 `allow-top-navigation` 只能拦住跳转顶层页面，拦不住 iframe 自己跳走。
    - WebRTC 的 STUN/TURN 请求。CSP 的 `webrtc` 指令基本没有浏览器实现。
    - 部分浏览器的 `dns-prefetch`。
  - 模块能拿到的东西有：`init` 里的 `mastery`，还有孩子在模块里打的「我有个问题」原文。iframe 跳走以后，`event.source` 还是同一个窗口对象，新文档不带我们插的 CSP，宿主之后用 `"*"` 发给它的消息也会送过去。
- 建议：
  - 插入点改成「紧跟在开头的 `<!DOCTYPE html>` 之后」，并在构建器或审核里拒收开头不是 `<!DOCTYPE html>` 的模块。
  - 适配层监听 iframe 的 `load`，第二次 `load` 就立即中止并移除 iframe（`reason: error`），这也给了「出错」一个能检测的来源，见问题 6。
  - `init` 只发模块必需的字段，`mastery` 能不发就不发。
  - 用例 8 加上 iframe 自跳转、`meta refresh`、`RTCPeerConnection` 三项。
  - 在 ADR-005「不能保证」里如实写上「跳转和 WebRTC 只能事后发现、无法事前阻止」，不要再写「连不上网」。

### 6. `reason: error` 检测不到，`timeout` 也永远写不出来
- 严重程度：重要
- 位置：第 2 节状态表「中止」一行、「舰长看到的」；第 3 节 `attempt.abandoned` 的 `reason`
- 问题：iframe 带 sandbox、不同源，父页面拿不到它的 `window.onerror`。iframe 元素的 `error` 事件也不会因为脚本出错而触发。activity/1.1 里也没有模块报错的消息。所以「iframe 报错是 `error`」实现不了。另一边，`timeout` 只会发生在 `ready` 之前，那时还没有 `attempt.started`（用例 3 就是这么算的），于是 `reason: timeout` 永远不会被写出来。表里三个 `reason` 实际只用得到 `left`。
- 建议：把 `error` 定义成能检测到的情况：iframe 第二次 `load`（问题 5），以及运行中 committer 失败（问题 3）。写明 `timeout` 这一版不会出现在事件里。补一个「运行中 iframe 跳走」的用例。

### 7. 和 ADR-005 的字面差别不止两处，应该写成增补
- 严重程度：重要
- 位置：第 2 节「说明两处和 ADR-005 字面不同的地方」；ADR-005 第 3、4、6 条
- 问题：除了 `run_id` 和心跳，还有两处：
  - ADR-005 第 4 条把「来自当前 iframe」列在「不满足就丢掉**并记警告**」里，规格的第 1 条改成了静默忽略；
  - ADR-005 第 3 条的状态是「加载 → 就绪 → 运行（预测、观察）」，规格把「就绪」并进了「运行」，也没有预测、观察两个阶段。
  
  这四处在实现上都说得通：一次运行一个 iframe，按窗口对象认就等于 `run_id`；别的窗口、浏览器扩展发来的消息不该算模块的警告。但 ADR 是已接受的决定，十年后的读者对着 ADR 看代码，会以为实现错了。
- 建议：在同一个 PR 里给 ADR-005 写「增补 1」，四处各一句：`run_id` 由「一次运行一个 iframe，按 `event.source` 认」实现；来源不对的消息静默忽略；「就绪」并进「运行」，预测、观察阶段留给 #28；activity/1.1 没有心跳，靠宿主画在模块外面的「重新开始」兜底。增补走 Luka 确认。

### 8. 「试玩记录」实际上就是 ADR-006 说的「试用」，「以后可能算数」缺一个机制
- 严重程度：重要
- 位置：第 5 节；「拍板结果」第 1 条；ADR-006 第 1、4 条和「后果」
- 问题：
  - ADR-006「后果」写的是「试用（CURIO-009a）要等 CURIO-006 做完才能开始」。孩子在正式外壳里玩真实内容、留下记录，这就是试用。换个名字不等于没有放宽，规格说「本切片不放宽它」不准确。
  - 「以后由 Luka 决定留不留」的风险：这期间事件格式还会改（比如 Codex 审查里延后的数据模型改动），到时候要留这些记录，就需要升级器或导入工具。ADR-006 第 4 条还要求每个历史格式在 `tests/fixtures/` 里留一份样例，规格没有安排。
  - iPad 上的 Safari 会删网站的脚本存储：网站连续 7 天没打开（按用浏览器的天数算），IndexedDB 就会被清掉。加到主屏幕的网页应用不受这条限制。「长时间不打开」对家长来说太模糊。
- 建议：
  - 第 5 节写明「这是 ADR-006 意义上的提前试用，经 Luka 2026-11-11 同意；数据只当作可以丢掉的」，并在 ADR-006 末尾记一句。
  - 如果保留「可能算数」这个选项：现在就把本切片的事件格式冻结成一份夹具放进 `tests/fixtures/`；写明格式变了时要怎样才算「可以留下」，比如必须有升级器并通过夹具测试，否则清掉。
  - 那行提示改成「试玩记录 · 只在这台设备上 · 还没有备份 · 7 天不打开可能会丢」。演示步骤里加一步「把演示页添加到主屏幕」，适配层调用 `navigator.storage.persist()`。
  - 这行提示要在 5a-1 就出现，见问题 14。

### 9. 完成以后的消息和「我有个问题」会显示自相矛盾的话，还会刷警告
- 严重程度：重要
- 位置：第 2 节状态表「完成」一行、「模块里『再玩一次』可以照常玩」；第 3 节「『我有个问题』这一版不记录」；演示步骤 8
- 问题：
  - chromosome 的 `ask()`（217 行）不看第几轮，「再玩一次」时照样发 `predicted`、`answered`；三个模块重玩时也都照样发 `state`。在「完成」状态下，这些都会被丢掉并记警告，正常重玩一次就能攒满 20 条警告。
  - 「完成」状态不收 `note_question`。孩子在星卡页点「我有个问题」，宿主什么都不显示，模块却说「好问题，我记下来了。等会儿一起找答案。」（三个模块都这样写，比如 chromosome 237 行）。就算在「运行」状态，孩子也会同时看到模块说「我记下来了」、宿主说「我现在还带不走」，两句话互相矛盾，这正是不该对孩子说的假话。
- 建议：
  - 「完成」状态下的 `event`、`state` 静默丢掉，不记警告（这是已知的合法行为）；
  - `note_question` 在「运行」和「完成」两个状态都接收，都显示宿主那句话；
  - 宿主那句话改成能接住模块那句的说法，比如「其实这一次还没记下来。先讲给爸爸妈妈听，好吗？」，或者干脆在本切片里不显示「我有个问题」入口。入口在模块里，宿主藏不掉，所以只能改文案。请 Luka 在演示步骤 8 里确认这两句话放在一起读得通。

### 10. 验收用例有一处期望值取决于没写的时间，还缺几种重要情况
- 严重程度：重要
- 位置：「测试接缝」用例 6、7 和缺的用例
- 问题：
  - 我手算核对了用例 1、3、4、5：
    - 用例 1：`duration_ms` = 90000 − 400 = 89600；`try` 是 1、2，符合合法性第 5 条；`simulation` 的完成尝试在 `mastery.js` 里得到 `explored`；
    - 用例 3：0 条事件；
    - 用例 4：4 条事件，`untouched`；
    - 用例 5：`app/app.js` 的 `completedBefore` 按 `activity_id` 判断，结果是 `retry`。
    
    这几个都对。用例 2 的 8 条也都符合第 2 节的规则。
  - 用例 7「一次运行里收到 250 条 `observed`」没给时间。如果在同一秒里到达，先被频率配额截在 60 条，期望值就不是 200 条。
  - 「每秒」是固定的时间窗还是滑动窗，没有定义，用例 6 没法写成确定的测试。
  - 缺的情况：重复的 `ready`；「加载」状态收到 `resize`（真实模块的 `ResizeObserver` 碰巧在 `ready` 之后才触发，规则一变就会出警告）；「重新开始」之后旧 iframe 迟到的消息；`complete` 和「回星图」同时发生；页面刷新时一次未结束的模拟尝试（含 `poe.predicted`、`sim.observed`）被补成 `abandoned`，这要求 `session.js` 依赖的 `projectMastery` 先认识新动词；committer 失败（问题 3）；iframe 跳走（问题 5）。
- 建议：用例 7 写明「每 100 ms 一条」；频率改成「从运行开始按 1000 ms 划固定窗」之类可以手算的定义；把上面缺的情况各补成一个用例，期望值手算写进去；「加载」状态收到 `resize` 时静默应用或丢掉，不记警告。

### 11. 换出来的事件十年后不好读，同一个站号写成了三种样子
- 严重程度：建议
- 位置：第 3 节的表
- 问题：同一次尝试里，第 1 站写成了 `step: "1"`（字符串）、`value: 1`（数字）、`item_id: "station-1"` 三种。`sim.observed {observable: "station", value: 1}` 读起来像「观察到站号是 1」，其实意思是「第 1 站的观察做完了」。`item_id: "station-4"` 和挑战里的题目 id 混在同一个动词里，内容文件里却查不到它是哪道题；以后的错题投影（6.4 `source: item`）可能把模拟里的答错当成错题。`response: String(choice)` 是选项的序号，不是选项 id，只有和 `activity_version` 一起看才有意义。
- 建议：全规格统一用一种写法，比如 `s1`、`s3.pairing`：`sim.observed {observable: "s1", value: true}`、`item_id: "sim:s4"`。在第 3 节写一句「模拟里的 `item_id` 以 `sim:` 开头，不对应内容文件里的题目，掌握度和错题投影都不用它」，并在事件规格 6.4 里同步写上。

### 12. 给 `poe.predicted` 加字段只对「新读者读旧事件」兼容
- 严重程度：建议
- 位置：第 3 节「事件格式的一处改动」；事件规格第 8 节
- 问题：第 8 节允许「加可选字段」，所以字面上合规。但 schema 是 `additionalProperties: false`，旧版本的内核读到带 `step`、`correct`、`misconception` 的新事件会判为不合格并隔离。现在只有一台设备，问题不大；到了多设备同步（#11）、浏览器里缓存着旧外壳的时候，就会冒出来。另外，`correct` 放在「预测」上，和将来平台自己做的 POE（#28，预测本来无所谓对错）语义不合。
- 建议：保留这个方案，但在事件规格第 8 节加一句「新增可选字段的版本，必须先让所有读者升级，写入方才能开始写」。或者换一个办法：把这几个模块的 `predicted`（本质上是一道有标准答案、带误区的选择题）记成 `item.answered`（`item_id: "sim:s1.predict"`），不用改 schema，误区 id 也保住了，代价是 3.7 表里的这一行要改。两条路请在规格里选定一条，并写明理由。

### 13. 和活动契约的几处小矛盾和漏写
- 严重程度：建议
- 位置：第 2 节；`docs/activity-contract.md`
- 问题：
  - 契约写「不带 `contract: "activity/1.1"` 的一律忽略」，规格对 `activity/1.0` 记警告；
  - 契约写「3 秒内没收到 `ready` 记一条警告」，规格只有 10 秒中止；
  - `request_hint` 在契约里有，规格的接收表里没有；
  - `complete` 的 `{score, total}` 没定类型；
  - `init` 的 `phase`、`mastery`、`palette` 发什么值没写；
  - `resize`「多的丢掉」可能让最后一次高度没被应用；
  - 按 `JSON.stringify` 量消息大小时，结构化克隆可以送来 `BigInt`、循环引用，这时 `stringify` 会抛错。
- 建议：把这些都写进要更新的契约文档：
  - 契约版本不对时记警告，契约里的那句同步改掉；
  - 删掉 3 秒那条，或者写明它只是诊断警告；
  - `request_hint` 这一版收到就警告；
  - `score`、`total` 写成非负整数；
  - 列出 `init` 的每个字段和取值；
  - `resize` 取时间窗内的最后一次；
  - `stringify` 抛错时算形状不符。

### 14. 分步：顺序对，但 5a-1 要多带几样东西，5a-2 可以再拆
