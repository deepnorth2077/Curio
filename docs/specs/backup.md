## 问题

现在舰长的作答只存在一台设备的浏览器里。清一次缓存、换一台平板、Safari 自己清理存储，记录就全没了。ADR-006 定了：导出、恢复没做、没演练过之前，设备上的记录只算试玩记录，不能当真。

## 方案

做完以后：

- 家长在「家长」页点「做一份备份」，得到一个加密的备份文件（`.curio`），存到电脑或网盘。第一次做的时候，Curio 先给一把**恢复密钥**（25 个字母数字），家长抄两份、放两个地方。以后的备份都用这一把，云上的副本（CURIO-008）也用这一把。
- 另有「导出成文字」：一个人和别的程序都看得懂的文本文件（JSON Lines），不加密，不能用来恢复。
- 在另一台设备、另一个浏览器上点「从备份恢复」，选文件、输入恢复密钥，星星和记录原样回来。再导入一次同一个文件，什么都不变。文件坏了、密钥不对、是别的孩子的，都给明确的提示，原有记录一点不动。
- 家长页显示「上次备份：几天前」和一个**记录指纹**（8 个字符）。两台设备指纹一样，就说明记录一样，Luka 用眼睛就能比。
- Luka 做一次真实的恢复演练，记录写进 `docs/retros/`。演练通过以后，设备上的记录开始算数。

## 实现上的决定

### 1. 备份里有什么

v1 备份包含设备存储里**全部**的东西（`docs/specs/slice-1.md` 6.2 的三个仓库，加上本规格新加的两个），一样不挑：

| 部分 | 内容 | 顺序 |
| --- | --- | --- |
| `inbox` | 收件表里的每一条原始文字，**原样**（包括被隔离的原文） | 按到达顺序 |
| `receipt` | 收据（事件规格 5.3） | 按 `event_id` 的码点顺序 |
| `receipt_archive` | 以前恢复时带过来的旧收据（第 5 节） | 按存入顺序 |
| `import` | 以前的导入批次记录（第 5 节） | 按存入顺序 |

再加上清单里的身份（`learner_id`、做备份的 `device_id`）。

**不放进备份**的：恢复密钥本身；`nextSeq`（恢复出来的设备是新设备，序号从 1 开始）；上次备份的时间（每台设备自己的事）；内容发布包（发布包按 `content_release` 的哈希能从网站重新拿到，ADR-006 表里的「能拿到它们的确切来源」）。

**收件表要保留到达顺序**：同一个 `event_id` 先来的被接收、后来的内容不同的进隔离区。恢复到干净设备时按原顺序重新摄入，才能得到一模一样的日志。

现在还没有私人文字、附件、航线、奖励（竖切片 2～4 才有）。等它们有了，清单升到 `backup-manifest/2`，加新的部分（第 3.4 节）。

### 2. 恢复密钥

**样子**：25 个字符，分 5 组，每组 5 个，用 Crockford Base32 的字符（`0-9`、`A-Z` 去掉 `I L O U`）：

```
7KQ2M-XW9PD-4HN6T-RB3CJ-8FVA2
```

- 前 24 个字符是 15 个随机字节（120 位）按 Crockford Base32 编码，大端，每 5 位一个字符，不补位。
- 第 25 个字符是校验位：这 15 个字节的 SHA-256 的第一个字节，取高 5 位，编成一个字符。抄错一个字符，几乎一定当场发现。
- **输入时宽容**：忽略空格和连字符；小写当大写；`O` 当 `0`，`I`、`L` 当 `1`；有 `U` 或别的字符就提示「有一个字不对」；长度不是 25 提示「位数不对」；校验位不对提示「抄错了一个字，请对照纸上再看看」。
- 用 `crypto.getRandomValues` 生成，不用 `Math.random`。

**来历和以后**：这就是 ADR-010 第 7 条的「家庭恢复密钥」。CURIO-008 做云上副本时，它就是主密钥，不再另做一把。v1 里设备直接把这 15 个字节存在本机（第 5 节 `meta`）。能摸到这台设备的人本来就能看到记录，所以这不增加风险；备份文件放到网盘、被别人拿到，没有密钥就读不出来，这才是要防的。CURIO-008 再按 ADR-010 给本机这份包一层本地口令。

**第一次做备份时**：

1. 显示密钥（大字、等宽字体），下面写：「这是恢复密钥。抄两份，放在两个地方。丢了它，备份就打不开了。」给一个「打印」按钮：打印页只有密钥、日期和一句用法说明。
2. 家长点「抄好了」以后，要把 25 个字符**完整输入一遍**，和原密钥一致（按上面的宽容规则比较）才算完成，然后才开始做第一份备份。输入不一致：提示哪一组不一样，可以回去再看。
3. 以后在家长页可以「再看一次恢复密钥」。

v1 **不能换密钥**。要换的话以后写 ADR（旧的备份文件还得用旧密钥打开，这要说清楚）。

### 3. 备份文件格式（`curio-backup/1`）

#### 3.1 文件的样子

文件名：`curio-backup-YYYYMMDD-HHMM.curio`（本地时间，UTC+8，和事件规格第 1 节一致）。文件是二进制，依次是：

1. 第一行：ASCII 的 `CURIO-BACKUP/1`，后跟一个换行 `\n`（0x0A）。
2. 第二行：**文件头**，一个 JSON 对象，UTF-8，紧凑写法，整行不超过 4096 字节，后跟一个 `\n`。
3. 后面全部是**密文块**，一个接一个，中间没有分隔。

文件头：

```json
{"format":"curio-backup/1","created_at":"2026-11-13T10:30:00.000Z","kdf":"hkdf-sha256","salt":"<16 字节>","key_check":"<16 字节>","cipher":"aes-256-gcm","nonce_prefix":"<7 字节>","chunk_size":1048576,"compression":"gzip"}
```

| 字段 | 说明 |
| --- | --- |
| `format` | 固定 `curio-backup/1` |
| `created_at` | 做备份的 UTC 时间，格式同事件规格第 1 节 |
| `kdf` | 固定 `hkdf-sha256` |
| `salt` | 每个文件新生成的 16 个随机字节，标准 Base64（带 `=` 补位） |
| `key_check` | 16 字节，标准 Base64，见 3.2 |
| `cipher` | 固定 `aes-256-gcm` |
| `nonce_prefix` | 每个文件新生成的 7 个随机字节，标准 Base64 |
| `chunk_size` | 明文块的字节数，v1 固定 1048576（1 MiB） |
| `compression` | `gzip` 或 `none`。写的时候浏览器有 `CompressionStream` 就用 `gzip`；读的程序两种都必须支持 |

不允许有表里以外的字段；字段缺了、值不对，都按「文件坏了」处理（3.5）。文件头不加密，里面没有孩子的任何信息。

#### 3.2 密钥和加密

- **派生**：用 HKDF-SHA256，输入密钥材料是恢复密钥的 15 个字节，`salt` 是文件头里的 16 个字节，派生两样东西：
  - 加密密钥：`info` = ASCII `curio-backup/1 enc`，长度 32 字节，作 AES-256-GCM 的密钥；
  - 密钥检查值：`info` = ASCII `curio-backup/1 check`，长度 16 字节，写进文件头的 `key_check`。
- **读的时候先比 `key_check`**：不一样就是「恢复密钥不对」，不用去解密文。这样「密钥不对」和「文件坏了」能分开说。
- **明文流**：把第 4 节的明文文档（UTF-8 字节）按 `compression` 压缩（`gzip` 是 RFC 1952 的 gzip 格式，和 `CompressionStream("gzip")` 一样），得到一串字节，从头切成每块 `chunk_size` 字节，最后一块可以短，但不能是 0 字节（明文文档不可能是空的）。
- **每一块**单独用 AES-256-GCM 加密：
  - 随机数（12 字节）= `nonce_prefix`（7 字节）+ 块序号（4 字节，大端无符号，从 0 开始）+ 末块标记（1 字节：最后一块是 `0x01`，其他是 `0x00`）；
  - 附加数据（AAD）= 文件第二行的原始字节，不含结尾的 `\n`。改动文件头的任何一个字节，所有块都解不开；
  - 密文块 = 密文 + 16 字节的认证标签。所以除最后一块外，每个密文块都正好是 `chunk_size + 16` 字节。
- **读的时候**：按 `chunk_size + 16` 一块一块切；最后剩下的不足一整块（或正好一整块）的就是末块，用末块标记 `0x01` 解；其他用 `0x00` 解。文件被截断在块的边界上时，最后一块会用 `0x01` 去解一个当初用 `0x00` 加密的块，必然失败，所以截断一定能发现。剩下 0 字节、或最后一块不足 17 字节，是「文件坏了」。
- 块的总数不超过 2^32 − 1。

#### 3.3 为什么这样做

- 分块：十年的记录可能有几百 MB，iPad 上不能一次把整个文件读进内存再解。分块可以边读边解边写。
- 末块标记和块序号放进随机数，是成熟的「分块认证加密」做法（STREAM），防止块被调换顺序、被截断。
- 每个文件新的 `salt` 和 `nonce_prefix`：同一把恢复密钥做几百个备份，每个文件的加密密钥都不同，随机数永不重复。
- 用浏览器自带的 Web Crypto（HKDF、AES-GCM）和 `CompressionStream`，不引入任何依赖（ADR-008）；Python 的标准做法也能读，十年后不靠 Curio 也有办法解开。

#### 3.4 版本

- 文件第一行的 `/1`、文件头的 `format` 是**文件格式**的版本（加密和分块怎么做）。
- 明文文档第一行的 `schema` 是**内容**的版本（`backup-manifest/1`，第 4 节）。加私人文字、附件时只升这个，文件格式可以不变。
- 读的程序遇到不认识的版本（比如 `curio-backup/2`、`backup-manifest/3`），提示「这个备份是新版本的 Curio 做的，请先更新 Curio」，什么都不写。
- **每一个版本**都在 `tests/fixtures/backup/` 里永久留一个样例文件，配一把公开的测试密钥（ADR-006 第 4 条）。以后的读程序必须一直能读它们。

#### 3.5 读不了的时候

读备份按下面的顺序检查，**第一处不对就停**，存储一点不动：

| 情况 | 提示（给家长） |
| --- | --- |
| 第一行不是 `CURIO-BACKUP/` 开头 | 这不是 Curio 的备份文件 |
| 第一行或文件头的版本不认识 | 这个备份是新版本的 Curio 做的，请先更新 Curio |
| 文件头不是合法 JSON、字段缺了或不对 | 备份文件坏了 |
| 恢复密钥格式不对（第 2 节） | 按第 2 节的提示 |
| `key_check` 不一样 | 恢复密钥不对。请对照纸上的密钥再输一次 |
| 任何一块解不开、gzip 解不开、明文不是合法 UTF-8 | 备份文件坏了，或者不完整。换一个备份文件试试 |
| 明文文档不符合第 4 节 | 备份文件坏了 |

### 4. 明文文档（`backup-manifest/1`）

解密、解压以后是一个 JSON Lines 文档：UTF-8，每行一个紧凑 JSON 对象，每行以 `\n` 结尾（包括最后一行），没有空行。

第一行是清单：

```json
{"schema":"backup-manifest/1","created_at":"2026-11-13T10:30:00.000Z","learner_id":"lrn_…","device_id":"dev_…","app_commit":"275c460","counts":{"inbox":120,"receipt":118,"receipt_archive":0,"import":0}}
```

- `created_at` 和文件头的一样；`learner_id`、`device_id` 是做备份的这台设备的身份；`app_commit` 是做备份时外壳的提交号（7～40 个小写十六进制，查问题用，读的时候不检查）；`counts` 是后面每一部分的行数。

中间是记录，按 `inbox`、`receipt`、`receipt_archive`、`import` 的顺序，每部分内部按第 1 节的顺序：

```json
{"t":"inbox","raw":"{\"schema\":\"event/2\",…}"}
{"t":"receipt","v":{"event_id":"evt_…","recorded_at":"…","source":"local"}}
{"t":"receipt_archive","v":{…一条收据…}}
{"t":"import","v":{…一条导入记录，第 5 节…}}
```

最后一行：

```json
{"t":"end","lines":239,"sha256":"<64 位小写十六进制>"}
```

- `lines` 是清单和全部记录的行数（不含这一行）；`sha256` 是这些行（含每行的 `\n`）的 UTF-8 字节的 SHA-256。认证加密已经保证文件没被改过，这个校验和防的是**写的程序自己出错**（漏写、写错顺序）。
- 读的时候全部检查：`schema` 认识；`t` 只能是这五种，顺序不能乱；每部分的行数和 `counts` 一致；`lines`、`sha256` 对；`end` 后面不能再有东西；`raw` 是字符串（内容不在这里检查，恢复时交给日志判断）；`receipt` 和 `receipt_archive` 的 `v` 符合 `schemas/ingest-receipt.schema.json`；`import` 的 `v` 符合第 5 节。任何一条不对，整个文件按「备份文件坏了」处理。

### 5. 设备存储的升级（IndexedDB 版本 1 → 2）

`app/store.js` 的数据库从版本 1 升到 2，**只加东西，不改旧仓库**（原则 7：迁移就是在 `onupgradeneeded` 里建两个新仓库；旧的 `inbox`、`receipts`、`meta` 原样保留）：

| 仓库 | 主键 | 存什么 |
| --- | --- | --- |
| `receipts_archive` | 自增 | 恢复时从备份带过来的收据（备份里的 `receipt` 和 `receipt_archive` 两部分），只追加 |
| `imports` | `batch_id` | 每次恢复一条导入记录 |

`meta` 新加三个键：`recoveryKey`（15 字节，`Uint8Array`）、`lastBackup`（`{at, file_name}`）、`restoring`（恢复进行中的标记，见 6.3）。

导入记录（`import-record/1`）：

```json
{"schema":"import-record/1","batch_id":"imp_…","imported_at":"…","source":"backup","file_created_at":"…","file_device_id":"dev_…","accepted":118,"duplicate":0,"quarantined_new":2,"quarantined_skipped":0,"archived":118}
```

计数都是非负整数，意思见 6.2。这一条格式写进 `schemas/import-record.schema.json`。

### 6. 恢复

#### 6.1 能不能恢复到这台设备

外壳一打开就会建身份（slice-1 6.3），所以「干净的设备」也已经有一个 `learner_id`。规则：

| 这台设备上 | 备份是 | 怎么办 |
| --- | --- | --- |
| 收件表是空的 | 任何孩子 | 可以恢复。身份换成备份的 `learner_id`，`device_id` 和 `nextSeq` 不变（这台设备还是它自己，事件规格第 1 节：新设备、新 ID） |
| 收件表不空，`learner_id` 和备份一样 | 同一个孩子 | 可以恢复：把备份**合并**进来（6.2） |
| 收件表不空，`learner_id` 不一样 | 另一个孩子 | 不恢复。提示「这个备份是另一个孩子的，这台设备上已经有记录了」 |

恢复出来的设备**用自己的 `device_id`** 继续记录，不冒用备份里那台设备的 ID：原来的设备可能还在用，两台用同一个 ID 就会撞序号。

#### 6.2 恢复计划（纯函数）

`planRestore(existing, backup, {batchId, now})`：不碰存储、时间和随机数，在 Node 里能直接测。

- `existing`：`{identity, inbox: [raw…], archive: [收据…]}`（从存储读出）；
- `backup`：第 4 节解出来的清单和各部分；
- 返回 `{ok: false, reason}`，或者 `{ok: true, identity, appendInbox, receipts, appendArchive, record, report}`。

步骤：

1. 按 6.1 判断能不能恢复，不能就返回 `ok: false`。
2. 用 `existing.inbox` 按顺序 `ingest` 建一个日志（和外壳启动时一样）。
3. 备份的 `inbox` 按顺序，每一条：
   - `log.check(raw)` 是 `accepted`：`ingest`；放进 `appendInbox`；生成收据 `{event_id, recorded_at: now, source: "import", batch_id}` 放进 `receipts`；`accepted` 加一。
   - `duplicate`：什么都不放；`duplicate` 加一。
   - `quarantined`：如果这段原始文字**逐字节相同**的一份已经在 `existing.inbox` 里、或者已经放进了 `appendInbox`，跳过，`quarantined_skipped` 加一；否则 `ingest`（进隔离区），放进 `appendInbox`，`quarantined_new` 加一。没有这一条，同一个文件每导入一次，隔离区就多一份。
4. 备份的 `receipt`、`receipt_archive` 两部分按顺序，每一条：和 `existing.archive`、已经放进 `appendArchive` 的每一条按事件规格 5.2 的「语义相同」比，都不同才放进 `appendArchive`，`archived` 加一。
5. 备份的 `import` 部分**不**进本机的 `imports`（那是别的设备的导入历史），只在 `report` 里列出条数。
6. `record` 是这次的导入记录（第 5 节），`identity` 是恢复后的身份（6.1）。
7. `report` 给家长看：接收了几条、重复几条、新进隔离区几条、恢复后的记录指纹（第 8 节）。

同一个文件导入第二次：步骤 3 全是 `duplicate` 或 `quarantined_skipped`，步骤 4 全部相同，`appendInbox`、`receipts`、`appendArchive` 都是空的。只多一条导入记录，日志、星星、奖励都不变。

#### 6.3 写进存储

- 恢复在拿着写锁的窗口里做（slice-1 6.3）。开始前把 `committer` 冻结，不能同时开始挑战。
- **先查空间**：`navigator.storage.estimate()` 能用时，剩余空间少于要写的原始文字总字节数的 2 倍，提示「这台设备的空间不够了」，不写。
- **分批写**：每个事务最多 500 条。第一个事务写 `meta.restoring = {batch_id, started_at}` 和新身份（如果要换），最后一个事务写导入记录、删掉 `restoring`。写进 `inbox` 的顺序就是 `appendInbox` 的顺序。
- **写到一半失败**（空间不足、页面关掉、浏览器出错）：已经写进去的都是合法的、按顺序的事件，不会坏。下次打开时看到 `restoring` 还在，外壳不进入「可以写」，显示「上次恢复没做完。请再从同一个备份恢复一次」。再恢复一次时，已经写进去的都算重复，剩下的补上，最后删掉标记。
- 全部写完：显示结果（6.2 的 `report`），然后**重新加载页面**，从存储重建一切。
- 恢复成功后，把输入的恢复密钥存进这台设备的 `meta.recoveryKey`（这台设备以后做备份用同一把）。设备上原来就有密钥、而且和输入的不一样时，不覆盖，提示「这台设备上已经有另一把恢复密钥」，备份照样恢复。

#### 6.4 完整性检查

事件规格 4.2 要求导出、恢复时两个方向都查「事件和文字」。v1 还没有私人文字，这一条随竖切片 2（#25）加进 `backup-manifest/2`。v1 只查收据：恢复后，被接收的事件里没有任何收据（本次的、旧的都没有）的，`report` 里列出条数。这只是提示，收据只用来审计，不影响恢复。

### 7. 做备份

`buildBackup(store 里读出的全部, {recoveryKey, now, random, appCommit})` → 文件字节。随机数（`salt`、`nonce_prefix`）由参数传进来，测试时可以固定。

- 在**一个只读事务**里读出全部仓库，保证备份是某一时刻的完整快照。
- 做完以后，**马上在内存里把它从头解一遍**（用同一把密钥，按第 3、4 节全部检查），解出的每一部分和读出来的完全相同，才交给家长下载。不同就提示「备份没做成，请再试一次」，不更新 `lastBackup`。
- 下载：用 `<a download>`；iPad 上浏览器支持 `navigator.share` 带文件时，给一个「存到文件或网盘」按钮。下载开始后写 `meta.lastBackup`。（下载有没有真的存好，页面不知道，所以演练是唯一的确认。）

### 8. 记录指纹

被接收的事件的 `event_id` 按码点排序，每个后面加 `\n`，连起来取 UTF-8 字节的 SHA-256，取前 8 个十六进制字符，显示成两组：`3fa9 c021`。家长页显示「记录 N 条 · 指纹 3fa9 c021」。

- 只看被接收的事件，不看隔离区、收据、身份。所以干净设备恢复以后，指纹和做备份的那台**当时**一样；之后哪台设备上多做一件事，指纹就变。
- 这是给眼睛比的，不是安全措施。

### 9. 可读导出（`curio-export/1`）

文件名 `curio-export-YYYYMMDD-HHMM.jsonl`，UTF-8，不加密，每行以 `\n` 结尾：

1. 第一行：`{"format":"curio-export/1","exported_at":"…","learner_id":"lrn_…","events":N,"note":"每行一条学习事件，格式见 Curio 仓库 docs/specs/events.md。最后一行是前面所有行的 SHA-256。"}`
2. 接下来 N 行：每条**被接收的**事件的原始文字，**原样**，按事件规格 6.2 的排序键排序。原始文字里有 `\r` 或 `\n` 的（外壳自己写的不会有），改成把它解析后紧凑写出的一行，这是导出里唯一会重写的地方。
3. 最后一行：`{"sha256":"<前面所有行的 UTF-8 字节的 SHA-256>"}`。

隔离区、收据不进可读导出（它是事实记录，不是排查工具）。以后有了私人文字，加在事件后面，删掉的写成「已删除」，格式随 `curio-export/2` 定。

### 10. 家长页（够验收就行，画面 Luka 看）

- 入口：星图页底部一行小字「家长」，不显眼（AGENTS.md 产品规则：家长的东西不放首页显眼处）。v1 不设 PIN（见文末问题 3）。
- 页面上：「上次备份：N 天前」（没做过是「还没有备份」，用醒目的颜色）；超过 30 天，入口旁边多一个小圆点。「记录 N 条 · 指纹 xxxx xxxx」。按钮：「做一份备份」「导出成文字」「从备份恢复」「再看一次恢复密钥」。
- 一句提醒：「恢复出来的设备和原来的不会自动同步（以后做了同步才会）。演练完以后，请只在一台设备上继续用。」
- 所有提示用第 3.5 节和第 6 节的话，句子短，不出现技术词。
- 打开数据库失败、读不出记录时，外壳停在错误页（现在就是这样），**不**新建身份、不显示成空白星图。

### 11. 恢复演练

## 不做什么

- **多设备同步、云上副本**：CURIO-008（#11）。恢复出来的设备和原来的各记各的。
- **换恢复密钥**、本机密钥加一层本地口令：CURIO-008 之前写 ADR。
- **私人文字、附件、航线、奖励的备份**：它们出现的那个竖切片里，给 `backup-manifest/2` 加部分，同时加 6.4 的双向检查。附件要按 ADR-006 第 8 条每个单独加密，那时另写。
- **旧打卡工具、原型的数据导入**：原型的记录可以丢；打卡工具的导入在 G3 之后（#8 原文）。
- **自动提醒孩子、自动下载**：只在家长页提醒。
- **PIN**：跟正式的指挥中心一起做。
