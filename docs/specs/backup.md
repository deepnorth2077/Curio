## 问题

现在舰长的作答只存在一台设备的浏览器里。清一次缓存、换一台平板、Safari 自己清理存储，记录就全没了。ADR-006 定了：导出、恢复没做、没演练过之前，设备上的记录只算试玩记录，不能当真。

## 方案

做完以后：

- 家长在「家长」页点「做一份备份」，得到一个加密的备份文件（`.curio`），存到电脑或网盘。第一次做的时候，Curio 先给一把**恢复密钥**（6 个数字），家长抄两份、放两个地方，再完整输入一遍确认。以后的备份都用这一把。
- 另有「导出成文字」：一个人和别的程序都看得懂的文本文件（JSON Lines），不加密，不能用来恢复。
- 在另一台设备、另一个浏览器上点「从备份恢复」，选文件、输入恢复密钥，星星和记录原样回来。再导入一次同一个文件，什么都不变。文件坏了、密钥不对、是别的孩子的，都给明确的提示，原有记录一点不动。
- 家长页显示「上次备份：几天前」和一个**记录指纹**（8 个字符）。两台设备指纹一样，就说明记录一样，Luka 用眼睛就能比。
- Luka 做一次真实的恢复演练，记录写进 `docs/retros/`。演练通过以后，设备上的记录开始算数。以后每季度照同一个手册演练一次（ADR-006 第 5 条）。

## 实现上的决定

### 1. 备份里有什么

v1 备份包含设备存储（第 5 节，版本 2）里**全部**学习数据，一样不挑：

| 部分 | 内容 | 顺序 |
| --- | --- | --- |
| `inbox` | 收件表里的每一条原始文字，**原样**（包括被隔离的原文） | 按到达顺序 |
| `receipt` | 本机的收据（事件规格 5.3） | 按 `event_id` 的码点顺序 |
| `import` | 本机的导入记录（第 5.3 节） | 按 `batch_id` 的码点顺序 |
| `archive` | 以前恢复时从别的备份带过来的收据和导入记录（第 6.2 节） | 按存入顺序 |
| `release` | 这台设备用过的每个内容发布包的 `release.json`，原样 | 按 `release_id` 的码点顺序 |

再加上清单里的身份（`learner_id`、做备份的 `device_id`）。

- **收件表要保留到达顺序**：同一个 `event_id` 先来的被接收、后来的内容不同的进隔离区。恢复到干净设备时按原顺序重新摄入，才能得到一模一样的日志。
- **发布包**：网站上只有最新的一份发布包，旧的拿不到。所以外壳每次读到并核对通过一个发布包，就把它的 `release.json`（约 10 KB，里面有 `source_commit`）存进本机的 `releases`（第 5 节），备份带上它们。事件里的 `content_release` 由此总能找到对应的内容清单，再按 `source_commit` 从仓库拿到内容本身。这满足 ADR-006 表里「被事件引用过的内容发布清单」。
- **不放进备份**的：恢复密钥本身；`nextSeq`（第 6.2 节重新算）；上次备份的时间（每台设备自己的事）；`restoring` 标记。

现在还没有私人文字、附件、航线、奖励（竖切片 2～4 才有）。它们怎么进备份，见第 3.6 节。

### 2. 恢复密钥

#### 2.1 样子

**6 个数字**，由 Curio 随机生成（不让家长自己挑，免得用上生日、门牌这类好猜的数），显示和打印时分成两组：`482 105`。

- 生成：用 `crypto.getRandomValues` 取一个 32 位无符号整数 `x`；`x` ≥ 4294000000（2^32 以下最大的 10^6 的倍数）就丢掉重取，否则取 `x mod 1000000`，左边补零到 6 位。这样每个 6 位数的机会一样。不用 `Math.random`。
- 存和比较都用这 6 个 ASCII 数字组成的字符串。
- 公开的测试密钥是 `123456`，样例文件和黄金向量都用它。真实家庭的密钥由程序随机生成，碰巧是它也没关系。

**Luka 2026-11-13 定：用 6 位数字。**这是知道风险以后的选择：恢复密钥只保护备份文件本身，拿到文件的人可以在自己的电脑上一个个试，不会被锁住。第 3.2 节故意让每试一次都慢（在 iPad 上大约 1 秒），但用一块显卡试完全部 100 万个数，大约只要几分钟。所以**备份文件的安全主要靠家长自己保管好**：存在自己的电脑或自己的网盘里，不发给别人、不放进公开的分享链接。家长页做备份的地方写一句：「备份文件请存在只有你能打开的地方。」以后觉得不够，可以出 `curio-backup/2` 换更长的密钥，旧备份照样用旧密钥打开。

#### 2.2 输入时怎么规整

按顺序做，第一处不对就停在那一处的提示：

1. 做 Unicode NFKC 规整（全角数字变半角，全角空格变成 U+0020，全角横线变成 `-`）。
2. 去掉这些字符（列表是封闭的，JS 和 Python 照这张表做，不用各自语言的「空白」定义）：空白 U+0009～U+000D、U+0020、U+00A0、U+3000；横线 `-`（U+002D）、U+2010、U+2011、U+2012、U+2013、U+2014、U+2015、U+2212、U+30FC。
3. 剩下的字符有不是 `0`～`9` 的 →「恢复密钥只有数字」。
4. 不是正好 6 个 →「恢复密钥是 6 个数字」。

两把密钥「一样」，指规整以后的 6 个数字相同。6 位数字没有校验位：输错一个数，会在读文件时报「恢复密钥不对」（3.8 第 5 步）。

#### 2.3 存在哪里、什么时候存

它是这个家的备份密钥，一家只应该有**一把**。ADR-010 第 7 条原来打算让云上副本也用「家庭恢复密钥」作主密钥；6 位数字太短，**CURIO-008 不直接拿它当云上副本的主密钥**，云上副本用什么密钥在 CURIO-008 之前另写增补重新定（ADR-010 增补 1 已写明）。

v1 里设备把这 6 个数字存在本机 `meta.recoveryKey`（第 5 节）：`{digits, confirmed_at}`。能摸到这台设备的人本来就能看到这台设备上的记录，这不增加多少风险；但他也能用这把密钥打开这家所有的旧备份文件。换密钥的办法以后要用时再写 ADR。

规则：

- **只在拿着写锁的窗口里**生成、确认、覆盖密钥（slice-1 6.3）。只读窗口点这些按钮，提示「请在正在用的那个窗口里做」。
- **干净的设备**（第 6.1 节）不能生成密钥：那里「做一份备份」按钮不出现，页面以「从备份恢复」为主。
- **先存后显示**：点「做一份备份」时，本机还没有密钥，就先在一个事务里生成并写入 `{digits, confirmed_at: null}`（已经有了就中止，像 `store.init`），然后才显示。中途刷新、关掉，再进来显示的还是这一把，不重新生成。
- **确认**：家长点「抄好了」以后，要把 6 个数字完整输入一遍，规整后和本机的一样，才写 `confirmed_at`，然后才开始做第一份备份。不一样：提示「和刚才的不一样，请对照纸上再看看」，可以回去再看。`confirmed_at` 为空时不能做备份。
- **恢复开始时**（第 6.3 节的 `restoreBegin`，和标记同一个事务）按下面写。这时 `key_check` 已经通过，证明家长手里有这把；放在开始而不是结束，是为了恢复中途断了、家长点「不恢复了」以后，本机也已经有这把，不会再生成第二把：
  - 本机没有密钥，或者有但 `confirmed_at` 为空 → 换成输入的这把，`confirmed_at` 写成恢复的时间（能打开备份，就证明家长手里有这把）。
  - 本机已经有确认过的密钥，和输入的一样 → 不变。
  - 本机已经有确认过的、**不一样**的密钥 → 备份照样恢复，本机的不覆盖；家长页一直显示「这台设备用的是另一把恢复密钥，两把都要留着」。v1 不能换密钥，这种情况只在一家人先在两台设备上各自做了密钥时才会出现。
- 以后在家长页可以「再看一次恢复密钥」（只在写锁窗口里）。
- v1 **不能换密钥**。

### 3. 备份文件格式（`curio-backup/1`）

#### 3.1 文件的样子

文件名：`curio-backup-YYYYMMDD-HHMM.curio`（本地时间 UTC+8，和事件规格第 1 节一致）。文件是二进制，依次是：

1. **第一行**：ASCII 的 `CURIO-BACKUP/1`，后跟一个 `\n`（0x0A）。
2. **第二行**：**文件头**，一个 JSON 对象，UTF-8，按第 3.7 节的写法，不含结尾的 `\n` 最多 4096 字节，后跟一个 `\n`。
3. 后面全部是**密文块**，一个接一个，中间没有分隔。

文件头的字段**按这个顺序**写，不能有别的字段：

```json
{"format":"curio-backup/1","created_at":"2026-11-13T10:30:00.000Z","kdf":"pbkdf2-sha256+hkdf-sha256","iterations":600000,"salt":"…","key_check":"…","cipher":"aes-256-gcm","nonce_prefix":"…","chunk_size":1048576,"compression":"gzip"}
```

| 字段 | 说明 |
| --- | --- |
| `format` | 固定 `curio-backup/1` |
| `created_at` | 做备份的 UTC 时间，格式同事件规格第 1 节 |
| `kdf` | 固定 `pbkdf2-sha256+hkdf-sha256` |
| `iterations` | PBKDF2 的轮数。**写**的程序 v1 固定写 600000；**读**的程序接受 100000 到 10000000 之间的整数。黄金向量也用 600000（实测一次约 0.1 秒，不慢） |
| `salt` | 每个文件新生成的 16 个随机字节，标准 Base64（带 `=` 补位） |
| `key_check` | 16 字节，标准 Base64，见 3.2 |
| `cipher` | 固定 `aes-256-gcm` |
| `nonce_prefix` | 每个文件新生成的 7 个随机字节，标准 Base64 |
| `chunk_size` | 明文块的字节数。**写**的程序 v1 固定写 1048576（1 MiB）；**读**的程序接受 64 到 16777216 之间的 2 的幂，按文件头的值切块（样例文件和黄金向量用 64） |
| `compression` | `gzip` 或 `none`。写的时候浏览器有 `CompressionStream` 就用 `gzip`；读的程序两种都必须支持 |

**读文件头**，两条都要满足，否则「文件坏了」：

- **值对**：`format`、`kdf`、`cipher` 等于上表的固定值；`created_at` 符合事件规格第 1 节的时间格式；`iterations` 是 JSON 整数、在范围内；`salt`、`key_check` 是标准 Base64，解码后正好 16 字节，`nonce_prefix` 解码后正好 7 字节；`chunk_size` 是 JSON 整数、在范围内、是 2 的幂；`compression` 是 `gzip` 或 `none`。
- **写法对**：解析出来以后，按上表的顺序和第 3.7 节的写法重新写一遍，必须和原来那一行**逐字节相同**。这一条同时挡住重复的键、多余的空格、别的转义写法、不规范的 Base64（解码后再编码要和原文相同）。

**第一行**必须正好是 `CURIO-BACKUP/`、一个不带前导零的十进制正整数、`\n`。数字不是 1 →「请先更新 Curio」；是 1 而 `format` 不是 `curio-backup/1` →「文件坏了」。读到第二行的第 4097 个字节还没有 `\n` →「文件坏了」。

文件头不加密，里面没有孩子的任何信息。

#### 3.2 密钥和加密

- **先放慢**：PBKDF2-HMAC-SHA256，口令是恢复密钥的 6 个 ASCII 数字（6 个字节），`salt` 是文件头里的 16 个字节，轮数是 `iterations`，输出 32 字节，叫它 `prk`。这一步故意慢（600000 轮在 iPad 上大约 1 秒），让一个个试密钥变慢；做一次备份、恢复一次各算一次。浏览器用 Web Crypto 的 `PBKDF2`，Python 用 `hashlib.pbkdf2_hmac`。
- **再派生**：HKDF-SHA256，输入是 `prk`，`salt` 为空，派生两样东西：
  - 加密密钥：`info` = ASCII `curio-backup/1 enc`，32 字节，作 AES-256-GCM 的密钥；
  - 密钥检查值：`info` = ASCII `curio-backup/1 check`，16 字节，写进文件头的 `key_check`。
- **读的时候先比 `key_check`**，不一样就是「恢复密钥不对」，不去解密文。这样「密钥不对」和「文件坏了」能分开说。
- **附加数据（AAD）** = 文件前两行的原始字节，不含第二行结尾的 `\n`（也就是 `CURIO-BACKUP/1\n` 加上文件头那一行）。改动这两行的任何一个字节，所有块都解不开。
- **明文流**：把第 4 节的明文文档（UTF-8 字节）按 `compression` 处理（`none` 就是原样），得到一串字节，从头切成每块 `chunk_size` 字节；最后一块可以短，但不能是 0 字节。
- **每一块**单独用 AES-256-GCM 加密：
  - 随机数（12 字节）= `nonce_prefix`（7 字节）+ 块序号（4 字节，大端无符号，从 0 开始）+ 末块标记（1 字节：最后一块是 `0x01`，其他是 `0x00`）；
  - 密文块 = 密文 + 16 字节认证标签。所以除最后一块外，每个密文块都正好是 `chunk_size + 16` 字节。
- **读的时候认末块**：从第三行起，每次读 `chunk_size + 16` 字节；读满一整块以后，看后面还有没有字节，没有了它就是末块（用 `0x01` 解），还有就不是（用 `0x00` 解）。最后剩下不足一整块的，就是末块。剩下 0 字节、或末块不足 17 字节 →「文件坏了」。文件被截断在块的边界上时，最后一块会用 `0x01` 去解一个当初用 `0x00` 加密的块，必然失败，所以截断一定能发现。
- 块的总数不超过 2^32 − 1。

#### 3.3 gzip 的约定

- **写**：恰好一个 gzip 成员（RFC 1952），`FLG` = 0（不带文件名、注释、额外字段），`MTIME` = 0；压缩级别、`XFL`、`OS` 不限定。所以 `gzip` 模式**不要求**逐字节相同，逐字节的黄金向量只用 `none`。
- **读**：接受一个或多个首尾相接的成员（浏览器的 `DecompressionStream("gzip")` 本来就这样，也没法知道第一个成员在哪里结束）。每个成员的 CRC32 和 ISIZE 必须对；最后一个成员结束后**不能再有任何字节**（包括零字节），一个成员结束后紧接着的字节不是 gzip 的开头 `1F 8B` 也算多余的字节。浏览器用 `DecompressionStream("gzip")`，它对这些情况报错。Python 不能直接用 `gzip.decompress`（它悄悄接受末尾的零），要循环：`zlib.decompressobj(16 + zlib.MAX_WBITS)` 解一个成员，检查 `eof` 为真，`unused_data` 为空就结束，不为空就必须以 `1F 8B` 开头，用它接着解下一个成员。（写的程序只写一个成员；读的程序宽一点不要紧，认证加密已经保证内容没被改过。）
- **恢复时**，解压后的大小超过 1 GiB，或超过 `navigator.storage.estimate()` 给出的剩余空间，就停下来「备份太大，这台设备放不下」。做完备份马上读一遍的自检（第 7 节）只用 1 GiB 这一条：做备份本身不需要那么多空间。

#### 3.4 为什么这样做

- **分块**：不受单次加密的大小限制，读的时候能边解密边解压，不必一次分配一整块大内存。（v1 的恢复计划要先拿到整份明文才做检查，几十 MB 的事件没问题。以后加附件到几百 MB，很可能要 `curio-backup/2`：每个附件单独一段密文、可以跳着读。不要以为只升清单版本就够。）
- 末块标记和块序号放进随机数，是成熟的「分块认证加密」做法（STREAM），防止块被调换、被截断。
- 每个文件新的 `salt` 和 `nonce_prefix`：同一把恢复密钥做几百个备份，每个文件的加密密钥都不同，随机数永不重复。
- 不在文件头里放「这是哪把密钥」的编号：6 位数字的编号不经过放慢的那一步就能被一下子试出来，等于把密钥写在文件上。
- HKDF 的 `info` 带着用途（`curio-backup/1 enc`、`curio-backup/1 check`），以后要派生别的东西换一个 `info` 就行，不会冲突。
- 只用浏览器自带的 Web Crypto（PBKDF2、HKDF、AES-GCM）和 `CompressionStream`，不引入依赖（ADR-008）。Python 的标准库加 `cryptography` 也能读，十年后不靠 Curio 也有办法解开。

#### 3.5 版本

- 第一行的 `/1`、文件头的 `format` 是**文件格式**的版本（加密和分块怎么做）。
- 明文清单的 `schema` 是**内容**的版本（`backup-manifest/1`，第 4 节）。
- 读的程序遇到不认识的版本，提示「这个备份是新版本的 Curio 做的，请先更新 Curio」，什么都不写。
- **每一个版本**都在 `tests/fixtures/backup/` 里永久留样例文件（`none` 和 `gzip` 各一个），用第 2.1 节的公开测试密钥。以后的读程序必须一直能读它们（ADR-006 第 4 条）。

#### 3.6 以后加私人文字、附件时（现在就定的门槛）

- 私人文字、附件怎么进备份（明文放进清单、只受恢复密钥保护，还是按 ADR-010 第 7 条每段单独用数据密钥加密、数据密钥另存在密钥库），**在竖切片 2（#25）之前写 ADR 决定**。两种做法对「删掉的文字在旧备份里还能不能读出来」的答案不同，带文字的备份一旦散出去就改不回来。**要先摆在前面的一点**：恢复密钥只有 6 位数字，「明文进清单」等于拿到备份文件的人几分钟就能读到孩子写的文字；真要选这种做法，先换更长的密钥。没有这个决定，不加 `backup-manifest/2`。
- `backup-manifest/2` 里文字类的部分一律放在 `inbox` 之后。恢复时先摄入全部事件，再处理文字，已有 `text.erased` 的文字直接丢弃（事件规格 4.2 第 2 条）；拿不到比这份备份更新的删除事件时，提示「可能恢复出已删除的文字」。同时加上事件规格 4.2 的双向完整性检查。
- **竖切片 2 和 `backup-manifest/2` 同时上线，不能先上竖切片 2**。否则设备上会有备份里没有的文字。

#### 3.7 本规格里 JSON 行的写法

文件头、清单、记录行、`end` 行、导入记录、可读导出的首尾两行，**写**的程序都按这个写法：

- 键按本规格表格里的顺序写（收据按 `event_id, recorded_at, source, batch_id, clock_skew_ms`，没有的字段不写）。
- 不加任何空格。
- 字符串：非 ASCII 字符原样写成 UTF-8，不转义；只转义 `"`、`\` 和 U+0000～U+001F：`\b \f \n \r \t` 用短写法，其余写成 `\u00xx`（小写十六进制）。这就是 `JSON.stringify` 的行为；Python 写成 `json.dumps(v, separators=(",", ":"), ensure_ascii=False)`。
- 这些行里的数都是整数（以后同步来的收据里 `clock_skew_ms` 可以是负数），写成十进制，可以有负号，不带小数点、不带指数。
- 字符串里不会有单独的 UTF-16 代理项（外壳写的原文、从 UTF-8 文件读出的原文都不会有）。遇到就是写的程序出错，做备份时停下，提示「备份没做成」。

**读**的时候，除了文件头（3.1 要求逐字节相同），只要求字段对：字段齐全、没有多余的、值合格；**不查**键的顺序和写法（`end` 行的校验和已经覆盖原始字节）。`raw` 里的事件原文是一个字符串，按上面的规则写进记录行，原文本身不受影响。

**规范 JSON**（第 6.2 节的比较键用）：第 3.7 节的写法，但对象的键按码点排序，数值是整数的一律写成整数（`5.0`、`5e0` 都写成 `5`）。这样同一个值在 JS 和 Python 里写出来一样。

#### 3.8 读的顺序和给家长的话

读一个备份并决定能不能恢复，**按这个顺序**检查，第一处不对就停，给出那一行的话，存储一点不动。两个实现对同一个坏文件必须停在同一行。

| 步 | 检查 | 不对时给家长的话 |
| --- | --- | --- |
| 1 | 恢复密钥的输入（第 2.2 节，按那里的顺序） | 第 2.2 节的两句之一 |
| 2 | 第一行是 `CURIO-BACKUP/` 加数字加 `\n`（3.1） | 这不是 Curio 的备份文件 |
| 3 | 第一行的数字是 1 | 这个备份是新版本的 Curio 做的，请先更新 Curio |
| 4 | 文件头：长度、是合法 JSON 对象、值对、写法对（3.1） | 备份文件坏了 |
| 5 | `key_check`（3.2） | 恢复密钥不对。请对照纸上的密钥再输一次 |
| 6 | 解开**全部**密文块（3.2），全部解开以后才往下 | 备份文件坏了，或者不完整。换一个备份文件试试 |
| 7 | `compression` 是 `gzip` 时解压（3.3） | 备份文件坏了，或者不完整。换一个备份文件试试 |
| 8 | 解压后的大小（3.3，只在恢复时） | 备份太大，这台设备放不下 |
| 9 | 严格 UTF-8、不以 BOM 开头（第 4 节） | 备份文件坏了 |
| 10 | 第一行能解析，`schema` 是认识的版本 | 这个备份是新版本的 Curio 做的，请先更新 Curio |
| 11 | 第 4 节的其余规则 | 备份文件坏了 |
| 12 | 能不能恢复到这台设备（6.1，按表的顺序） | 6.1 表里的话 |
| 13 | 空间够不够（6.3 第 2 步） | 这台设备的空间不够了 |

第 2 步「不是 Curio 的备份文件」也用在文件不到 15 字节、或前 13 个字节不是 `CURIO-BACKUP/` 的时候。

### 4. 明文文档（`backup-manifest/1`）

解密、解压以后是一个 JSON Lines 文档：严格的 UTF-8，**不能以 BOM 开头**，每行一个 JSON 对象，每行以 `\n` 结尾（包括最后一行），没有空行。浏览器用 `new TextDecoder("utf-8", {fatal: true, ignoreBOM: true})` 解码，再检查第一个字符不是 U+FEFF；Python 用 `bytes.decode("utf-8")`（严格）。

**第一行是清单**，字段按顺序：

| 字段 | 说明 |
| --- | --- |
| `schema` | 固定 `backup-manifest/1` |
| `created_at` | 必须和文件头的 `created_at` 相同 |
| `learner_id` | `lrn_<ULID>`（事件规格第 1 节的格式） |
| `device_id` | 做备份的设备，`dev_<ULID>` |
| `app_commit` | 做备份时外壳的提交号，7～40 个小写十六进制。格式要查，值不用 |
| `counts` | `{"inbox":n,"receipt":n,"import":n,"archive":n,"release":n}`，正好这五个键、按这个顺序，值是非负整数 |

**中间是记录**，按 `inbox`、`receipt`、`import`、`archive`、`release` 的顺序，每部分内部按第 1 节的顺序。每行正好这两个字段：

| 行 | 样子 | 检查 |
| --- | --- | --- |
| 收件 | `{"t":"inbox","raw":"…"}` | `raw` 是字符串（内容不在这里查，恢复时交给日志判断） |
| 收据 | `{"t":"receipt","v":{…}}` | `v` 符合 `schemas/ingest-receipt.schema.json` |
| 导入记录 | `{"t":"import","v":{…}}` | `v` 符合第 5.3 节 |
| 带过来的 | `{"t":"archive","v":{"kind":"receipt","v":{…}}}` 或 `kind` 为 `import` | 里面的 `v` 按 `kind` 检查，同上 |
| 发布包 | `{"t":"release","raw":"…"}` | `raw` 是字符串，解析出来是对象；`release_id` 是 `rel_<64 位小写十六进制>`，而且等于 `"rel_"` 加上它的 `content_hash`；按 `release_id` 排序、不重复 |

**最后一行**：`{"t":"end","lines":n,"sha256":"<64 位小写十六进制>"}`

- `lines` 必须等于 1 加上 `counts` 各项之和；`sha256` 是 `end` 之前所有行（含每行的 `\n`）**解压后的原始字节**的 SHA-256，不先解码再编码。认证加密已经保证文件没被改过，这个校验和防的是**写的程序自己出错**（漏写、写错顺序）。
- 读的时候全部检查（`counts` 的键要正好是那五个，但不查顺序，见 3.7）：每一行都是 JSON 对象、字段正好是表里的；`t` 只能是这几种，部分的顺序不能乱；每部分的行数和 `counts` 一致；`lines`、`sha256` 对；`end` 后面不能再有东西。任何一条不对，整个文件按「文件坏了」处理。

`app/store.js` 的数据库从版本 1 升到 2。**只加东西，不改旧仓库**：`onupgradeneeded` 按 `oldVersion` 分支：0 → 建全部仓库；1 → 只建新加的三个（这就是原则 7 的迁移，要有测试，见测试接缝）。

| 仓库 | 主键 | 存什么 | 新加？ |
| --- | --- | --- | --- |
| `inbox` | 自增 | 原始文字（slice-1 6.2） | |
| `receipts` | `event_id` | 本机的收据 | |

- 6b 上线之前设备上的事件引用的发布包没有存下来。那些是试玩记录，可以接受。
- **旧窗口让路**：现在的 `onversionchange` 只是 `db.close()`。改成按「失去写锁」处理：冻结 `committer`、进入只读、提示「请刷新页面」（slice-1 6.3）。
- **回退**：演示页回退到旧提交时，旧代码用版本 1 打开版本 2 的数据库会得到 `VersionError`，停在错误页，数据不丢。这一点写进 PR。

#### 5.2 存储的接口（版本 2）

在 slice-1 6.2 的 `loadAll`、`init`、`putInbox`、`commit`、`close` 之外（这些不变，`loadAll` 额外返回 `restoring`），新加：

| 方法 | 做什么 | 事务 |
| --- | --- | --- |
| `snapshot()` | 读出全部仓库：`{identity, nextSeq, inbox, receipts, imports, archive, releases, recoveryKey, restoring}` | 一个只读事务 |
| `putRelease(raw, release_id)` | 没有才写 | 一个 |
| `createRecoveryKey(digits)` | 写 `{digits, confirmed_at: null}`；已经有就中止 | 一个 |
| `confirmRecoveryKey(at)` | 写 `confirmed_at`；没有密钥就中止 | 一个 |
| `setLastBackup({at, file_name})` | | 一个 |
| `restoreBegin(marker, identity?, recoveryKey?)` | 没有 `restoring` 时：写 `restoring`；要换身份时一起写身份；需要时按第 2.3 节写恢复密钥。已经有 `restoring` 时：**不重写**，只核对 `marker` 的 `file_created_at`、`file_device_id`、`file_salt`、`file_learner_id` 和存着的一样，不一样就中止 | 一个 |
| `restoreBatch(items, ownSeqMax)` | `items` 按顺序：`{inbox: raw, receipt?}`、`{archive: …}`、`{release: raw}`。一条原始文字和它的收据**在同一个事务里**。`ownSeqMax` 是这一批里本机 `device_id` 的**被接收**事件的最大 `device_seq`（没有就是 0），同一个事务里把 `meta.nextSeq` 推进到 max(当前值, `ownSeqMax` + 1) | 一个，最多 500 项 |
| `restoreEnd(record)` | 写导入记录，删掉 `restoring` | 一个 |
| `restoreAbandon(record)` | 写 `partial: true` 的导入记录，删掉 `restoring`（第 6.3 节） | 一个 |

`nextSeq` 随每一批推进、恢复密钥在开始时就写，所以任何时刻断掉，存储里的 `nextSeq` 都不会落后，本机也不会没有密钥。

每个写方法只用一个事务，只在 `complete` 以后 resolve，`abort`、`error` 时 reject（同 slice-1 6.2）。

#### 5.3 导入记录（`import-record/1`）

```json
{"schema":"import-record/1","batch_id":"imp_…","imported_at":"…","source":"backup","partial":false,"file_created_at":"…","file_device_id":"dev_…","file_salt":"<文件头的 salt>","accepted":118,"duplicate":0,"not_yet_known":0,"quarantined_new":2,"quarantined_skipped":0,"archived":120,"releases":1}
```

字段按这个顺序，计数都是非负整数，意思见 6.2。写进 `schemas/import-record.schema.json`。

`source: backup` 的批次**不能**用 `import.voided` 作废：恢复的事件信封里没有 `import_batch`（原样保留），作废对它们不起作用。恢复错了孩子的情况由 6.1 拒绝，不靠作废。

### 6. 恢复

#### 6.1 能不能恢复到这台设备

外壳一打开就会建身份（slice-1 6.3），所以干净的设备也已经有一个 `learner_id`。**干净**的意思是：`inbox`、`receipts`、`imports`、`archive` 都是空的，而且没有 `restoring`。

| 这台设备 | 备份是 | 怎么办 |
| --- | --- | --- |
| 干净 | 任何孩子 | 可以恢复。身份换成备份的 `learner_id`，`device_id` 不变 |
| 不干净，`learner_id` 和备份一样 | 同一个孩子 | 可以恢复：把备份**合并**进来（6.2） |
| 不干净，`learner_id` 不一样 | 另一个孩子 | 不恢复。提示「这个备份是另一个孩子的，这台设备上已经有记录了」 |
| 有 `restoring`，而备份和标记里的不是同一个文件（`file_created_at`、`file_device_id`、`file_salt`、`file_learner_id` 有一个不同） | 任何 | 不恢复。提示「上次恢复的是另一个备份，请先用它恢复完，或者点『不恢复了』」 |

判断顺序：先看有没有 `restoring`（第 4 行），再看干净不干净（第 1～3 行）。有 `restoring` 而且是同一个文件时，照第 2 行合并（这时身份已经是备份的了），**沿用标记里的 `batch_id`**，这样第一次写进去的收据和最后的导入记录指向同一个批次。

**为什么干净设备上换身份是安全的**：没有任何事件带着旧的 `learner_id`；`device_id` 和 `nextSeq` 不变；`openSession` 读到已有身份就不再 `init`，补写放弃只看本机 `device_id`，都不受影响。

恢复出来的设备**用自己的 `device_id`** 继续记录，不冒用备份里那台设备的 ID：原来的设备可能还在用，两台用同一个 ID 就会撞序号。

#### 6.2 恢复计划（纯函数）

`planRestore(existing, backup, {batchId, now})`：不碰存储、时间和随机数，在 Node 里能直接测。`existing.restoring` 有值时忽略参数 `batchId`，用标记里的（6.1）。

- `existing`：`store.snapshot()` 的结果；
- `backup`：第 4 节读出来的清单和各部分，加上文件头的 `salt`、`created_at`；
- 返回 `{ok: false, reason}`，或者 `{ok: true, identity, items, nextSeq, record, report}`。`items` 是给 `restoreBatch` 的全部项，按顺序。

步骤：

1. 按 6.1 判断，不能恢复就返回 `ok: false`。
2. 用 `existing.inbox` 按顺序 `ingest` 建一个日志（和外壳启动时一样）。把 `existing.inbox` 的原文放进一个集合 `seenRaw`。
3. 备份的 `inbox` 按顺序，每一条：
   - `log.check(raw)` 是 `accepted`：`ingest`；放进 `items`，带收据 `{event_id, recorded_at: now, source: "import", batch_id}`，并标上它的 `device_id`、`device_seq`（给第 6 步和 `restoreBatch` 的 `ownSeqMax` 用）；`accepted` 加一。
   - `duplicate`：什么都不放；`duplicate` 加一。
   - `quarantined`：原文已经在 `seenRaw` 里（逐字节相同）→ 跳过，`quarantined_skipped` 加一。否则 `ingest`、放进 `items`（没有收据）、加进 `seenRaw`，再按下面的规则二选一计数。
   - **「这一版还不认识的」**（`not_yet_known`）：`planRestore` 自己解析原文判断，不依赖 `log.check` 的 `detail`。原因是「不合格」（`invalid`），原文能解析成 JSON 对象，`schema` 是以 `event/` 开头的字符串，而且满足下面任一条：`schema` 不是 `event/2`；`verb` 是字符串，但不在本版内核接收的动词表里（`kernel/js/validate.js` 导出的那张，现在是竖切片 1 的 6 个）。它们在更新 Curio 以后重放收件表时会自动算上。其他的（包括认识的动词多了一个字段）记 `quarantined_new`。
4. 「带过来的」：备份的 `receipt`（当作 `kind: receipt`）、`import`（当作 `kind: import`）、`archive` 三部分按顺序，每一条算一个**比较键**：`kind` + `\n` + `v` 的规范 JSON（第 3.7 节末尾）。这个键和本机 `receipts`（`kind: receipt`）、`imports`（`kind: import`）、`archive` 里每一条的比较键都放进一个集合；已经在集合里的跳过，不在的放进 `items`、加进集合，`archived` 加一。（和「语义相同」的结果一样，但是线性的，而且 JS 和 Python 算出来一样。用自己的备份恢复自己时，全部跳过。）
5. 发布包：备份的每个 `release`，本机 `releases` 里没有这个 `release_id` 的，放进 `items`，`releases` 加一。
6. **`nextSeq`** = max(本机的 `nextSeq`，合并后日志里本机 `device_id` 的**被接收**事件的最大 `device_seq` + 1；隔离区里的不占序号)。正常情况下就是本机原来的值；但如果这台设备的网页存储被回滚过（例如 iPad 整机从旧备份恢复），备份里会有本机以前的、序号更大的事件，不这样做，下一条本机事件就会撞号进隔离区，以后每一条都一样，写入永远卡住。存储里的 `nextSeq` 由 `restoreBatch` 每批推进（5.2），所以中途断了也不会落后。这种情况 `report` 里提一句「备份里有这台设备以前的记录」。
7. `identity`：6.1 第一行时是新身份，其他时候是原来的。`record` 是这次的导入记录。`report` 给家长看：接收几条、重复几条、「这一版还不认识的」几条、新进隔离区几条、恢复后的记录指纹（第 8 节），以及被接收的事件里一条收据都没有的条数（只是提示，收据只用来审计）。

同一个文件导入第二次：第 3 步全是 `duplicate` 或 `quarantined_skipped`，第 4、5 步全部跳过，`items` 是空的，`nextSeq` 不变。只多一条导入记录，日志、星星、奖励都不变。

#### 6.3 写进存储

1. 家长选文件、输密钥 → 读文件（第 3、4 节）→ `store.snapshot()` → `planRestore`。任何一步不行就显示提示，这个窗口照常能用，存储一点没动。
2. **先查空间**：`navigator.storage.estimate()` 能用时，剩余空间少于 `items` 里全部原文的 UTF-8 字节数的 3 倍，提示「这台设备的空间不够了」，不写。
3. 显示要恢复的内容（几条、哪天做的备份），家长点「恢复」以后，**这时**才冻结 `committer`，开始写：
   - `restoreBegin({batch_id, started_at, file_created_at, file_device_id, file_salt, file_learner_id}, 新身份?, 恢复密钥?)`（恢复密钥按第 2.3 节决定写不写）；
   - `items` 按顺序，每 500 项一次 `restoreBatch`，带上这一批的 `ownSeqMax`；
   - `restoreEnd(record)`。
   - **每个事务之前**检查一次是否已经失去写锁（照 `session.js` 的 `guardDeps` 做法）。失锁就停，留着标记。
4. 不管成功、失败还是失锁，结束后显示结果，然后**重新加载页面**，从存储重建一切。

**写到一半断了**（空间不足、页面关掉、浏览器出错、失锁）：已经写进去的都是合法的、按顺序的原文，原文和收据成对，不会坏。下次打开时，`openSession` 照常做第 1～3 步（建身份、重放、补写本机的放弃），只是看到 `restoring` 还在，外壳**不进入「可以写」**，显示「上次恢复没做完」和两个按钮：

- 「再恢复一次」：选**同一个**备份（别的文件按 6.1 第 4 行被拒）。沿用标记里的 `batch_id`；已经写进去的都算重复，剩下的补上，最后写导入记录、删掉标记。
- 「不恢复了，就用现在这些」：`restoreAbandon`，写一条 `partial: true` 的导入记录，删掉标记，设备照常能用。删标记是安全的，因为写进去的都是合法事件。

### 7. 做备份

`buildBackup(snapshot, {recoveryKey, now, random, appCommit, compression})` → 文件字节。随机数（`salt`、`nonce_prefix`）由参数传进来，测试时可以固定。

- `store.snapshot()` 在**一个只读事务**里读出全部，保证备份是某一时刻的完整快照。只读窗口也能做备份，但本机还没有确认过的密钥时，提示「请在正在用的那个窗口里做」。
- 做完以后，**马上在内存里把它从头读一遍**（按第 3、4 节全部检查；可以复用刚派生出的加密密钥，不必再算一次 PBKDF2，但 `key_check` 要照样比），读出的每一部分和快照完全相同，才交给家长下载。不同就提示「备份没做成，请再试一次」，不更新 `lastBackup`。
- 下载：用 `<a download>`；浏览器支持 `navigator.share` 带文件时，另给一个「存到文件或网盘」按钮。下载开始后写 `lastBackup`（只在写锁窗口里写）。下载有没有真的存好，页面不知道，所以演练是唯一的确认。

### 8. 记录指纹

被接收的事件的 `event_id` 按码点排序，每个后面加 `\n`，连起来取 UTF-8 字节的 SHA-256，取前 8 个十六进制字符，显示成两组：`3fa9 c021`。家长页显示「记录 N 条 · 指纹 3fa9 c021」。

- 只看被接收的事件，不看隔离区、收据、身份。所以干净设备恢复以后，指纹和做备份的那台**当时**一样；之后哪台设备上多做一件事，指纹就变。
- 0 条事件时是 `e3b0 c442`（空串的 SHA-256），家长页显示「还没有记录」，不显示指纹。
- 这是给眼睛比的，不是安全措施。

### 9. 可读导出（`curio-export/1`）

文件名 `curio-export-YYYYMMDD-HHMM.jsonl`，UTF-8，不带 BOM，不加密，每行以 `\n` 结尾，首尾两行按第 3.7 节写：

1. 第一行，字段按顺序：`{"format":"curio-export/1","exported_at":"…","learner_id":"lrn_…","events":N,"note":"每行一条学习事件，格式见 Curio 仓库 docs/specs/events.md。最后一行是前面所有行的 SHA-256。"}`
2. 接下来 N 行：每条**被接收的**事件的原始文字，按事件规格 6.2 的排序键排序。原始文字里的每个 `\r`、`\n` 换成一个空格（合法 JSON 的字符串里不可能有原样的换行，它们只会在记号之间的空白里，换掉不改变意思），其余原样，不解析、不重写。
3. 最后一行：`{"sha256":"<前面所有行的 UTF-8 字节的 SHA-256>"}`。

隔离区、收据不进可读导出（它是事实记录，不是排查工具）。以后有了私人文字，格式随 `curio-export/2` 定。

### 11. 顺带修改：`first` 和 `retry`

外壳判断 `attempt.started` 的 `mode` 时，现在只看「这台设备上」有没有完成过这个活动（slice-1 6.3「开始一次挑战」）。恢复到新设备以后，舰长再做原来做过的挑战会被记成 `first`，这是存下来的事实，以后分析「第一次就答对」会被它误导。6b 里改成：这个孩子在**任何设备**上有一次合法、已完成的这个活动的尝试（掌握度投影的定义，slice-1 第 4 节；被判不一致的、被放弃的不算）就是 `retry`，否则 `first`。并修订 slice-1 6.3 的这一句。这一改动在 6b 里、也就是演练之前上线，所以所有算数的记录都是同一种含义。

## 不做什么

- **多设备同步、云上副本**：CURIO-008（#11）。恢复出来的设备和原来的各记各的。
- **换恢复密钥**、更长的密钥：要用时再写 ADR，出 `curio-backup/2`（第 2.1 节）。
- **云上副本用什么密钥**：CURIO-008 的 ADR 重新定，不直接用这 6 个数字（第 2.3 节）。
- **私人文字、附件、航线、奖励的备份**：按第 3.6 节的门槛，随它们所在的竖切片做。附件很可能要 `curio-backup/2`。
- **删除先应用、双向完整性检查**（#8 验收标准第 3、4 条）：v1 没有私人文字，随 `backup-manifest/2` 做（第 3.6 节）。#8 关闭前另开 issue 跟踪。
- **旧打卡工具、原型的数据导入**：原型的记录可以丢；打卡工具的导入在 G3 之后（#8 原文）。
- **自动提醒孩子、自动下载**：只在家长页提醒。
- **PIN**：跟正式的指挥中心一起做。

## 第 2～4 稿改了什么

### 第 4 稿（Luka 的拍板）

- 恢复密钥改成 6 位随机数字（第 2.1、2.2 节）；派生先过 PBKDF2-SHA256（文件头加 `iterations`，`kdf` 改名），再 HKDF（3.2）；去掉文件头的 `key_id`（6 位数字的编号能被直接试出来）；「同一个文件」改用文件头的 `salt` 识别（`file_salt`）；云上副本不直接用这把密钥（2.3）。改动经独立子 agent 复审，见 `docs/reviews/pr-129.md` 第 3 轮；按 R41～R46 补了 ADR-010 增补 1、文字备份的风险、轮数下限 100000 且向量用 600000、自检复用密钥、找回脚本。

### 第 3 稿（第 2 轮 R26～R40）

- **阻塞**：加回「读的顺序和给家长的话」，一张有序的表，两个实现对同一个坏文件停在同一步（R26，3.8）。
- **应改**：`nextSeq` 随每一批推进（R27）；再恢复一次沿用标记里的 `batch_id`，只能用同一个文件（R28）；比较键用规范 JSON，整数值一律写成整数（R29）；`not_yet_known` 写成能机械判断的规则（R30）；文件头字段的值怎么查（R31）；gzip 读的时候接受多个成员，Python 循环解（R32）；整数可以是负数（R33）；恢复密钥在 `restoreBegin` 里就写，放弃以后也不会有第二把（R34）。
- **建议**：空白和横线写成封闭的表（R35）；发布包只在写锁窗口存、同 ID 保留先存的、查 `release_id` 格式（R36）；`first`/`retry` 的定义写死、演练前上线（R37）；大小上限只用在恢复（R38）；单独代理项（R39）；读的时候不查 `counts` 的键顺序（R40）。

### 第 2 稿（第 1 轮 R1～R25）

按 `docs/reviews/pr-129.md` 的 R1～R25 全部采纳：

- **阻塞**：读的程序接受 64～16 MiB 的 2 的幂作块大小，写的程序固定 1 MiB（R1）；加第 3.7 节 JSON 行的写法（R2）；恢复密钥先存后显示、只在写锁窗口生成、干净设备不能生成、恢复时什么情况覆盖本机密钥（R3，第 2.3 节）。
- **应改**：gzip 的读写约定（R4，3.3）；严格 UTF-8、不带 BOM、校验和按原始字节（R5）；文件头重写后逐字节比较、第一行进 AAD、4096 不含换行、末块的认法（R6）；示例密钥换成合法的测试密钥、规整步骤和提示顺序、全角输入、校验强度说准（R7）；恢复后重算 `nextSeq`（R8）；原文和收据同一事务、标记记下文件、「不恢复了」的退路、标记还在时 `openSession` 照常（R9）；冻结时机、失锁就停、旧窗口让路、按 `oldVersion` 升级（R10）；存储接口（R11，5.2）；私人文字进备份要先写 ADR、竖切片 2 不能先上线（R12，3.6）；发布包存进本机并进备份（R13）；带过来的东西用比较键去重（R14）；清单和记录行的字段表（R15）；可读导出把换行换成空格（R16）；补黄金向量和升级测试（R17）。
- **建议**：导入记录也带过来、和本机的也比（R18，`archive` 合成一个仓库）；「干净」的定义和换身份安全的理由（R19）；本机存密钥的风险说准、加 `key_id`（R20）；「这一版还不认识的」单独计数（R21）；`first`/`retry` 按孩子算（R22，第 11 节）；分块的理由改写、附件可能要新文件格式、解压大小上限（R23）；恢复批次不能作废（R24）；显示存储是否持久、干净设备首页的恢复提示（R25）；每季度演练。
