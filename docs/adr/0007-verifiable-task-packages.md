# ADR-007 协作以可校验的任务包为准

- 状态：已接受（2026-11-06）
- 日期：2026-11-06
- 相关：CURIO-000（#2）、`docs/collaboration.md`、`docs/submission.md`

## 背景

实现 AI 看不到仓库，所以提示词必须把规格原样贴进去。但贴进去的只是复制品：规格改了，旧提示词里的还是旧版，这叫「契约漂移」。另外，长篇交付在聊天里传来传去，可能被截断、漏段，或者附件对不上号。

## 决定

1. **规格的原件只在仓库里。**提示词里贴的都是快照。
2. **每个实现任务生成一次性的任务包**，开头写明：
   - 基于哪个提交（`source_commit`）；
   - 契约版本；
   - 贴进来的每份资料的路径和 SHA-256。
   规格改了，旧任务包作废，重新生成。
3. **交付物由 Claude 校验**：用 `tools/intake.py` 收货，检查分段、清单、截断，算出每个文件的字节数和 SHA-256，记进 issue。实现 AI 只负责分段编号和结束标记，**不要求它算哈希**，因为没有代码环境的模型算不准。
4. **issue 粒度**：一个知识点一个主 issue，下面每个活动一个子 issue。状态标签贴在实际流转的那个 issue 上。
5. 以后会写一个生成任务包的脚本（`tools/make_task.py`），代替手工拼提示词，保证贴进去的规格和仓库里的一字不差。

## 放弃的方案

- **让实现 AI 直接访问仓库**：多个 AI 同时写仓库，会冲突、互相覆盖，也绕开了审核。
- **让实现 AI 自己报哈希**：算不准，会造成大量误判打回。

## 后果

- 任何一次交付，都能查到它基于哪一版规格。
- 这次修订已经在 PR #1 里部分落地（收货工具、交付包分段、issue 粒度）；任务包生成脚本留到第一个真实任务之前完成。

## 拍板结果（2026-11-06，Luka）

- **任务以文件形式交付**：每个任务包是一个 Markdown 文件 `<任务 id>.task.md`。Claude 在对话里把这个文件直接发给 Luka，Luka 原样上传给实现 AI。同一个文件提交到这个任务的工作分支，issue 里放它的链接，作为留档。
- 不再要求 Luka 从 issue 页面复制长文本，也就不会出现复制漏了一截的问题。
