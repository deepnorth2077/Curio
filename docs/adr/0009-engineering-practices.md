# ADR-009 开发实践：借鉴 Matt Pocock 的工程技能

- 状态：已接受（2026-11-06：Luka 要求吸收这套做法，PR #22 经外部模型审阅后由 Luka 确认）。有增补 1（按风险分四档审，2026-11-07）
- 日期：2026-11-06
- 相关：`docs/collaboration.md`、`GLOSSARY.md`、`docs/standards.md`、`docs/specs/TEMPLATE.md`、`docs/reviews/pr-22.md`
- 参考：[mattpocock/skills](https://github.com/mattpocock/skills)（MIT 许可），读的是 2026-10-31 的版本 `4ae2317`：grilling、domain-modeling、to-spec、to-tickets、tdd、code-review、prototype、retro、writing-for-agents

## 背景

Luka 要求后续开发吸收 Matt Pocock 这套技能里更好的做法。这套技能有一个前提：单个 AI 直接在仓库里写代码、自己跑测试。我们的前提不同：实现 AI 碰不到仓库，由 Luka 传话，Claude 是唯一的维护者（ADR-007）。所以不照搬技能本身，只吸收其中的做法，并改写成适合「传话」的形式。

## 决定

1. **按轮提问，附推荐答案**（来自 grilling）。需要 Luka 拍板时，把所有当前就能回答的问题（前提都已确定的那些）放在同一轮里一起问。每个问题都附上 Claude 的推荐答案，并且措辞成「回答『是』就等于采纳推荐」。查得到的事实由 Claude 自己去查，只把真正需要 Luka 决定的事交给他。
2. **术语表**（来自 domain-modeling）。仓库根目录的 `GLOSSARY.md` 每个词只写「指的是什么」，并列出「指这个概念时避免的说法」。任务文件只嵌入和这个任务相关的章节，加上「协作」一节。对象的 ID、生命周期、不变量仍写在 `docs/domain.md` 和 ADR 里，两边不重复。
3. **ADR 要节制**（来自 domain-modeling）。以后只有同时满足三条，才写 ADR：难以撤回；不交代背景，后来的人会奇怪「为什么这样做」；确实在几个方案之间做了取舍。三条缺一条，就写进规格或文档，不写 ADR。ADR 可以只有一段话。已接受的 ADR 怎么改，见 `docs/adr/README.md`。
4. **规格模板**（来自 to-spec）。新增 `docs/specs/TEMPLATE.md`，规格必须写明：问题、方案、**用户故事**（孩子、家长、维护者各自要什么）、实现上的决定、**测试接缝**、不做什么。测试接缝在写规格时就定好，并接受审阅。
5. **竖切片拆任务**（来自 to-tickets）。平台任务以**一个可以独立演示的外部行为**为单位，例如「做完分数挑战，星星亮起来」。只改这个行为需要改的层，不要求每个任务把所有层都改一遍。每个 issue 写清四件事：唯一的主流程、测试接缝、Luka 的演示步骤、明确不做的部分。
   - 一次交付装不下时，**缩窄行为**，不要把同一个行为按层切开。比如把「做完挑战点亮星星」缩成「只支持选择题的挑战点亮星星」，而不是拆成「先做存储」「再做界面」。
   - **例外**：知识点下的活动子 issue（内容任务）、工具、文档、预备改动，不按竖切片拆。影响面很广的机械改动，按「先扩展、再迁移、最后收缩」分成几步。
   - 每个 issue 写明「被哪些 issue 阻塞」。拆分方案先交 Luka 确认粒度和依赖，再建 issue。
6. **验收用例先行**（取自 tdd，但不是完整的测试驱动开发）。实现 AI 大多跑不了仓库里的测试，没法真正做到「先失败、再通过」，所以我们只取其中能做到的部分：
   - **测在接缝上**：提示词写明测试接缝，测试只通过公开接口检查行为，不测内部实现。
   - **期望值来自独立来源**：手算的字面值，或者规格里的例子，不能由被测代码自己算出来。
   - **高风险规则的验收用例由 Claude 在派发前写好**（事件、奖励、投影这类规则，写成黄金向量或验收测试），每条用例写明输入、完整的期望输出和手算依据。整合时，先确认这些用例在旧代码上失败，再确认它们在新代码上通过。
   - 审核时 Claude 还会故意改坏几处规则，看测试能不能发现，用来检验测试是不是真的在把关。
7. **审核分两条线**（来自 code-review）。审核评论分「规格」「规范」两节，各写各的结论，不混在一起排序：
   - **规格**：做的是不是规格要的；有没有漏做、做错，或者做了没要求的。
   - **规范**：是否符合 `docs/standards.md`。代码坏味道只算提醒。

   每条意见都标严重程度（阻断、重要、建议）和位置。一份交付可能规格对、规范错，也可能反过来，分开写才不会让一边盖住另一边。
8. **原型和复盘**（来自 prototype、retro）。
   - **原型**：回答交互和产品设计上的问题。做成用完就丢的单文件 HTML，Luka 不懂代码也能点着试。原型不进 `main`，只把结论写进规格。多设备同步、奖励去重这类行为规则，靠确定性测试和黄金向量验证，不靠原型。
   - **复盘**：每过一个里程碑（G1、G2……）做一次复盘。重点找能用自动检查拦住的错误：**能写成检查的，就不写成规则**。结果存在 `docs/retros/`。
9. **任务文件只带必要的东西**（来自 writing-for-agents）。实现 AI 看不到仓库，任务文件就是它的全部上下文，所以：
   - 只嵌入这个任务用得到的规格章节和术语；
   - 给出带独立期望值的正例和反例；
   - 写明它可以怎样自己验证（能跑测试的模型照着跑，不能跑的照着逐条核对）；
   - 用正面说法写要求（「每条用例写明手算依据」），少用禁令。

   嵌入内容和原件是否一致，由 `tools/make_task.py` 从已合入的提交读取并记录哈希来保证。

## 不采纳的部分

- **让 AI 在仓库里直接实现，并行开子 agent**（implement、implement-spec）：和「只有 Claude 碰仓库」（ADR-007）冲突。
- **用规格模板改写现有规格**：已合入的内容规格和事件规格不改写，新规格按模板写。
- **规格里不写文件路径**：to-spec 担心路径过时。我们的实现 AI 看不到仓库，交付清单必须写明路径，所以保留路径。

## 后果

- 审核评论变长一点，但「做错了」和「写得不好」不会再混在一起。
- 路线图已按竖切片重排（Luka 2026-11-06 确认，见 #13）：先做发布构建器（002b），再做第一条竖切片「分数挑战点亮一颗星」；Python 参考内核推迟到做同步的时候；浏览器内核随各条切片逐步长出来，黄金向量由 Claude 手算。
- 已经派发的 CURIO-003a 不受影响。

## 增补 1（2026-11-07）：按风险分四档审，子 agent 默认当实现者

- 状态：Luka 2026-11-07 在对话里采纳，等外部审阅（#77）
- 取代：原文「不采纳的部分」第 1 条（「并行开子 agent」那半句）；`docs/collaboration.md`「Claude 自己的改动」里「小的文档修正可以跳过审阅」的范围
- 不变：ADR-007（只有 Claude 写仓库；经 Luka 传递的交付走任务包和收货）

### 背景

前六个里程碑（M0–M6）里，每件事不论大小都走同一套审查。代价集中在两处：

- **Luka 传话**：7 个内容活动交给 Kimi，每个来回 1 到 2 轮，每轮 Luka 要传两次（发任务文件、带回交付包），一个知识点大约 6 到 12 次，还不算事实核对和审阅。「掰巧克力」做了一次多模型对比，一个模块就有 9 条记录。
- **审查花在不怕错的地方**：交接说明、小工具、原型界面这类改了也容易改回来的东西，和数据格式用同样的力气审。

同时，真正保住质量的是另外几样东西：外部模型在数据格式和流程上挑出的设计问题（PR #22、#46）；独立核对挑出的事实错误（`docs/reviews/life-manual-content.md`）；孩子试玩发现的问题（「答案全是 A」）。第一批讲解按旧流程过了全部审查，Luka 仍觉得没意思；改用 `curio-anatomy` 以后才好起来。审美靠的是方法和样板，不是审查的轮数。

### 决定

1. **按风险分四档**。一个 PR 跨几档，按最高的一档审；拿不准就往高一档放。

| 档 | 包括什么 | 怎么审 |
| --- | --- | --- |
| **A 难以撤回** | `schemas/`、事件和投影规则、ID、数据迁移、活动契约、放宽 CI 或检查规则、ADR | 和写的人不同的模型审阅（外部模型，或没参与过的 Claude 会话），意见存 `docs/reviews/`；ADR 和方向性决定要 Luka 确认；规则代码有正反测试和变异检查。AGENTS.md 说的「架构改动」就是这一档 |
| **B 科学事实** | 给孩子看的每一个事实：讲解、题目、正确和错误选项、提示、反馈、配图里的数量 | 一轮独立核对：没参与制作的子 agent 逐句对出处，拿不准的上网查权威来源。**每个学科的第一个知识点**（第一次做物理、化学、地理……）改用别家模型核对一次，校准子 agent 的盲点 |
| **C 体验和审美** | 动手模块、讲解、挑战、反思好不好玩、画面和手感 | 制作时按 `curio-anatomy` 和 `references/lessons.md` 自查；一个没参与制作的子 agent 审查；Claude 在无头浏览器里截亮色、暗色、手机三张图发给 Luka。**最终关口是 Luka 在 iPad 上看和孩子试玩**，知识点 PR 仍要等试玩结果才合入。不再用多个模型打分对比 |
| **D 其他** | 文档、交接快照、小工具、原型界面、重新生成内容包和试玩页 | Claude 自检，CI 通过就合入。改 `tools/` 仍要正反测试（AGENTS.md 原则 8） |

2. **内容和模块默认交给子 agent**。Claude 在自己的会话里开子 agent：Opus 实现，Sonnet 或另一个 Opus 审查（制作和审查不是同一个子 agent）。子 agent 不碰 git，写好的文件由 Claude 整合，所以 ADR-007「只有 Claude 写仓库」不变。子 agent 的产出不经过传话，**不用** `make_task.py` 和 `intake.py` 的哈希核对，但仍要：设计说明存 `prompts/<任务 id>.md`；审查记录存 `docs/reviews/`；提交写 `Implemented-By: <模型> 子 agent`。
3. **外部模型（Kimi、GLM 等）只用在三处**：A 档审阅；B 档每个学科第一个知识点的核对；Luka 特意想试一个新模型。这三处照旧走 ADR-007 的任务包和收货。
4. **两条线审核**（原文第 7 条）只用在 A 档和外部模型的交付上。C 档用 `curio-anatomy` 的审查清单。

### 后果

- Luka 的传话从每个知识点约 6 到 12 次降到 0，只剩 A 档审阅和偶尔的跨模型核对。Luka 的时间留给 iPad 上看和陪孩子试玩。
- **风险一：同一家模型的盲点相同**。制作、审查、核对都是 Claude，可能一起看漏同一类错误。对策：B 档每个学科第一个知识点用别家模型核对；C 档的最终关口是孩子，不是模型。
- **风险二：D 档自己合入，界面问题可能漏过去**。对策：另开一个 `chore/` 任务，把无头浏览器截图脚本放进 `tools/`（附测试），之后每个改原型或模块的 PR 都跑一遍。
- 复盘（原文第 8 条）时检查：有没有 D 档合入后才发现、本该往高一档放的改动；有就调整分档。
