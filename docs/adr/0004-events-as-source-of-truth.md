# ADR-004 事件是事实来源，状态由投影产生

- 状态：提议
- 日期：2026-11-06
- 相关：CURIO-003（#5）、CURIO-006（#8）、CURIO-008（#11）

## 背景

现在的事件格式只有 `verb + ts + 任意的 result`。它无法支持三件必须做到的事：

- **多端同步**：平板、电脑、手机都会产生事件，联网后要合并，既不能丢也不能重复。
- **审计**：能查出某个能量是因为哪件事发的。
- **十年重放**：换掌握度算法时，能用全部历史事件重新算一遍。

## 决定

1. **学习证据只追加。**事件写下后永不修改、永不删除。
2. **事件信封**，每条事件都有：
   - `event_id`：全局唯一，设备离线时自己生成（ULID）；
   - `learner_id`、`device_id`、`device_seq`（这台设备上的递增序号）；
   - `attempt_id`（做活动时）；
   - `occurred_at`（设备时钟）、`recorded_at`（服务器收到的时间）；
   - `schema_version`；
   - `node_id`、`activity_id`、`activity_version`、`content_release`（和内容相关时）；
   - `verb` 和 `payload`。每种动词各有一份 payload schema，不再共用一个任意对象。
3. **状态由投影产生**：掌握度、点亮、复习计划、能量余额，都是从事件算出来的。投影带 `algorithm_version`，换算法不改写任何历史事件，重新算一遍即可。
4. **有生命周期的对象**（错题、问题、航线、奖励）可以有状态，但每一次状态变化都要记成一条事件，例如「错题已打开」「错题已修好」。
5. **奖励不重复发**：每条奖励事件都写明是哪条事件触发的（`cause_event_id`）。同一个原因只能发一次奖励，重放、重复同步都不会多发。
6. **同步**：
   - 设备上先写进本地的 **outbox**（待发送队列），联网后上传；
   - 服务器按 `event_id` **幂等摄入**，同一事件收到几次都只算一次；
   - 用 `device_seq` 发现漏传。
7. **时间和顺序**：投影按「设备内用 `device_seq`，设备之间用 `occurred_at`」排序。设备时钟偏差超过一定范围时，以 `recorded_at` 为准，并在家长端提示。
8. **旧事件靠升级器读取**：格式升级时，写一个把旧版本转成新版本的升级器，原事件原样保留。

## 放弃的方案

- **直接存「当前状态」**（例如只存掌握度 70%）：简单，但多端合并会冲突，也查不出为什么是 70%。
- **按时间戳去重**：设备时钟不可靠，两件事可能落在同一毫秒。

## 后果

- 「同一次操作同步多遍，不会重复加分」由事件 ID 和 `cause_event_id` 保证，而不是靠小心。
- 事件会越来越多。按每天几百条估算，十年也只是几百万条，SQLite 和浏览器存储都应付得了。
- 原型里的 `MIGRATIONS` 思路保留下来，变成事件升级器。
