# ADR-004 事件是事实来源，状态由投影产生

- 状态：已接受（2026-11-06，经外部模型复审修订）
- 日期：2026-11-06
- 相关：CURIO-003（#5）、CURIO-006（#8）、CURIO-008（#11）、`docs/domain.md`、`docs/specs/events.md`
- 修订：2026-11-06，随事件规格（PR #21）修订第 1、2、3、5、6、7 节，详见 `docs/specs/events.md` 第 10 节

## 背景

原先的事件格式只有 `verb + ts + 任意的 result`，下面三件必须做到的事一件都支持不了：

- **多端同步**：平板、电脑、手机都会产生事件，联网后要合并，既不能丢，也不能重复。
- **审计**：能查出某一笔能量是因为哪件事发的。
- **十年重放**：换掌握度算法时，能用全部历史事件重新算一遍，而且每次算出的结果都一样。

## 决定

### 1. 学习证据只追加

事件写下后不修改、不删除。只有三种例外，而且都要留下痕迹：

- **隐私擦除**：附件（例如错题照片）按对象单独加密，需要擦除时销毁它的密钥。事件本身留下，但它引用的附件再也读不出来。
- **删除私人文字**：孩子或家长写的自由文字（反思、提问、备注）不放进事件，单独存为私人文字（PrivateText），事件只引用它的 ID。需要删除时追加一条「删除文字」事件，各处副本随之删除。事件本身留下，「孩子写过一段反思」这个事实不变。
- **撤销错误导入**：例如把别人的备份导错了。追加一条「作废」事件，指向那一批导入；投影跳过被作废的事件，原事件依然保留，可以追查。

除此之外，没有任何途径能改动或删除事件。

### 2. 事件信封

每条事件都有下面这些字段：

| 字段 | 说明 |
| --- | --- |
| `schema` | 事件格式版本，例如 `event/2` |
| `event_id` | 全局唯一，设备离线时自己生成（ULID） |
| `learner_id`、`device_id` | 属于哪个孩子，在哪台设备上产生 |
| `device_seq` | 这台设备上的递增序号，从 1 开始，不跳号 |
| `occurred_at` | 设备时钟记下的发生时间 |
| `actor` | 谁做的：孩子、家长，还是系统 |
| `attempt_id` | 做活动时才有 |
| `content` | 活动来源，和内容有关时才有：`node_id`、`activity_id`、`activity_kind`、`activity_version`、`content_release` |
| `import_batch` | 导入的事件才有 |
| `verb`、`payload` | 每种动词各有一份 payload schema，不再共用一个任意对象。payload 里不放自由文字，只放私人文字的 ID |

字段的完整定义以 `docs/specs/events.md` 第 2 节为准。

服务器什么时候收到这条事件（`recorded_at`），**不写进事件**，而是另存一张摄入收据（IngestReceipt）。这样同步、恢复、重放都不会改动设备产生的事件。

### 3. 唯一约束是防重复的最后一道关

ID 本身不能防重复，存储层的唯一约束才能。设备本地和家用后端都建这些约束：

- `event_id` 唯一；
- `(device_id, device_seq)` 唯一；
- 私人文字的 `text_id` 唯一。

摄入时撞上唯一约束，而且内容语义相同，说明这条事件已经收过：直接确认，不报错，也不产生任何效果。这就是**幂等摄入**。内容不同则是冲突，放进隔离区，不覆盖已有的事件。

另外两种「唯一」不在存储层，而在投影层，因为它们需要在多条事件之间做选择：

- 奖励流水：`(learner_id, cause_key, rule_id, currency)` 唯一（见第 5 条）；
- 航线：同一个孩子同一天只有一条**生效**航线（见第 7 条）。两台设备各建的航线都会被接收，由投影决定哪条生效。

### 4. 状态由投影产生

掌握度、点亮、复习计划、奖励余额，都是从事件算出来的。

- 投影带 `algorithm_version`。换算法时，不改写任何历史事件，用新算法重新算一遍即可。
- 同样的事件集合，不管以什么顺序到达、重放多少次，投影结果必须完全一样（见第 6 条）。

### 5. 奖励流水

能量、补给点不是一个可以随便加减的数字，而是一条流水（RewardEntry），余额由流水累加得到。流水本身也是**从事件确定性算出**的投影：每一笔都指向引起它的事件，存下来的流水表只是缓存，随时可以从事件重建出完全相同的结果。

| 字段 | 说明 |
| --- | --- |
| `entry_id` | 由唯一键算出的哈希，不同设备独立算出的结果相同 |
| `learner_id` | 属于哪个孩子 |
| `currency` | `energy`（能量）或 `supply`（补给点） |
| `kind` | `earn`（获得）、`spend`（花费，例如兑换）、`adjust`（家长手动调整）、`revoke`（撤销某一笔） |
| `amount` | 整数 |
| `cause_key` | 这笔流水「因为什么」，例如「某天的某项打卡任务」「某个兑换申请」。同一原因只算一次 |
| `cause_event_id` | 引起它的那条事件，用于追溯 |
| `target_entry_id` | 只有 `revoke` 有：撤销的是哪一笔 |
| `rule_id`、`rule_version` | `earn` 由哪条奖励规则、哪个版本算出来 |

规则：

- **`earn` 只能由奖励规则产生，设备不能直接写。**奖励规则读取触发事件（例如「完成实验」），按当时生效的规则版本算出要发什么。
- 一个原因可以产生多笔奖励（例如同时给能量和补给点），但同一原因、同一规则、同一种货币，**最多一笔**。这由第 3 条的唯一约束保证；多条事件争同一个原因时，按确定的规则选一条，其余列为冲突。
- 重放事件、重复同步时，规则再算一遍，产生的流水撞上唯一约束，自然被忽略，不会多发。
- 规则改版只对生效之后的触发事件起作用。已经发出的流水是历史事实，不会因为规则改了就重算。
- `spend`、`adjust`、`revoke` 由家长的操作事件产生，同样受唯一约束保护。孩子撤销打卡不产生 `revoke`：任务最终没完成，那笔 `earn` 自然就不存在。

### 6. 顺序：不追求跨设备的全局顺序

不同设备的时钟不可靠，离线设备的上传顺序也不固定。所以不去排一个「所有事件的真实先后」，而是：

1. **一次尝试之内**，按这台设备的 `device_seq` 排序，再由活动的状态机检查前后是否合理。一次尝试只发生在一台设备上。
2. **余额、计数这类投影**，设计成和顺序无关的加法：先加后加，结果一样。
3. **确实需要排序的地方**（例如两台设备同一天各建了一条航线，要决定保留哪条），用确定性的排序键：`(occurred_at, device_id, device_seq, event_id)`。同样的事件集合，永远排出同样的顺序。
4. `recorded_at` 只记在摄入收据里，**不参与排序**。设备时钟和服务器时间差得太多时，在家长端提示，但不改写事件。
5. **接受时钟风险**：投影只读设备记下的时间，所以设备时钟错了，按天计算的东西（例如每天的奖励）可能算错。这是有意的取舍：投影若去读服务器收到的时间，就不再只取决于事件集合，而且单设备阶段根本没有服务器时间可以对照。纠正靠家长撤销奖励。等后端上线、确实出现问题时，再写 ADR 加防护。

### 7. 有生命周期的对象

错题、问题、航线可以有状态，但每一次状态变化都要记成事件，例如「错题已打开」「错题已修好」。对象的当前状态，也是由事件投影出来的。

航线 `(learner_id, plan_date)` 唯一：两台设备离线时同一天各建了一条，同步后按第 6 条的排序键保留第一条，另一条算作「被取代」，它上面已经完成的任务合并到保留的那一条。「被取代」由投影得出，不另写事件。

### 8. 同步

- 设备先把事件写进本地的 **outbox**（待发送队列），联网后上传。
- 服务器按第 3 条幂等摄入，回执里带上已确认的最大 `device_seq`。
- 设备用 `device_seq` 发现漏传，并补传。

### 9. 旧事件靠升级器读取

事件格式升级时，写一个把旧版本转成新版本的升级器。原事件原样保留；读取时先升级，再进投影。

## 放弃的方案

- **直接存「当前状态」**（例如只存掌握度 70%）：简单，但多端合并会冲突，也查不出为什么是 70%。
- **奖励由设备直接写「+1 能量」**：一旦重放或重复同步就会多发，只能靠小心。
- **按时间排一个全局顺序**：设备时钟不可靠，结果会随上传顺序变化，没法重放。

## 后果

- 「同一次操作同步多遍，不会重复加分」由唯一约束保证，不靠小心。CURIO-003 要为此写专门的测试：同一批事件，换顺序、重复、跨设备交错到达，投影和余额结果必须完全一样。
- 事件会越来越多。按每天几百条估算，十年也只是几百万条，SQLite 和浏览器存储都应付得了。
- 原型里的 `MIGRATIONS` 思路保留下来，变成事件升级器。
