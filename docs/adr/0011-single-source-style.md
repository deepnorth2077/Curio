# ADR-011 画风只有一个出处：数值由宿主下发，代码按版本抄进模块

- 状态：提议（2026-11-11，等外部审阅和 Luka 确认）
- 日期：2026-11-11
- 相关：#107；ADR-003（发布不可变）、ADR-005（活动宿主）、ADR-008（不打包）；`docs/activity-contract.md`；`docs/specs/kit.md`

## 背景

Curio 的画风（暖纸面、手绘墨线、淡彩）现在抄了很多份，而且已经抄出了不一致：

1. **颜色和字体变量**在 `prototype/index.html`、`app/index.html`、`preview/template.html`、`references/starter.html` 和每个模块的 `index.html` 里各有一份。两套名字并存：外壳叫 `--c-sci`、`--c-math`、`--wash`，模块叫 `--sage`、`--apricot`、`--paper`。
2. **契约说颜色由宿主下发，实际只下发了一部分。**activity/1.1 的 `init.palette` 没有规定键名。原型发的是 `accentSoft`、`sci`、`math`；骨架只接受全小写加连字符的键，并且认的是 `accent-soft`、`sage`、`apricot`。结果：底色、墨线、强调色跟着宿主走，淡彩色块不跟。试玩页发的是空表。
3. **手绘线和页面骨架**（`sketchLib`、`Host`、`actions`、`ask`、防误触）每个模块整段抄一份。四个模拟模块里同名函数有 20 多个，每个模块 800 到 1300 行。多模型对比里，有一份交付只改错了手绘曲线函数的一个下标，整屏的线都扭了（`docs/reviews/bench.chocolate-split-01.md`）。
4. 平台要用约十年。期间一定会改画风，也一定会修骨架里的缺陷（`lessons.md` 里已有 32 条）。照现在的做法，每次都要逐个改模块。

同时有三条已接受的约束不能破：模块是单文件、不联网、单独打开也能玩（契约、ADR-005）；发布不可变，同一个发布的字节永远不变（ADR-003）；浏览器运行前不要求打包，提交进仓库的文件就是能运行的文件（ADR-008）。

## 决定

把「画风」分成两类东西，用两种办法管。

1. **数值在运行时由宿主下发。**数值指颜色表和明暗模式。契约升到 activity/1.2，只增不改：
   - `init.palette` 的键名写进契约，共 20 个，就是模块里 CSS 变量去掉 `--` 以后的名字（`bg`、`pane`、`hover`、`rule`、`ink`、`text`、`muted`、`accent`、`accent-soft`、`sage`、`sage-bg`、`sky`、`apricot`、`paper`、`dad`、`mom`、`good`、`good-soft`、`bad`、`bad-soft`）。宿主要发全；模块忽略不认识的键。
   - `init` 增加 `scheme`：`"light"` 或 `"dark"`。模块据此设置 `color-scheme`，不再自己看系统的明暗设置。
   - 这样以后改颜色、调深色模式，只改外壳一处，所有模块（包括已发布的）立刻跟着变，不用重新发布。
2. **代码按版本抄进模块，由工具管，由 CI 核对。**代码指变量的默认值、三种线的样式、`Host`、`sketchLib`、页面骨架。
   - 原件放在 `kit/<版本号>/`（`kit.css`、`kit.js`）。版本号是正整数，只增；旧版本的目录永远留着。
   - 模块的 `index.html` 里用一对注释标出库的位置（`/* curio-kit:1 begin */` … `/* curio-kit:1 end */`，样式和脚本各一段）。`tools/kit.py sync` 把库的内容写进这两段。**写进去以后的文件直接提交**，它本身就能运行，没有另外的源文件，也没有构建产物。
   - manifest 增加可选字段 `kit: <版本号>`。声明了它的模块，CI 逐字节核对两段内容和 `kit/<版本号>/` 一致；不一致就不能合入。这条检查代替现在靠人「逐字比对」。
   - 模块升级库的版本，是一次普通的改版：改 `kit`、重新同步、`version` 加一、照常审查。不升级的模块永远用它发布时的那一版。
3. **外壳用同一份数值。**`prototype/index.html`、`app/index.html`、`preview/template.html`、`references/starter.html` 里的基础颜色变量，也用同样的标记和同一个工具从 `kit/` 同步。宿主发 `palette` 时，按契约的 20 个键从自己的变量里取。
4. **名字统一到模块现在用的那一套**（`sage`、`sky`、`apricot`、`paper`）。它们说的是颜色，不是学科；哪个学科用哪个颜色，是外壳自己的事。外壳原来的 `--c-sci` 等名字保留为别名，指向这一套。
5. **库只收已经重复的东西。**第 1 版只收骨架里现在每个模块都抄的那些。把手、小牌子、拨盘这类零件，等有第二个模块要用时再加进下一版。
6. **已发布的 activity/1.1 模块不改。**宿主同时认 1.1 和 1.2：消息里的 `contract` 用模块 manifest 里写的那个；对 1.1 的模块也发新键名的 `palette` 和 `scheme`（1.1 的骨架会忽略 `scheme`，并且本来就接受这些键名）。

## 放弃的方案

- **宿主在运行时把库注入模块。**好处是改库不用动任何模块。放弃的原因：模块单独打开就不能玩了；同一个发布在不同版本的外壳上行为不同，和 ADR-003「字节不变」的精神相反；宿主要改写模块的内容，ADR-005 的边界变复杂。
- **另设源文件，构建时生成 `index.html`。**放弃的原因：仓库里会同时有源文件和产物，哪个是原件要靠约定；ADR-008 要求提交的文件就是能运行的文件。
- **把线宽、字号、动效快慢也放进 `init` 下发。**放弃的原因：现在没有任何要在运行时改它们的需求（`docs/standards.md`：只做规格要的）。它们留在库里，要改就出新版本。按年龄调字号用已有的 `init.age_band`，在库里处理。
- **保持现状，继续靠 `lessons.md` 和审查。**放弃的原因见背景第 2、3 条：已经抄出了不一致，也已经有人改坏。

## 后果

- 改颜色：改 `kit/` 里的变量，同步到外壳，所有模块在运行时跟着变。
- 修骨架的缺陷：出库的新版本；要吃到修复的模块各改一次版。旧模块不会被悄悄改变，这是有意的。
- 新模块只写 `MODEL`、场景和台词。目标是模拟模块 400 行以内（现在 800 到 1300 行）。
- 多了一个要维护的东西：`kit/` 和 `tools/kit.py`，以及 CI 里的一条检查。
- 发布清单的 `contracts` 里会同时出现 `activity/1.1` 和 `activity/1.2`（内容规格 3.8）。设备上的宿主要先支持 1.2，带 1.2 模块的发布才会切换过去。
- 库的每个版本一旦有已发布的模块在用，就不能再改一个字节：改了，CI 会让所有用它的模块都不通过。

## 拍板结果（2026-11-11，Luka）

三个问题都采纳了推荐：

1. 契约升到 activity/1.2，只增不改。
2. 颜色的名字统一到模块现在用的 `sage`、`sky`、`apricot`、`paper`，外壳的旧名字留作别名。
3. 已发布的四个模块先不迁移，只迁移染色体一个来证明没变样，其余等各自改版时再迁。
