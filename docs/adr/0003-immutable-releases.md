# ADR-003 内容发布不可变，事件引用内容版本

- 状态：已接受（2026-11-06，经外部模型复审修订）
- 日期：2026-11-06
- 相关：CURIO-002（#4）、CURIO-007（#9）、`docs/domain.md`

## 背景

git 历史能回答「文件是怎么改的」，回答不了「孩子那天做题时看到的到底是哪一版」。如果内容可以原地覆盖，旧的答题记录就会对不上：比如一道题改了答案，孩子之前那次「答错」就说不清了。

## 决定

1. **版本号**：知识点和活动都带 `version` 整数。改内容就加一，ID 不变。
2. **内容发布（ContentRelease）是一份不可变的清单**，内容包括：
   - 收录的每个知识点、每个活动的 ID 和版本；
   - 每个文件的 SHA-256；
   - 整个清单的内容哈希。
3. **发布的 ID 就是完整的内容哈希**：`rel_<SHA-256>`。同样的内容不管哪天构建，都得到同一个 ID。界面上可以显示成 `<日期> · <前 8 位>` 这样短一点的形式，但它只用于显示，不是身份。
4. **发布不可变**。要修订，就产生新版本和新发布。同一份内容重复构建，必须得到同样的哈希（可复现构建）。
5. **部署（Deployment）和发布分开**：「现在生效的是哪个发布」是一个可变的指针，每次切换都记一条：预览、生效、被取代、回滚。**回滚只改指针**，不删任何发布，也不改任何事件。
6. **事件引用发布**：每条和内容相关的学习事件，至少记录 `activity_version` 和 `content_release`。
7. **保留规则**：
   - 发布清单永久保留。
   - 文件（以后会有 SVG、图片、字体、语音）按内容哈希存一份，被多个发布共用，不重复存。
   - 被任何事件引用过的发布，它的清单和全部文件都永久保留，保证随时能打开当时的那一版。
   - 从来没有生效过、也没有被任何事件引用过的预览发布，可以清理。

## 放弃的方案

- **只靠 git 提交号**：一次提交里可能有还没发布的草稿，而且孩子的设备不知道 git。
- **允许热修改已发布内容**：省事，但历史记录会失真。
- **用日期加短哈希做 ID**：同样的内容在不同日期会得到不同的 ID，而且短哈希可能撞车。

## 后果

- 孩子做过的每件事，都能查到当时的内容版本，并且能打开那一版看（这是 Luka 要验收的六件事之一）。
- 设备上缓存当前发布和最近几个发布，断网时也能用。
- 构建管线（CURIO-007）负责生成发布清单和哈希；部署历史由它记录，家长端能看到并能回滚。
