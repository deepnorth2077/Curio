# ADR-008 当前不引入前端框架，浏览器运行前不要求打包

- 状态：已接受（2026-11-06，经外部模型复审修订）
- 日期：2026-11-06
- 相关：CURIO-005（#7）、CURIO-007（#9）
- 增补：文末「增补 1」（2026-11-07，提议）取代第 7 条。没被增补提到的原文继续有效

## 背景

前端要用很多年，而前端框架大约三到五年就换一代大版本，跟着升级的成本不低。Luka 不写代码，所以部署和更新越简单越好：最好拷贝文件就能运行，不需要在家里装构建工具。

## 决定

这是**当前阶段**的约束，而不是永久的技术立场。

1. **当前不引入前端框架。**使用浏览器原生能力：ES 模块、Web Components（只在需要时用）、CSS 自定义属性。
2. **浏览器运行前不要求打包。**源码就是可以运行的代码。写 JavaScript，用 JSDoc 注释标注类型；CI 里用 TypeScript 编译器只做类型检查（`tsc --noEmit`），不产生构建产物。
3. **内容构建用 Python**，和 `tools/` 下的检查脚本共用一套环境，产物是内容发布包（ADR-003）。
4. **离线**：用 Service Worker 缓存外壳和当前内容发布，断网时也能用。
5. **字体随项目自带**，只保留用得到的字形，不依赖 Google Fonts。
6. **原型 `prototype/index.html` 只作视觉和交互参考**，不作为正式代码的起点。正式代码按内核和外壳分目录。
7. **后端暂不定**，留到 CURIO-008 决定。届时的标准：单个进程，数据库用 SQLite，在 NAS 上用一个容器就能跑起来，依赖尽量少。

## 什么时候重新评估

出现以下任何一种情况，就写一份新 ADR，重新评估是否引入框架或打包：

- 通用活动引擎和界面状态管理的复杂度明显上升，原生写法开始难以维护；
- 测试、可访问性的维护成本，超过了引入框架的成本；
- 我们开始重复实现成熟框架早已解决的问题（例如自己写一套组件更新机制）；
- 浏览器原生能力或 TypeScript 的类型检查方式发生了不兼容的变化。

## 放弃的方案

- **现在就用 React、Vue 等框架**：生态好，但升级负担重，对家庭规模的项目来说收益不够。
- **TypeScript 加打包工具**：类型安全，但每次运行前都要构建，部署和排错都多一层。
- **继续维护单文件原型**：已经约 15 万字节，多个任务同时改必然冲突，也没法测试。

## 后果

- 写同样的功能，可能比用框架多一些代码；换来的是更少的依赖和升级工作。依赖也不会是零：类型检查用的 TypeScript、测试用的无头浏览器，照样需要定期升级。
- 打开浏览器的开发者工具，看到的就是源码，排错直接。
- 实现 AI 要遵守「不引入框架、不要求打包」这条约束，提示词里会写明。
